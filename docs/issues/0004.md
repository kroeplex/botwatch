# 0004 — Emit events as JSONL with a stable envelope, and report channel failures on the same stream

**Status:** Open
· **Kind:** Feature
· **Parent:** <a href="0001.md" title="0001 — botwatch: a one-shot `select` over many event sources">0001</a>
· **Feeds:**
  <a href="0005.md" title="0005 — Define the channel driver contract and ship a conformance kit every driver must pass">0005</a>,
  <a href="0006.md" title="0006 — Wait on every channel at once: the select, the two clocks, and the departure guards">0006</a>

> Standard output is the caller's entire view of what happened. Whatever
> `botwatch` fails to say there, the caller does not know — and the caller is
> usually a program, often a language model, reading line by line.
>
> Two things have to be true of that stream and neither is free. **Every line
> must be a JSON object**, so a caller never has to guess whether a line is data
> or a warning. And a source that has broken must **say so on the same stream**,
> because a broken source and a quiet one are otherwise identical from outside:
> the run exits `0` either way, the cursor is unchanged either way, and nothing
> else is written either way.
>
> There is also a trap that only appears in production. Piped stdout is
> block-buffered by default in most runtimes, so a design that promises events
> "as they are detected" delivers them all at once at exit instead — and works
> perfectly when tested by hand at a terminal.

## Background

A run's output is JSONL: one JSON object per line, written as each event is
detected *(sketch)*:

```console
$ botwatch --config watch.yaml --state state.yaml
{"channel":"dev-slack","type":"slack","kind":"message","id":"1785633376.000000","ts":"2026-08-02T01:16:16Z","meta":{},"payload":{"...":"driver-specific"}}
```

The envelope is `botwatch`'s; the payload is the driver's:

| Field | Owner | Meaning |
| --- | --- | --- |
| `channel` | botwatch | The stable key. |
| `type` | botwatch | The channel type, copied from config. |
| `kind` | driver | What sort of event this is (`message`, `commit`, …). `error` is reserved. |
| `id` | driver | Source-native identity, **stable across replays**. |
| `ts` | driver | When it happened **at the source**, RFC 3339. |
| `meta` | botwatch | The caller's opaque payload for this channel, echoed verbatim. |
| `payload` | driver | Everything else. |

### The silence problem

Now watch what a caller sees when a Slack token expires on Tuesday:

```console
$ botwatch --config watch.yaml --state state.yaml   # Tuesday
$ echo $?
0
```

```console
$ botwatch --config watch.yaml --state state.yaml   # a genuinely quiet week
$ echo $?
0
```

Identical. The exit code is `0` because the failure localised correctly and the
run completed; the state file's recorded position is unchanged because a failed
driver's position is deliberately left alone; and `inspect` reports the channel
as idle, which is exactly what it reports for a channel where nothing happened.

So `botwatch` writes a record of its own, in the same envelope, whenever a
channel fails:

```json
{"channel":"upstream-main","type":"git","kind":"error","id":"upstream-main@2026-08-02T01:05:31Z","ts":"2026-08-02T01:05:31Z","meta":{},"payload":{"error":"ssh: connect to host github.com: timed out"}}
```

Same shape, same `channel`, same `meta` — one more line, which a caller that
ignores kinds it does not recognise can skip for free. What it buys is that an
agent reading the stream sees the failure **while the run is still going**,
rather than inferring it from a silence that looks like good news.

### The one place `id` is deliberately not stable

The envelope promises `id` is stable across replays, and caller-side
deduplication is built on that promise. Failure records are the exception, and
they have to be: a channel that has failed on twenty consecutive runs should
report twenty records, because each is a separate observation of a source still
being unreachable — not a replay of the first one. Deduplicating by `id` would
collapse them into one, and it would do so silently, since a technique that
never matches never complains.

## Scope

Implements [Event output](0001.md#event-output) — the JSONL framing, the flush
discipline, the envelope and its ownership split, and
[failure records](0001.md#failure-records) — plus the rule that diagnostics
never appear on stdout.

**Out of scope:** *when* a record is written and whether it affects the run's
timing (a failure record does not open the boarding window — [0006](0006.md));
`last_event` not moving for a failure record ([0003](0003.md)); what any
particular driver puts in `payload` (the driver issues).

## The rules this implements

- **JSONL on stdout**, one self-delimiting JSON object per line, written as each
  event is detected rather than batched at exit.
  ([Event output](0001.md#event-output))
- **stdout is flushed after each record**, terminal or pipe. This is contract,
  not implementation detail: the claims "a streaming caller can start work
  during the window" and "a crashed run leaves behind what it had already
  reported" are both claims about what an *external observer* sees.
- **The envelope, and who owns each field** — including that `ts` is the
  source's time, not `botwatch`'s, and that `id` is stable across replays.
  ([Envelope](0001.md#envelope))
- **`kind: error` is reserved** for `botwatch`'s own records.
- **A failure record is written whenever a channel fails** — its stream ended in
  an error, *or* its driver rejected the channel's config before a stream ever
  started. ([Failure records](0001.md#failure-records))
- **Every failure record gets a fresh `id`**, derived from the channel key and
  the observation timestamp, so consecutive failures do not collapse.
- **`meta` is echoed verbatim** on every event from that channel, failure
  records included.
- **Diagnostics go to stderr, never stdout.** A caller parsing stdout must never
  have to skip a line. ([Envelope](0001.md#envelope))

## Acceptance

*Each criterion names the implementation it falsifies. A criterion that the
design's rejected alternative also passes is not coverage.*

- **Every line of stdout parses as JSON, under conditions that tempt an
  implementation to print.** Across a run with a failing driver, a run whose
  driver logs a warning, a run rejecting a channel's config, and a run that
  exits non-zero on a structurally invalid config: every line written to stdout
  parses as a JSON object — and in each of those cases stderr is **non-empty**.
  *Falsifies:* "diagnostics mostly go to stderr", which passes any test whose
  run is healthy; and suppressing diagnostics altogether, which would satisfy a
  stdout-only assertion while destroying the operator's only explanation. Both
  halves are needed.
  *(This rule had no criterion in [0001](0001.md).)*

- **The first record is readable through a pipe before the run exits.** With
  stdout connected to a pipe rather than a tty, a reader process has the first
  event's complete line in hand well before the boarding window closes; and a
  run SIGKILLed after its first event leaves that line already delivered to the
  reader.
  *Falsifies:* default block buffering, which delivers everything at exit and
  loses the buffer entirely to a SIGKILL. The pipe is load-bearing in the
  criterion: a terminal is line-buffered, so the broken implementation passes an
  interactive test perfectly.

- **`id` is fresh on failure records and stable on source events — in one
  test.** Twenty consecutive failing runs on one channel produce twenty failure
  records with twenty distinct `id`s. In the same suite, a source event
  re-reported on a later run (because the previous run's cursor was discarded)
  carries the **same** `id` both times.
  *Falsifies:* deriving a failure record's `id` from the channel key alone,
  which collapses twenty observations into one for a caller deduplicating by
  `id`; and making every `id` fresh — a per-record UUID — which passes the
  twenty-records half while destroying the deduplication the envelope exists to
  support.

- **A driver that never started still reports.** A channel whose driver rejects
  its config before any stream exists produces a failure record carrying that
  channel's `channel`, `type` and `meta`, and the validation error in
  `payload`.
  *Falsifies:* emitting records only from streams that raised, which leaves the
  most common config mistake — one bad channel in a generated config — entirely
  silent on the caller's only structured surface.

- **`meta` is echoed verbatim, and cannot displace the envelope.** A `meta`
  containing a nested mapping, a list, and a key literally named `channel`
  appears unchanged under the `meta` field of every source event from that
  channel **and** of its failure records, while the envelope's own `channel`
  field still holds the key.
  *Falsifies:* merging `meta` into the envelope's top level, where a caller's
  innocuous `channel` key silently rewrites the field every other guarantee is
  matched through; and omitting `meta` from failure records, which breaks the
  "one more line of the same shape" property the record's design rests on.
  *(This rule had no criterion in [0001](0001.md); its state-file half is in
  [0003](0003.md).)*

- **`ts` is the source's clock on events and `botwatch`'s on failure records.**
  An event whose source timestamp is an hour old is emitted with that hour-old
  `ts`, not with the time it was noticed; a failure record's `ts` is the moment
  the failure was observed.
  *Falsifies:* stamping every record with `now`, which is invisible in any test
  driven by a live source producing events in real time — the two clocks agree
  there — and wrong for every replay and every backfill.

- **A failure record is a `kind: error` and nothing else is.** No driver-produced
  event in the suite carries `kind: error`, and a caller filtering on it sees
  exactly the failure records.
  *Falsifies:* letting a driver's own error-ish event type occupy the reserved
  value, which makes a caller's failure handling fire on a source event.

## Decisions this issue owes

1.  **What happens when a driver yields `kind: "error"`.** The value is
    documented as reserved; the RFC does not say whether such an event is
    rejected, renamed, or passed through. Proposed: reject it in the conformance
    kit ([0005](0005.md)) as a driver bug, and have the runtime refuse to emit
    it, since the alternative is a caller that cannot trust the one field its
    failure handling keys off.
2.  **Whether `payload` on a failure record is only `{"error": "..."}`.** The
    sketch shows one key. Structured detail (an exception type, a retry-after)
    would be useful to an operator, and the shape should be settled before
    drivers start inventing their own.
3.  **Line length and encoding.** JSONL implies no embedded newlines and one
    encoding; a driver payload carrying a multi-line message must not be able to
    break the framing.
