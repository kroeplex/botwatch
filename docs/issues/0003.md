> Everything `botwatch` remembers between runs lives in a single file the caller
> holds. If that file is written at the wrong moment, half-written, or read back
> with the wrong idea of which sources are new, the result is the failure this
> design ranks worst: events that silently never arrive and leave no trace that
> they were skipped.
>
> The file does not exist yet, and neither does the reasoning that has to go
> with it — how a source that was removed from the config last week is
> recognised when it comes back, what "this source has never worked" looks like
> as distinct from "this source is new", and how long a source has been broken.
>
> Getting each of those wrong is quiet. A source that resumes from the wrong
> place reports nothing unusual; it just misses a week.

## Background

`botwatch` is a pure function of *(config, state, world) → (events, state′)*.
The state file is the only carrier of the middle term. It is YAML, it is
`botwatch`'s own artifact, and it is meant to be legible to a developer
debugging a driver at 2am *(sketch, abridged)*:

```yaml
version: 1
created: 2026-07-28T09:00:00Z     # when this state file was first written
updated: 2026-08-02T01:12:44Z     # when this run wrote it

config:                           # a complete copy of the config this run got
  version: 1
  defaults: {...}
  channels: [...]

channels:
  dev-slack:
    created: 2026-08-01T22:10:00Z # when this key was first seen
    updated: 2026-08-02T01:12:44Z
    last_event: 2026-08-02T01:12:41Z
    last_error: null
    meta: {}
    driver:                       # opaque to botwatch; the driver's own
      cursor: "1785633161.000000"
```

### The lifecycle, walked in order

A channel's identity is its `key`, and the interesting behaviour is what happens
when a key comes and goes. Follow one key across four runs:

| Run | Config | State file afterwards |
| --- | --- | --- |
| 1 | `old-experiment` present | `driver:` cursor recorded; `created` set |
| 2 | *removed from the config* | **retired**, not deleted: cursor kept, `retired:` stamped, and the channel's own config copied into its state block |
| 3 | still absent | untouched — no driver runs for a channel nobody configured |
| 4 | `old-experiment` back | `retired:` and the per-channel config copy both removed; the driver resumes **from the run-1 cursor** and reports what arrived while it was away |

Deleting on run 2 instead would make removing a line from the config a
destructive act. A caller that removes a channel for an afternoon — or by
accident, or through a bug in whatever generates its config — silently loses the
cursor and gets a replay or a gap when it comes back.

### The case that is easy to get exactly backwards

A driver is handed three things about its own channel: `config` (this run's),
`prev_config` (as last configured, or `None`), and `prev_state` (a position to
resume from, or `None`). The tempting shortcut is to key "am I new?" off
`prev_config is None`. Here is the trace where that skips a week:

```text
run 1   channel `upstream-main` is configured for the first time
        its driver fails: the remote is unreachable
        → no position recorded. `created` is set. prev_config exists.

run 2   the remote is back
        driver asks: prev_config is None?  → no, it was configured last run
        driver concludes: "not new, resume from my cursor"
        → there is no cursor. Either it crashes, or it starts from now.
```

Starting from now is precisely the silent gap retirement exists to prevent, and
it arrives from nothing more exotic than a driver failing on its channel's first
run. The division of labour: **state** answers *do I have a position to resume
from*; **config** answers *what has changed about how I am configured*. Only the
second is a comparison.

### The crash that eats the file

State is written **at exit**, after events have been emitted, so a run killed
mid-way leaves the previous run's state and the next run re-reports what was in
flight. That is at-least-once, and it is deliberate: a duplicate is visible and
annoying, a dropped event is invisible and wrong.

The guarantee only holds if the write is atomic. The obvious implementation —
open the path, serialise, close — killed mid-write leaves truncated YAML, and
truncated YAML is the dangerous kind of broken: it often *parses*, as a mapping
with the last few channels missing. The next run then treats every channel below
the tear as new and starts from now, on all of them, silently.

## Scope

Implements the [State file](0001.md#state-file) section of [0001](0001.md) —
schema, the atomic write, the common per-channel metadata and all its
clearing/freezing rules, retirement, and the classification that decides what
each driver is handed.

It also picks up two rules `0001` states outside any component's section, both
of which are about what `botwatch` writes and so have no other plausible home:
**[statelessness](0001.md#stateless)** — this file is the only thing written —
and the decision that
**[concurrent runs are undefined](0001.md#concurrent-runs-against-one-state-file)**,
with no lock, no detection and no waiting.

**Out of scope:** what a driver *does* with `prev_state` ([0005](0005.md));
when the write happens relative to the wait ([0006](0006.md)); reading the file
back for a human ([0007](0007.md)); removing retired state
([0008](0008.md)).

## The rules this implements

- **Format and audience.** YAML, machine-owned but legible. Callers do not parse
  it; [`inspect`](0007.md) is the sanctioned reader.
  ([Format and audience](0001.md#format-and-audience))
- **The whole config is embedded on every write**, and handed back next run.
  Storing a diff, a hash, or selected fields would each be smaller and each
  eventually wrong, because "which fields matter" is a per-driver question.
  ([Why the state file embeds the whole config](0001.md#why-the-state-file-embeds-the-whole-config))
- **Five cases must be distinguishable**: new, reconfigured, removed, returning,
  and *configured before but never positioned*. `prev_state`, not `prev_config`,
  is what separates a channel with a position from one without.
- **Common per-channel metadata** — `created`, `updated`, `last_event`,
  `last_error`, `last_error_at`, `failing_since`, `retired`, `meta`, `driver` —
  with `botwatch` owning all of them except `driver`.
  ([Common per-channel metadata](0001.md#common-per-channel-metadata))
  - `created` is **written once**, on the first run in which the key appears,
    and never rewritten — *including when that run's driver fails and records no
    position*.
  - `last_error` is cleared on the next run **in which that channel is
    configured** and does not fail. "Configured" carries weight: a retired
    channel is never run, so without it the rule fires vacuously.
  - `failing_since` is set on a run where the channel fails and had no *live*
    streak going in; `last_error_at` refreshes each failure. Together they
    bracket the streak.
- **Retirement retains.** A key absent from the config is retired, not deleted:
  cursor kept, `retired:` stamped, and the channel's config copied into its own
  state block. Both markers clear on return. Health fields **freeze** while
  retired and are **not carried forward** on return.
  ([Retired channels](0001.md#retired-channels))
- **The write is atomic** — temp file in the same directory, renamed over the
  target — and happens **at exit**, after events are emitted.
  ([Delivery semantics](0001.md#delivery-semantics))
- **A failed channel keeps its `driver:` block and gets its metadata anyway.**
  What obligation 4 leaves untouched is the recorded position, not the common
  metadata around it.
- **`meta` is copied from config verbatim.**
  ([Caller payload](0001.md#caller-payload))
- **This file is the only thing `botwatch` writes.** "Nothing lives in
  `~/.cache`, no lock directory is invented, no database appears" — the state
  file whose path the caller supplied is the entire memory between runs, which
  is what makes `botwatch` a pure function of *(config, state, world)* from
  outside. ([Stateless](0001.md#stateless))
- **Concurrent runs against one state file are undefined, and that is a
  decision.** There is **no advisory lock, no contention detection, and no
  waiting** for another run to finish. Not doing it is the caller's
  responsibility, and the caller is the party that can honour it, since it
  decides when to run.
  ([Concurrent runs against one state file](0001.md#concurrent-runs-against-one-state-file))

  The negative half is the one an implementer needs, because this is exactly the
  component where a lock looks like diligence. `0001` weighed it and refused:
  one paragraph in a design document, a long tail of platform-specific misery in
  an implementation, and a fresh question of its own — fail fast on contention,
  or wait? — to guard against something the caller can simply not do.

  > [!WARNING]
  > "Undefined" does not mean "unspecified, pick something sensible". Two runs
  > sharing a state file last-write-wins each other's cursors, and every event
  > covered by the losing write is dropped with no diagnostic, no non-zero exit,
  > and nothing in the state file to show it happened. That consequence is
  > documented for the caller; it is not a behaviour to hold an implementation
  > to, since the interleaving is undefined by design.

## Acceptance

*Each criterion names the implementation it falsifies. A criterion that the
design's rejected alternative also passes is not coverage.*

- **`created` is written once, dated from the first run the key appeared in —
  even if that run recorded no position.** A channel whose driver fails on run 1,
  succeeds on run 2, and fails again on run 3 carries the same `created` after
  all three runs, equal to run 1's timestamp.
  *Falsifies:* setting `created` when the `driver:` block is first written,
  which dates it from run 2; and re-stamping it on any run that records nothing,
  which walks it forward on every failing run. Both pass a test that only ever
  exercises a channel whose first run succeeded.
  *(This rule had no criterion in [0001](0001.md).)*

- **A killed state write leaves one of two exact documents.** SIGKILL delivered
  at many distinct points during the write leaves a file whose bytes equal
  either the previous run's file or the completed new one — never anything else.
  *Falsifies:* open-truncate-serialise. Asserting only that the file *parses* is
  not enough: a truncated YAML mapping usually parses, as a document missing its
  last channels, which is exactly the silent-gap case. The assertion has to be
  byte-equality with one of two known documents.

- **State advances at exit, not as events are emitted.** A run killed after
  events have reached stdout but before it exits leaves every cursor at its
  previous position, and the next run re-reports those events.
  *Falsifies:* advancing per-event or per-batch, which makes a crash swallow
  whatever was already accounted for.

- **All five cases are distinguishable, and the never-positioned case is handed
  the triple that makes it solvable.** For a channel that is new, reconfigured,
  returning, configured-but-never-positioned, and removed, the driver receives:

  | case | `config` | `prev_config` | `prev_state` |
  | --- | --- | --- | --- |
  | new | set | `None` | `None` |
  | reconfigured | set | set, differing | set |
  | returning (was retired) | set | **set** — from the per-channel copy | set |
  | never positioned | set | **set** | **`None`** |
  | removed | absent — no driver instantiated | — | — |

  *Falsifies:* sourcing `prev_config` only from the previous run's top-level
  config copy. That copy, by definition, does not mention a retired channel, so
  a returning channel would arrive with `prev_config: None` and be mistaken for
  a brand-new one — retaining the cursor only to have it ignored, which is the
  gap retirement was bought to avoid.

- **Retirement retains, and return clears both markers.** Removing a channel for
  one run and configuring it again on the next: the cursor survives untouched
  through the retired run, and on return **both** `retired:` and the
  per-channel `config:` copy are gone from its state block, while the cursor is
  still there.
  *Falsifies:* deleting on absence (loses the cursor); leaving `retired:` set
  (describes a live channel as retired through [`inspect`](0007.md)); and
  leaving the per-channel config copy behind (two sources of truth for a
  configured channel's config, free to drift).

- **The streak brackets, and clears together.** A channel failing on runs 1, 2
  and 3 carries a `failing_since` fixed at run 1 and a `last_error_at` that
  advances with each run. Run 4, in which it is configured and does not fail,
  clears `last_error`, `last_error_at` and `failing_since` together.
  *Falsifies:* re-dating `failing_since` on each failure, which makes it a
  duplicate of `last_error_at` and answers "broken since when" with "just now";
  and never clearing, which reports a channel that broke once a month ago as
  broken forever.

- **Retirement freezes the health fields; return re-evaluates them.** A channel
  that is failing when it is retired keeps `last_error`, `last_error_at` and
  `failing_since` byte-identical across any number of retired runs. Configured
  again and failing again on its return, it dates `failing_since` from the
  **return** run.
  *Falsifies:* scoping the clearing rule to "any run", which fires vacuously on
  the first retired run and discards how the channel stood when it went away;
  and carrying the frozen streak forward, which asserts the channel was failing
  throughout a period in which nothing was watching it.

- **A failed channel gets its metadata written and its position left alone.** A
  channel whose stream ends in an error has `updated`, `last_error`,
  `last_error_at` and `failing_since` written by that run, while its `driver:`
  block is byte-identical to the previous run's.
  *Falsifies:* skipping the whole block for a failed channel, which loses the
  error record; and rewriting the whole block, which advances a cursor on the
  word of a driver that has just failed.

- **`meta` reaches the state file verbatim.** A `meta` containing a nested
  mapping, a list, and a key named `channel` is present in the channel's state
  block with structure and keys unchanged, and is re-read identically on the
  next run.
  *Falsifies:* normalising, flattening, or filtering `meta` on the way in.
  *(This rule had no criterion in [0001](0001.md); its event-stream half is in
  [0004](0004.md).)*

- **The embedded config copy is complete.** After a run, the top-level `config:`
  equals the config as given — including driver-specific fields `botwatch` does
  not understand, `meta`, and the channels whose drivers failed.
  *Falsifies:* storing a diff, a hash, or a selected subset of fields, each of
  which passes any test whose config only uses fields the loader knows.

- **`last_event` moves only for source events.** A run in which a channel
  produces only a failure record leaves that channel's `last_event` at its
  previous value — `null` if it has never fired.
  *Falsifies:* setting `last_event` from anything written to stdout, which makes
  a permanently broken channel look freshly active.

- **A retired channel is never instantiated.** A key present in the state file
  and absent from the config produces no driver instance, no failure record, and
  no change to its state block.
  *Falsifies:* driving the run from the union of config and state.

- **A run writes nothing outside the state file's own directory, and leaves
  nothing behind but the state file.** Under a sandboxed `HOME` and a sandboxed
  working directory, a complete run creates no file anywhere except the state
  path and the temporary sibling the atomic write requires — and after exit the
  temporary sibling is gone. No cache directory, no lock directory, no database.
  *Falsifies:* a cache under `~/.cache` or `$XDG_CACHE_HOME` "for speed", a lock
  directory beside the state file, and a temp file left behind on a failure
  path — none of which any functional test notices, because each is invisible
  from the events and the state file, and every one of them breaks the property
  a caller relies on when it copies a state file to test against or generates
  one per context.
  *(This rule had no criterion in [0001](0001.md).)*

- **A second concurrent run is neither detected nor blocked.** With one run
  already waiting on a state file, a second run against the same file starts,
  proceeds, and completes without waiting for the first, without failing on
  contention, and without either run creating a lock file or lock directory
  anywhere.
  *Falsifies:* an advisory lock added "for safety" — which is the natural thing
  to reach for in precisely this component, and which converts a documented
  caller responsibility into a new failure mode the caller cannot see coming:
  a second run that blocks for the length of a twenty-minute quiet timeout, or
  exits non-zero on a condition `0001` decided not to have. The criterion
  asserts the *decision* — no lock, no detection, no waiting — and deliberately
  does **not** assert which run's cursors survive, because that interleaving is
  undefined by design and a test that pinned it would quietly make it defined.
  *(This rule had no criterion in [0001](0001.md).)*

## Open questions from [0001](0001.md)

- **State files written under an older schema**
  ([question 2](0001.md#open-questions)) — **assigned here.** This is the
  component that writes `version:` and the only one positioned to read it.

  The full question ("migrate in place, refuse loudly, or rebuild what can be
  rebuilt") does not have to be answered to ship, but **one part of it does**:
  what happens when the version is not the one this build writes. Today that is
  undefined, and both defaults are bad — a run that cannot start wedges the
  caller's loop on a file only a human can repair, and a silent reset to "start
  from now" on every channel is the total invisible gap this design ranks as its
  worst outcome. The minimum this issue must deliver is a **decided, documented,
  tested behaviour for an unrecognised version**, with the migration machinery
  itself deferred until there is a second schema to migrate from.

- **Where retirement ends** ([question 1](0001.md#open-questions)) — not here.
  This issue implements retention, which is the half that makes state grow;
  removal is [0008](0008.md), which is where that question closes.
