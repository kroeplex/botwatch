# 0008 — Specify `prune` and bound retired-channel growth

**Status:** Superseded by 0015
· **Kind:** Enhancement
· **Parent:** <a href="0001.md" title="0001 — botwatch: a one-shot `select` over many event sources">0001</a>
· **Builds on:**
  <a href="0003.md" title="0003 — Persist run state atomically, with a channel lifecycle that survives reconfiguration">0003</a>,
  <a href="0007.md" title="0007 — Add `botwatch inspect` for reading a state file's health out of band">0007</a>

**Superseded by [0015](0015.md),** which restarts the design from a smaller core.

> When a source is removed from the config, `botwatch` keeps its recorded
> position instead of deleting it, so that putting the source back resumes
> rather than starting over. That is deliberate — removing a line from a config
> should not destroy history — but nothing ever removes the retained state, so
> the file grows without bound.
>
> The design names a `prune` operation twice as the thing that removes it, and
> specifies it nowhere: no flag, no subcommand, no behaviour, no rule about what
> it may touch.
>
> This is not only a missing tool. The design document treats itself as complete
> once every open question is answered or explicitly deferred, and the question
> "where does retirement end" leans toward the answer *"never automatically —
> the caller runs `prune`"*. That answer cannot be adopted until there is a
> `prune` for it to point at.

## Background

Removing a channel from the config retires it rather than deleting it. The state
block survives, with a `retired:` timestamp and a copy of the config the channel
last ran under *(sketch, abridged)*:

```yaml
channels:
  old-experiment:                  # retired: kept, config and all
    created: 2026-07-28T09:00:00Z
    updated: 2026-08-01T18:00:00Z
    last_event: 2026-08-01T17:52:10Z
    retired: 2026-08-01T18:00:00Z
    config:                        # its config as it stood when last configured
      key: old-experiment
      type: git
      remote: git@github.com:example/experiment.git
      refs: [refs/heads/main]
    driver:
      refs:
        refs/heads/main: 91c4d7ab...
```

That retention is load-bearing. A caller that removes a channel for an afternoon,
or by accident, or through a bug in whatever generates its config, gets the
channel back with its cursor intact and reports what arrived while it was away.
Deleting on absence would give it a gap or a full replay instead, and would make
a config edit a destructive act.

**Now run that for a year.** A caller whose config is generated — which is the
expected case, since these configs are written by a language model — churns
channel keys as the things it watches come and go. Every key that ever appeared
is still in the file, with its cursor, its metadata, and a copy of its config.
Nothing removes any of it, because the only two things that touch the state file
are a run (which retires and never deletes) and `inspect` (which never writes).

The design already says who should remove it and roughly when:

> Retired state does not accumulate forever: it is what `inspect` surfaces and
> what a `prune` operation removes, **on the caller's schedule rather than as an
> invisible side effect.**

and lists garbage collection — "retired channel state, and state files for
contexts that no longer exist" — among the caller's own responsibilities. What
is missing is the operation itself.

### Why this is a design issue, not just an implementation one

Every other implementation issue in this set builds something the RFC already
settled. This one has to **decide** first, because the RFC's own completeness
criterion depends on it:

> [!IMPORTANT]
> The RFC is complete when its open questions are answered or explicitly
> deferred. Open question 1 ("where retirement ends") leans toward *never
> automatically; the caller runs `prune`* — and explicitly records that it
> **cannot close on that answer** until `prune` is specified somewhere for it to
> close onto. Answering it here is what this issue exists to do, and the
> answer should be written back into [0001](0001.md) when this lands.

## Scope

Specifies and implements `prune`: what it removes, what it must never remove,
how it is invoked, and how it writes.

**Out of scope:** retention itself and the retirement rules ([0003](0003.md));
reporting what is retired ([0007](0007.md)); state files for contexts that no
longer exist — deleting a whole state file is `rm`, and the design already
assigns it to the caller.

## The rules this must honour

`prune` is unspecified, but it is not unconstrained. The RFC pins four things
about it, and the specification has to be derived from them rather than invented
freely:

1.  **It runs on the caller's schedule, not as an invisible side effect.** So it
    is an explicit operation the caller invokes — never something a watch run
    does on the way past, however old the retired state is.
2.  **It removes *retired* state.** Retirement is the marker; age, silence, and
    failure are not.
3.  **Garbage collection is the caller's responsibility.** So `prune` is a tool
    the caller drives, and `botwatch` never escalates or decides for it.
4.  **Retirement exists to make removal reversible.** Pruning is the one
    operation in the system that is *not* reversible, so it has to be hard to
    fire by accident and easy to preview.

## Acceptance

*Each criterion names the implementation it falsifies. A criterion that the
design's rejected alternative also passes is not coverage.*

- **Only retired channels are removed.** `prune` removes channels carrying a
  `retired` timestamp and leaves every configured channel alone — including a
  live channel that has never fired, a live channel whose `last_event` is older
  than every retired channel's, and a live channel that has been failing for
  months.
  *Falsifies:* pruning by staleness or by silence, which reads plausibly and
  deletes the cursor of a channel that is quiet on purpose — a release branch
  that moves twice a year, a Slack channel used only during incidents.

- **A watch run never prunes.** No run of `botwatch` removes retired state, at
  any age, however many runs have passed since retirement.
  *Falsifies:* folding collection into the run "since it is already writing the
  file". This is the criterion that keeps the answer to **where retirement
  ends** honest: automatic removal reintroduces exactly the destructive
  behaviour retirement was built to avoid, and it does it on a schedule the
  caller did not choose.

- **A pruned channel comes back as a stranger; an unpruned one comes back as
  itself.** After pruning, re-adding the key behaves exactly like a
  never-before-seen channel: no `prev_state`, `created` dated from the re-add,
  and it starts from now. Without the prune, re-adding the same key resumes from
  the retained cursor and reports what arrived while it was away.
  *Falsifies:* leaving a tombstone or a partial block behind, which produces a
  channel that is neither — and it pins the two paths against each other, so
  neither can quietly become the other.

- **A killed prune leaves one of two whole files.** `prune` writes through the
  same temp-file-and-rename path as a run: SIGKILL at many points during the
  write leaves a file whose bytes equal either the pre-prune file or the
  completed post-prune one.
  *Falsifies:* an in-place rewrite, which is especially tempting here because
  the operation is "remove some keys" rather than "write the state" — and which
  can truncate the file into a document that still parses, with channels below
  the tear simply gone. That is indistinguishable, to the next run, from a prune
  that removed live channels.

- **Preview and execution agree.** A dry run reports exactly the set of channels
  a real prune then removes, against the same file.
  *Falsifies:* a preview computed by a separate code path from the removal —
  the usual way a "safe" preview stops matching what actually happens.

## Decisions this issue owes

These are the specification, and they are what **where retirement ends**
([question 1](0001.md#open-questions)) closes onto:

1.  **Surface.** A `botwatch prune <state>` subcommand, alongside `inspect`, is
    the obvious shape — it matches the read-only/writing split cleanly and keeps
    the watch run's argument surface unchanged. The alternative, a flag on the
    watch run, conflicts with *it runs on the caller's schedule* above.
2.  **Selection.** Whether `prune` takes an age threshold (`--retired-before`,
    `--older-than 90d`), an explicit key list, or defaults to *all* retired
    channels. Defaulting to all is the simplest and the most dangerous;
    requiring an explicit predicate is the safest and the most tedious.
3.  **Preview.** Whether the dry run is the default (`prune` reports, `--force`
    removes) or a flag (`--dry-run`). Given *retirement exists to make removal
    reversible* — this is the only irreversible operation in the system —
    reporting by default is the proportionate choice.
4.  **Output.** What `prune` prints, and whether it is the same rendering
    `inspect` uses for the channels it is about to remove. Sharing the rendering
    is attractive; sharing the *code path* between a reader that must never
    write and a writer is not.
5.  **Then close *where retirement ends* in [0001](0001.md)**
    ([question 1](0001.md#open-questions)) with the answer this issue
    implements, and remove the note recording that it could not close.

## Open questions from [0001](0001.md)

- **Where retirement ends** ([question 1](0001.md#open-questions)) —
  **assigned here**, and this is the issue that closes it. The RFC's leaning is
  *never automatically; the caller runs `prune`*, and the argument for it is
  that automatic removal reintroduces the destructive behaviour retirement
  exists to avoid. The cost it accepts — state files grow without bound if
  nobody ever prunes — is exactly what this issue's tooling makes manageable,
  which is why the question and the tool close together rather than separately.
