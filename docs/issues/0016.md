# 0016 — Retire sources that have gone quiet, with a heads-up one run ahead

**Status:** Open
· **Kind:** Enhancement
· **Parent:** <a href="README.md" title="Issues">Issues</a>

> An agent that joins threads keeps adding sources and rarely removes any. Most
> threads go quiet for good within days, so the watch set keeps growing unless
> the agent remembers when it last heard from each source and prunes by hand.
>
> This proposes that a source with `retire_after` set retires itself once it
> has been quiet that long. The run before it retires reports a heads-up, so
> the caller can keep it.

## Background

Each thread is its own source ([0015](0015.md)). An idle thread is cheap while
its first message is among the conversation's newest, but it still costs a
poll of its own once that message scrolls out, and every source stays in the
config, the state file and `botwatch show`. The caller can `botwatch remove` a
source, but only by tracking its quiet time itself.

## Proposal

**Config.** `retire_after`, a duration, on a source or at the top level as the
default for every source. Unset means never. Durations gain a `d` unit, and
`botwatch add` gains `--retire-after`.

**Quiet time.** The run records in the state file, for each source, when it
was last active: the end of the last run in which it emitted an event, or of
the run that first saved it. It's kept by the run rather than the source, so
every source type gets it. Excluded messages don't count, since the caller
never sees them. The local clock is fine at this granularity.

**Heads-up, then retirement.** At the end of every run, for each source with
`retire_after`:
1. If it emitted an event this run, it's active, and any heads-up is cleared.
2. Otherwise, if it already had a heads-up, it retires. The run emits
   `botwatch.source_retired`, removes the source from the config as
   `botwatch remove` would, and drops its state.
3. Otherwise, if it has been quiet for at least `retire_after`, the run emits
   `botwatch.source_retiring` and records the heads-up.

Both events are written as the run ends, after the linger, so they never wake,
extend or shorten a run. A heads-up therefore always comes one run before the
retirement, however long runs are, and a source that hears anything in between
stays.

**Keeping a source.** `botwatch keep --state STATE KEY…` clears a heads-up and
restarts the quiet time. It's meant to run between runs, as a heads-up arrives
when one ends.

**Retirement edits the config.** Removing the source keeps the config the live
watch set: `show` lists only what's watched, and `add` watches a retired source
again, from now. A run otherwise never writes the config. When it retires a
source, it re-reads the config and removes only that source, so a source added
during the run survives.

`show` gains each source's quiet time and any heads-up.

**The design spec** covers a source while it's configured. Retirement is a
removal, like one the caller makes, so a source's events end there. The new
events are `botwatch.*` events, which the spec already ignores.

### Considered and rejected

- **Leave the config alone and keep a tombstone in the state.** Then the config
  no longer says what's watched, and re-adding a retired source needs a way to
  clear its tombstone.
- **Retire at the start of a run.** A source would then miss anything posted
  between the heads-up and the next run.

### Open questions

- Should `botwatch add` of an already-watched source also restart its quiet
  time, in place of a separate `keep`?
- `retire_after` for every thread, but not top levels, wants per-type config
  defaults. Those are worth having for `exclude` too, so they're a separate
  change.

## Acceptance

- A source quiet for `retire_after` gets a heads-up as one run ends and retires
  as the next ends, unless it emits an event or is kept in between.
- Neither event wakes, extends or shortens a run.
- Retirement removes just that source from the config, keeping sources added
  during the run.
- `docs/design.md`, `docs/cli.md` and the README describe it.
