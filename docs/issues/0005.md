> **Superseded by [0014](0014.md) (2026-08-24).** The driver contract is folded
> into 0014's *sub-stream* model: three of the five obligations (2, 4, 5) carry
> over verbatim, and obligations 1 and 3 are generalised from *per source* to *per
> sub-stream* (source order holds within a sub-stream; state is a cursor map).
> The conformance kit is kept whole. Retained for that detailed reasoning; build
> from 0014.

> Each kind of source `botwatch` can watch is handled by a small piece of code
> called a driver. There will be many of them, most written long after the
> runtime is finished, and they all have to obey the same handful of rules.
>
> The rules are easy to state and easy to break by accident, and every way of
> breaking them is quiet. One mistake drops events permanently. Another replays
> the same events forever. A third turns the whole tool back into the busy
> polling loop it exists to replace — and it is committed by writing the most
> natural loop in the language.
>
> So the contract needs more than a written description: it needs an executable
> check that a driver author runs against their own driver, and that fails on
> each of those mistakes specifically.

## Background

A driver is instantiated once per configured channel, per run. The interface is
deliberately narrow *(sketch — illustrative, not prescriptive)*:

```python
class ChannelDriver(Protocol):
    def __init__(
        self,
        key: str,                            # the stable key
        config: ChannelConfig,               # this channel's config this run
        prev_config: ChannelConfig | None,   # as last configured, else None
        prev_state: DriverState | None,      # position to resume from, if any
        context: RunContext,                 # the run's shared settings
    ) -> None: ...

    def watch(self) -> AsyncGenerator[Event, None]:
        """The channel's event stream: one event yielded as each is detected."""

    def get_state(self) -> DriverState:
        """The state to record for next time."""
```

Events flow **out** and nothing flows in. The consumer — the runtime, which is
the only party that knows about the run's timing — decides when to stop pulling
and closes the stream, and that close is what runs the driver's cleanup and
makes its final state readable.

### Three mistakes, each written the obvious way

**One: the paging driver that drops events.** A source that returns pages is the
common case, and this is what a careful author writes first:

```python
async def watch(self):
    while True:
        page = await self._fetch(after=self._cursor)
        self._cursor = page.end          # ← recorded before anything is yielded
        for event in page.events:
            yield event
```

The consumer's close arrives **at a yield**, and nothing after it runs. Close
after event three of five and `get_state()` reports the position after event
*five*. Events four and five are never reported by any run: the next run resumes
past them. The fix is one line — update the record of "I have yielded this"
before each yield, not before the page.

**Two: the poller that ends its stream.** For a pull-based source, "nothing new"
is the ordinary result of almost every poll, and this loop reads perfectly:

```python
async def watch(self):
    events = await self._poll()
    for event in events:                 # ← empty on the first poll
        yield event                      #    so the loop body never runs
                                         #    and the generator returns
```

Ending the stream is not a way of saying "nothing right now". It is a positive
assertion that **this channel will produce nothing further for the rest of this
run**, and the runtime acts on it. With every driver written this way, the run
has nothing left to wait on, the caller relaunches immediately, and the tool has
become the hot poller it exists to replace — one process per tick, as fast as
the machine can spawn them.

**Three: the driver that decides it is new by looking at the wrong argument.**
`prev_config is None` looks like the natural test for "have I seen this channel
before". It gets exactly one case backwards, and that case arises from nothing
more exotic than a driver failing on its channel's first run — leaving a channel
that *has* been configured before and has *no* position to resume from. The
driver concludes "not new, resume", finds no cursor, and starts from now:
a silent gap. **`prev_state` answers "do I have a position"; `prev_config`
answers "what changed about how I am configured".**

None of the three is caught by a test that watches a healthy source and gets
some events. All three are caught by a kit that closes the stream at chosen
moments and inspects what the driver says afterwards.

## Scope

Implements [The channel driver contract](0001.md#the-channel-driver-contract)
and [The run context](0001.md#the-run-context) of [0001](0001.md), as:

1.  the **interface** — types, the `RunContext`, and the driver-facing
    documentation of the five obligations; and
2.  a **conformance kit**, which is three artifacts rather than one:

    -   the **driver-facing suite** — a reusable, importable test suite a driver
        package runs against its own driver;
    -   the **consumer contract** — the close-sequence checks factored out of
        that suite, parameterised over the consumer and **exported**, so the
        same checks can be run against a consumer this kit did not write. The
        kit's own stub is their first subject, not their only possible one; and
    -   the **fakes** both need — a fake source, a controllable consumer that
        can close a stream at a chosen instant, and a minimal `RunContext`.

**Out of scope:** the runtime that actually consumes the streams and enforces
the read-once/never-read-on-error rules ([0006](0006.md)); any concrete driver
(0009–0012).

The kit is the deliverable that makes this issue worth being separate. A written
contract that four driver authors read and interpret independently is a contract
with four dialects; a contract with an executable check has one.

**What the kit's consumer is, and what it deliberately is not.** It models the
**close discipline a driver is held to** — cancel the in-flight pull, await it,
then close — and nothing else. It does **not** model the runtime's read/record
policy, because that is [0006](0006.md)'s and asserting it here would certify
drivers against a lookalike of a component that does not exist yet.

That leaves one risk worth closing explicitly, since this issue lands before
0006 and every driver is certified against this consumer: the real runtime could
close streams differently from the stub, and four drivers would be conforming to
something they never run under. The obligation runs the other way to fix it —
**0006 is exercised through this kit's consumer contract** rather than the kit
being rewritten around 0006. The dependency already points that way (0006 builds
on this issue), so nothing is inverted, and the sequence drivers are certified
against is the sequence the runtime is checked against.

That obligation is only meetable if the contract is a **separable artifact**
rather than a property of the stub, which is why the **conformance kit**
deliverable above lists it as its own export and why the **consumer contract**
criterion below holds this issue to it. Written inline against the kit's own
consumer, the checks satisfy every driver-facing criterion here and still leave
0006's author looking for "the kit's consumer contract" and finding a fixture —
at which point the contract gets written in 0006, from 0006's reading of the
close discipline. That is two independent expressions of one rule by different
authors at different times, which is the drift this paragraph exists to prevent,
arriving one step later than expected.

## The rules this implements

The five obligations, from [0001](0001.md):

1.  **Yield each new event exactly once per run**, in source order where the
    source has one.
2.  **Stay open until the stream is closed, and release cleanly when it is.**
    Ending it sooner asserts the channel is finished for this run. What the
    driver owes *during* the close: release what it acquired, stop yielding, do
    not block the close on work that can be abandoned, and do not leave the
    state it is about to be asked for half-written.
3.  **Report state consistent with what was yielded.** Closed after three of
    five, `get_state()` describes position three. Reporting further **drops**
    events; reporting earlier **replays** them, which is merely wasteful — so
    exactness is the target and rounding down is the tolerable miss. A driver's
    own record of "I have yielded this" must be updated *before* the yield.
4.  **Localise its own failures.** A driver that cannot reach its source, or
    whose channel config does not validate against its own schema, fails *that
    channel* and leaves its recorded position untouched, rather than taking the
    run down.
5.  **Interpret nothing.** A driver reports that something happened and carries
    the payload; a deliberate crack is left open for bounded, declared,
    opt-in parsing where the driver is the only thing positioned to do it.

Plus the surrounding shape:

- **`context` carries the run's settings, not the config.** Handing over the
  whole `Config` would give every driver every other channel's config — access
  with no job attached, restrained only by a written rule nothing enforces.
  Widening later breaks nothing; narrowing later breaks every driver in the wild
  that reached through the wide type. ([The run context](0001.md#the-run-context))
- **`config` and `prev_config` stay explicit arguments**, not something to
  navigate the context for.
- **One instance per channel, and transport is private.** Ten `slack` channels
  means ten instances; whether they share a client underneath is the driver's
  business and nothing in the contract may pin it either way.
- **Cleanup runs under cancellation.** In Python the close reaches a waiting
  driver as a cancellation delivered at the suspension point inside `watch`, so
  a `finally:` that awaits must be short, local, and tolerant of not finishing.

## Acceptance

*Each criterion names the implementation it falsifies. A criterion that the
design's rejected alternative also passes is not coverage.*

Every criterion below is a check **in the conformance kit**: it runs against an
arbitrary driver, and every driver issue (0009–0012) passes it as part of its own
acceptance. **One exception**, marked where it appears — the **consumer
contract** criterion is *consumer*-facing rather than driver-facing. It holds
the kit itself to shipping a reusable artifact, and its second subject arrives
in [0006](0006.md) rather than in a driver issue.

- **State never runs ahead of the yields, and running behind is merely
  tolerated.** With a source of five events, the kit closes the stream
  immediately after taking the third and reads `get_state()`. Position three
  passes. Position two passes **with a recorded warning** (a tolerated replay).
  Position four or five **fails**.
  *Falsifies:* the paging driver above, which reports five. It also falsifies the
  obvious way to write this check — asserting `state == 3` — which would mark a
  legal, replaying driver broken, and, more importantly, a "within tolerance"
  check that accepted either direction, which would pass the dropping driver.
  The asymmetry is the point of the criterion.

- **A stream stays open across an empty poll.** Against a source that produces
  nothing for longer than several of the driver's own poll intervals, the stream
  is still open and still pending. Separately, a driver that *deliberately* ends
  its stream is allowed to, and its `get_state()` is **answerable afterwards**,
  describing the events it yielded.
  *Falsifies:* falling off the end of an empty poll loop (fails the first half);
  and a driver that ends its stream and then cannot say where it got to — one
  that leaves `get_state()` raising, or reporting a position it never reached
  (fails the second), which is the half a driver can be held to.
  *Scope:* whether the runtime **records** that state is the runtime's
  behaviour, not the driver's, and is [0006](0006.md)'s criterion — where it has
  the sharper falsifier, since it uses a driver whose `get_state()` raises if
  called and so observes "not called" rather than inferring it.

- **Cleanup runs from both suspension points.** The kit closes a stream while
  the driver is suspended mid-`await` inside its own body — the state every
  waiting driver is in when the boarding window closes — and asserts the
  driver's `finally:` ran and its resources were released. It then does the same
  with the driver suspended *at a yield*.
  *Falsifies:* cleanup written only on the normal loop-exit path, and cleanup
  that handles one suspension point but not the other. The mid-`await` case is
  the normal ending, not the edge case, so a kit that only tests the yield case
  passes a driver that leaks on every single run.

- **Events arrive in source order, per channel and not globally.** Against a
  source with a known order, the events a driver yields are in that order — in
  particular a driver that fans out concurrent fetches must not yield in
  completion order. The kit explicitly does **not** require ordering *between*
  channels.
  *Falsifies:* yield-on-completion, which is what any driver that parallelises
  page fetches produces by default and which no single-page test detects. The
  second half falsifies an over-strong check that would forbid the concurrency
  the whole design is built on.
  *(This rule had no criterion in [0001](0001.md).)*

- **All five configuration cases produce the right starting position — the
  never-positioned case included.** The kit constructs each
  `(config, prev_config, prev_state)` triple from [0003](0003.md)'s table and
  asserts where the driver starts:
  resume wherever `prev_state` is set; start from the agreed default wherever it
  is `None` — **including the case where `prev_config` is set and `prev_state`
  is `None`**.
  *Falsifies:* a driver keying "am I new?" off `prev_config is None`. That driver
  passes the new, reconfigured, returning and removed cases and fails only this
  one — which is why a kit that omits it certifies the bug.
  *(This rule had no criterion in [0001](0001.md).)*

- **A failing driver fails only its own channel.** A driver whose source is
  unreachable raises out of its stream; the kit asserts the exception is
  observable to the consumer as that stream ending, that the process is still
  alive, and that the driver did not attempt to exit or signal anything
  run-wide.
  *Falsifies:* a driver that calls `sys.exit`, or that catches its own failure
  and ends the stream cleanly — the second being worse, because it reports
  "this channel is finished for this run" and so produces no failure record and
  no `last_error` at all.

- **The context is narrow, and the channel's own config is not in it.** The
  kit's `RunContext` exposes the run-wide settings and nothing else, so a driver
  reaching for another channel's config fails to construct. In the same kit, a
  driver that navigates the context to find *its own* config also fails,
  because it is passed as an argument.
  *Falsifies:* handing drivers the whole `Config`, which no functional test
  would ever catch — it works fine and is only wrong later, when narrowing it
  breaks every driver that reached through it.

- **The declared-parsing crack stays opt-in and additive.** A driver variant
  that parses structure out of a payload emits the parsed fields **alongside**
  the raw payload, and filters nothing unless the channel's config explicitly
  turns filtering on. With it off, every source event reaches stdout.
  *Falsifies:* a driver that replaces the payload with its interpretation, or
  filters by default — either of which makes `botwatch` grow opinions about
  content on the caller's behalf.

- **The consumer contract is a separable artifact, not a property of the stub.**
  *(The consumer-facing criterion — the exception noted above.)* The
  close-sequence checks — cancel the in-flight pull, await it, then close, and
  the point at which a driver's `finally:` observes each step — run green
  against the kit's own stub, **and** are importable from outside the kit and
  runnable against a consumer the importer supplies. Demonstrated on a second
  consumer that shares no code with the stub.
  *Falsifies:* close checks written inline against the kit's own consumer — the
  natural way to write them, and a form that passes every driver-facing
  criterion above while leaving [0006](0006.md)'s "the kit's consumer contract
  is run against this runtime" unsatisfiable without re-deriving the contract
  there. It also falsifies exporting the checks with only the stub ever passed
  to them: a suite that has run against nothing but the consumer it was written
  beside is reusable by assertion rather than by test, and the coupling then
  surfaces in 0006 instead of here.

## Open questions from [0001](0001.md)

- **Startup position for a new channel** ([question 4](0001.md#open-questions))
  — **assigned here.** The question has two halves and they separate cleanly:

  - *Where does the decision live?* This is a contract question and it is
    answered here: **the driver decides**, because "now" means something
    different for a message timestamp, a ref SHA, and an acknowledgement id, and
    only the driver can render it. The contract states the default — start from
    now, not from the beginning of history, so a newly watched source does not
    dump its past at the caller — and the kit checks it.
  - *Should there be a `start: now | beginning | <cursor>` config key?* This
    half is **deferred on evidence**, per the RFC's own standard for widening a
    narrow contract: the first caller that genuinely wants backfill is what
    settles it. Until then a caller wanting history has the escape hatch the
    stateless design already gives them — hand-write a cursor into the state
    file, or start from an empty one. If it lands later it is additive, and
    [0002](0002.md) implements the validation.

- **Access to the overall config, current or previous**
  ([question 5](0001.md#open-questions)) — **explicitly deferred.** No use for
  either turned up that the channel-level `config` and `prev_config` did not
  already serve, and widening a narrow contract on a guess is how it stops being
  narrow.

  *Who decides, and when:* the author of the first driver that genuinely needs
  it, at the moment they need it, as an amendment to this issue naming the
  driver and the use. The trade is one-directional — widening later breaks
  nothing, narrowing later breaks every driver already in the wild — so there is
  no cost to waiting and a permanent cost to guessing. **No work is scheduled
  for this in any issue**; the deferral is the decision, and drivers 0009–0012
  should each note it if they find themselves wanting it.
