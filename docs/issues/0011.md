> An agent collaborating on a repository cares about pull requests opening,
> reviews arriving, comments being left, and checks going red. None of those is
> a git commit, and none of them moves a branch.
>
> The git driver watches refs, which is the right model for "code landed" and
> the wrong model for everything above. A review is not a ref moving; a check
> run failing is not a ref moving; a comment on a pull request is not a ref
> moving. Modelling them as one would mean stretching "a ref moved" past the
> point where it means anything.
>
> So this is a separate channel type, deliberately overlapping with the git one
> rather than carving the overlap out.

## Background

A repository configured twice, on purpose *(sketch)*:

```yaml
channels:
  - key: upstream-main         # refs: what has been pushed
    type: git
    remote: git@github.com:example/project.git
    refs: [refs/heads/main]

  - key: upstream-collab       # collaboration: PRs, reviews, comments, checks
    type: github
    repository: example/project
```

A push to `main` produces an event on `upstream-main`. It may **also** produce
one on `upstream-collab`, since a GitHub driver can report commits too. That
overlap is fine and deliberate: the two channels are independently keyed,
independently retired, and independently cursored, so a caller that wants both
configures both and a caller that wants one configures one. Suppressing the
overlap would cost more complexity than it saves, and it would mean one channel
silently changing what it reports based on what *another* channel is configured
to do.

### What is genuinely different from refs

```text
                                     is it a ref move?   has a ref-like cursor?
pull request opened                       no                    no
review submitted                          no                    no
review comment left                       no                    no
issue comment left                        no                    no
check run completed (red)                 no                    no
commit pushed to a PR branch              yes                   yes
```

Only the last row fits the git model, and it is the one already covered. The
other five are resources with their own identities, their own timestamps, and
their own notion of "what is new since last time" — which is not a SHA
comparison but a watermark over a list that can also be **edited in place**.

### The mutability problem, stated before it is discovered

This is where GitHub stresses the event envelope hardest, and it is worth
holding in view from the start:

```text
10:00  a reviewer leaves a comment          → event id = comment id, ts = 10:00
10:00  the agent reads it and acts
10:04  the reviewer edits the same comment  → same comment id
```

The envelope promises `id` is **source-native identity, stable across replays**,
and callers are explicitly told to deduplicate on it. A conforming caller
therefore **drops** the edited comment: same `id`, already seen. That is correct
behaviour for a replay and wrong behaviour for an edit, and nothing in the
design currently distinguishes the two.

The same shape reaches a pull request that is opened, then retitled, then
closed, then reopened — one resource, several things worth telling an agent
about.

**GitHub stresses it hardest, but it is not GitHub's to answer.** What an `id`
*means* when a resource changes is a promise the envelope makes to every caller
of every channel type — Slack messages ([0009](0009.md)) have the same shape,
and so do issue-tracker transitions and updated feed entries from `0001`'s own
*Further out* list. Answering it here would make `id` semantics vary by channel
`type`, which is the one thing the envelope exists to prevent. So the contract
belongs to [0004](0004.md), and what stays here is how *GitHub's* mutations are
detected and rendered.

## Scope

Implements the [GitHub](0001.md#github) channel type of [0001](0001.md) as a
driver conforming to [0005](0005.md).

**Out of scope:** ref watching, which is [0010](0010.md) — including for GitHub
repositories, where the remote git driver already works; the driver contract
([0005](0005.md)) and the envelope ([0004](0004.md)) — including, specifically,
what `id` means when a resource changes, which this driver renders rather than
decides.

## The rules this implements

- **GitHub is deliberately separate from git.** Pull requests, reviews, issue
  comments, and check runs are not refs and are not modelled as such.
  ([GitHub](0001.md#github))
- **The overlap with the remote git driver is deliberate and not suppressed.**
  A caller wanting both configures both; the two channels are independently
  keyed and independently retired.
- **`kind` distinguishes the resource types** within the `github` channel type,
  per the envelope's driver-owned `kind` field. ([Envelope](0001.md#envelope))
- **`ts` is the resource's own time at the source**, not when the run noticed.
- All five [driver obligations](0001.md#the-channel-driver-contract), verified
  through [0005](0005.md)'s conformance kit — obligation 4 in particular, since
  a rate-limited or 403'd GitHub API is the ordinary way this channel fails.

## Acceptance

*Each criterion names the implementation it falsifies. A criterion that the
design's rejected alternative also passes is not coverage.*

Plus: **the driver passes [0005](0005.md)'s conformance kit in full.**

- **The five collaboration events are reported, each with its own `kind`, and
  none as a ref move.** A pull request opened, a review submitted, a review
  comment left, an issue comment left, and a check run completing each produce
  an event with a distinct `kind`, and no event in the suite carries a ref name
  or a pair of SHAs as its identity.
  *Falsifies:* modelling collaboration activity as synthetic ref movement, which
  works well enough for the one case that has a SHA and produces nonsense for
  the four that do not.

- **A git channel and a github channel on one repository do not interfere.**
  With both configured: a push produces an event on each, each carrying its own
  `channel` and `meta`; the two hold independent cursors; and removing or
  retiring either leaves the other reporting exactly as before.
  *Falsifies:* suppressing the overlap — which makes one channel's output depend
  on whether an unrelated channel happens to be configured, and turns a caller
  removing a channel into a caller silently changing what a different channel
  reports.

- **A watermark is not a page boundary.** With more activity than one API page
  holds, a run reports every item exactly once and the recorded position after a
  close describes only the items actually yielded — including when the close
  lands part-way through a page.
  *Falsifies:* recording the page's end watermark before yielding its contents,
  which is the paging failure [0005](0005.md) exists to catch and which the
  GitHub API's pagination invites more strongly than any other source here.

- **A rate limit localises and does not advance anything.** A `403` with a rate
  limit, and a secondary rate limit, each produce a failure record, leave the
  channel's recorded position untouched, and leave the other channels reporting.
  *Falsifies:* retrying inside the driver until the run's timing is destroyed,
  and catching the limit to end the stream cleanly — which reports "nothing
  further this run" and so produces no failure record at all.

- **`ts` is the resource's time.** An event for a comment created an hour before
  the run started carries that hour-old `ts`.
  *Falsifies:* stamping the observation time, which agrees with the source on
  every live test and is wrong for the entire first run of any channel.

- **Every mutable GitHub resource is rendered under the envelope's answer, not
  a local one.** A comment edited, a pull request retitled, and a pull request
  closed and reopened each reach the caller as [0004](0004.md) decided a change
  is reported — the same rule the Slack driver renders against — so a caller
  deduplicating on `id` alone can tell each from a replay.
  *Falsifies:* answering the question inside this driver, which is the tempting
  move because GitHub meets it first and hardest, and which leaves `id` meaning
  one thing on `github` channels and another on `slack` ones; and re-reporting a
  changed resource under its original `id`, which a conforming caller silently
  drops.

## Decisions this issue owes

1.  **How GitHub's edits and state transitions are rendered** — the mutability
    problem above, minus the contract. **What an `id` identifies is not decided
    here**: it is owed by [0004](0004.md), which owns the envelope, and lands
    ahead of this issue by the existing dependency graph. Slack
    ([0009](0009.md)) renders against the same answer.

    What is decided here is GitHub's half: which field marks a revision
    (`updated_at` on comments and pull requests is the obvious candidate),
    whether a state transition is a different `kind` from an edit of the same
    resource, and which of the five resource types report changes at all versus
    only creations. The GraphQL and REST surfaces expose these differently,
    which ties this to the transport decision below.
2.  **What one `github` channel covers.** A whole repository, or one resource
    class (`pull_requests`, `checks`, …) per channel? Per-resource channels
    match the Slack driver's "one conversation, one channel" reasoning —
    independent keys, independent retirement, independent `meta` — and cost more
    API calls. Whole-repository is the fewest calls and the coarsest seam. The
    Slack precedent argues for the finer grain; the API's shape may argue back.
3.  **Transport.** Polling the REST API, the GraphQL API, or consuming
    `repos/{owner}/{repo}/events`. The events feed is closest to a genuine
    cursor and is famously incomplete; polling several resource endpoints is
    complete and expensive.
4.  **Credentials and scope.** Token handling stays outside the repo, and
    nothing about a token may reach a config, a state file, an event, or a
    failure record's `payload` — a `403` body in particular must be sanitised
    before it becomes an error string.
