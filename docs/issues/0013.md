# 0013 — Resync the vendored boilerplate before this repo is published

**Status:** Open
· **Kind:** Bug
· **Parent:** <a href="README.md" title="Issues">Issues</a>

> Three files in this repo are copies, maintained in another repo and pasted in
> here unchanged. Two of them carry something that shouldn't go public. One
> contains a paragraph naming an individual and a shell alias that exists only
> on that person's machines, as though it were general instruction. The other
> hardcodes a link into a private repo and prints it onto the front page of this
> repo's issue tracker, where it will 404 for every reader outside the org.
>
> Neither can be fixed here. Copying runs one way and by hand, so a fix has to
> be made at the source and re-copied — and the source has a fix pending for the
> paragraph and, so far, only an open question for the link.
>
> Usually that would just be slow-burn staleness. Here it has a deadline: this
> repo is meant to be open sourced, and neither defect is cheap to repair
> afterwards. The paragraph is public in the history as well as in the working
> tree, and the link sits on the first page a would-be contributor lands on.

## Background

### Three files here are copies, and fixing them here is the wrong move

A fresh clone of this repo has to be able to find the shared agent guide that
`CLAUDE.md` imports, with no setup step. That works because three files are
copied verbatim out of `kroeplex/dev-docs`, from its `boilerplate/` directory:

| file here | copied from |
| - | - |
| `.claude/skills/link-dev-docs/SKILL.md` | [`boilerplate/.claude/skills/link-dev-docs/SKILL.md`](https://github.com/kroeplex/dev-docs/blob/main/boilerplate/.claude/skills/link-dev-docs/SKILL.md) |
| `.claude/hooks/ensure-dev-docs` | [`boilerplate/.claude/hooks/ensure-dev-docs`](https://github.com/kroeplex/dev-docs/blob/main/boilerplate/.claude/hooks/ensure-dev-docs) |
| `scripts/render_issues` | [`boilerplate/scripts/render_issues`](https://github.com/kroeplex/dev-docs/blob/main/boilerplate/scripts/render_issues) |

Each copy says so in its own header:

```
<!--
  VENDORED FILE — source of truth in dev-docs:
    https://github.com/kroeplex/dev-docs/blob/main/boilerplate/…
  Copied verbatim into each Kroeplex repo; edit it upstream, not here.
-->
```

That header is the reason this issue exists rather than a one-line patch.
Editing the copy is the one move the contract rules out: the next person to
re-copy the file would silently revert it, and the divergence would be invisible
until then. A problem in one of these files gets fixed upstream and re-copied —
and this issue is the re-copy half, for two fixes that have not landed upstream
yet.

### The paragraph

`link-dev-docs` is a skill that walks an agent through repairing the symlink
chain pointing this repo at its local `dev-docs` clone. Its last branch — the
case where there is no local clone to link to — ends by telling the reader which
credentials to clone with, and it did that by narrating one contributor's machine
setup: a first name, that person's personal GitHub account, and a shell alias
that exists nowhere but their machines.

Nothing in it is secret, and the cost isn't disclosure. It is that machine-local
detail is worded as general instruction, so an agent anywhere else is told to
reach for an alias it does not have — in a file whose entire purpose is to be
copied into other repos.

It was found while reviewing [#1](https://github.com/kroeplex/botwatch/pull/1),
the PR that scaffolded this repo, where it was the only personal name in the
whole tree; the other eleven files had all been written for a public audience.
That review could not fix it, for the reason above, so it was raised upstream as
[`kroeplex/dev-docs#17`](https://github.com/kroeplex/dev-docs/pull/17), which
removes it from the source of truth. Merging that PR does not touch this repo.

This repo's own `CLAUDE.md` states the rule the paragraph sits crosswise to:
individual family members don't go into the history except where they
participate here directly — crediting a contributor for a point they raised is
right, narrating anything else about them is not.

### The generated index links a guide nobody outside the org can open

The second defect is in a different one of the three files, and it is the same
shape: not editable here, fixable only at the source, deadline at publication.

This repo's issue tracker has a landing page, `docs/issues/README.md`, and its
second line links the shared conventions guide. That page is **generated** by
`scripts/render_issues` — one of the three vendored files above, carrying the
same header — and the link is emitted from a constant:

```
scripts/render_issues:42
  readonly _GUIDE_URL="https://github.com/kroeplex/dev-docs/blob/main/docs/issue-tracking.md"

scripts/render_issues:194
  printf 'Conventions and how to write a good issue: **[the shared issue tracker guide](%s)**.\n\n' "${_GUIDE_URL}"
```

`kroeplex/dev-docs` is private. So is every other repo in the org today, which
is the only reason this has gone unnoticed — the link's correctness is an
accident of the current access setup, not a property of the link. Publish this
repo and the tracker's front page carries a 404 where it promises to explain how
to file an issue.

It is unfixable here twice over. Hand-editing the generated page does not
survive the next `render_issues` run — and worse than that, `--check` compares
against a fresh render, so a hand-patched link fails CI rather than merely being
reverted quietly. And `render_issues` itself is vendored, so the constant can
only change upstream.

Upstream now has the question, but not an answer:
[`dev-docs` 0011](https://github.com/kroeplex/dev-docs/blob/main/docs/issues/0011.md)
frames what a public repo's generated index should say when the guide is
private — omit the link, publish the guide, split the shared guides into a
public home, make the URL configurable, or vendor the guide — without choosing.
It also records that this repo's tree carries **nine** links into that private
repo across six files, of which this one is the only one that renders on a page
aimed at any reader; the other eight are the constant behind it and mentions
addressed to whoever edits the repo, and whether they are in scope is upstream's
call.

**This is why re-copying is not by itself enough.** Matching upstream delivers a
fix only where upstream has one, and for the link upstream has none yet — so
this repo could satisfy "byte-identical to `boilerplate/`" with the 404 fully
intact. That is what the second acceptance criterion below exists to catch, and
why it is written as an outcome rather than as a match. The outcome form also
survives `dev-docs` 0011 choosing to vendor the guide, which would make this
repo's vendored set four files rather than three — though under that option it
would catch a guide that was never copied, whose relative link 404s, and not one
whose copy has quietly gone stale against upstream.

### The working tree is not the whole job

This section is about the paragraph specifically. The link needs no equivalent
treatment: a dead URL in an old commit is unremarkable, and nothing about it is
worth rewriting history for.

The paragraph is in two places here, and overwriting the file only reaches one
of them.

`531a80c` — *Scaffold the repo: Kroeplex boilerplate and the issue tracker
(#1)* — is the only commit on `main` that touches any of the three vendored
files, and it introduced them complete with the paragraph. Since PRs here are
squash-merged, that single commit's diff is a full copy of the file as it stood.
Re-copying today therefore fixes the tip and leaves the old text in `git log -p`,
which becomes readable at the same instant the repo does.

Timing is what makes this worth writing down now rather than handling later.
The repo is private and nobody has cloned it, so rewriting that commit is
ordinary pre-publication housekeeping. Once it is public, the same rewrite is
neither quiet nor fully effective.

### Nothing is stale yet

As of 2026-08-03 all three vendored files here are byte-identical to
`boilerplate/` at `dev-docs` `main`. The drift this issue exists to fix does not
exist yet — it is created when `dev-docs#17` merges.

Note what that does *not* say about the link. Byte-identity is why the paragraph
is not yet stale; it is also why the link is already wrong. The copies match
upstream perfectly and upstream is the thing that is wrong, so for the link
there is no drift to wait for and never will be — only a fix to wait for.

Filing ahead of it is deliberate. The obligation lands in this repo, on whoever
publishes it, and nothing else in this repo would ever mention it; the tracking
issue for the general problem lives in another repo's tracker
([`dev-docs` 0008](https://github.com/kroeplex/dev-docs/blob/main/docs/issues/0008.md)),
which is not somewhere a person about to publish this repo has any reason to
look.

## The fix

1.  **Re-copy all three files** from `boilerplate/` at `dev-docs` `main`, once
    `dev-docs#17` has merged. Nothing local is being overwritten — no copy here
    has ever been edited — so this is a straight overwrite and a PR, not a
    merge.

2.  **Confirm the guide link before treating step 1 as done**, because the two
    defects wait on different upstream changes and will very likely not be ready
    at the same time. `dev-docs#17` is a specific pending PR; the link's fix is
    an open question ([`dev-docs` 0011](https://github.com/kroeplex/dev-docs/blob/main/docs/issues/0011.md))
    with five candidate answers and no decision. So expect the re-copy to happen
    twice, or to wait — and either is fine, as long as it is not mistaken for
    finished after the first pass. The second acceptance criterion is what makes
    the difference visible; a re-copy alone cannot.

3.  **Decide the history question at publication time:** whether `531a80c` is
    rewritten as well as the tip fixed. This issue deliberately does not
    recommend either course. Rewriting is cheap while the repo is private and
    unavailable afterwards, and none of this is a secret, so the call belongs to
    whoever publishes. What this issue owns is that it gets made on purpose
    rather than discovered afterwards by whoever first reads the history.

## Non-goals

-   **Not editing the copies in place.** That is what the vendored header
    forbids, and it would be reverted by the next re-copy without anyone
    noticing.

-   **Not solving propagation.** That an upstream fix reaches no copy is a
    general problem across every repo vendoring these files, and it is tracked
    where the source of truth lives, as
    [`dev-docs` 0008](https://github.com/kroeplex/dev-docs/blob/main/docs/issues/0008.md).
    This issue is only this repo's leg of it — the one with a deadline.

-   **Not choosing what the guide link should become.** Whether it is omitted,
    repointed at a public home, made configurable, or replaced by a vendored
    copy of the guide is
    [`dev-docs` 0011](https://github.com/kroeplex/dev-docs/blob/main/docs/issues/0011.md)'s
    decision, and it turns on questions about the whole ecosystem that this repo
    should not settle. What this issue owns is that whatever is chosen has
    arrived here before publication.

## Acceptance

-   All three vendored files here are byte-identical to `boilerplate/` at
    `dev-docs` `main`, and reached that state **before** this repo was
    published.

-   The guide link in the generated `docs/issues/README.md` **resolves for a
    reader outside the org, or is absent** — again before publication. Stated as
    an outcome rather than as a match with upstream on purpose: matching
    upstream delivers a fix only where upstream has one, so the criterion above
    can be fully satisfied with this defect intact. This one cannot.

-   Whether `531a80c` is rewritten as well as the tip fixed was decided
    explicitly — rewritten, or knowingly left — rather than discovered after
    publication.
