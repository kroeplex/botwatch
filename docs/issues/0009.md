> The first driver, and the one the whole design was pressure-tested against: an
> agent that needs to notice new messages in a chat workspace without keeping
> track of message timestamps itself.
>
> The decision that shapes it is what one watched unit *is*. A single Slack
> conversation — one Slack channel, one direct message, or one thread — is one
> botwatch channel, and a config that cares about six conversations has six
> entries. The economical-looking alternative, one entry that enumerates several
> conversations, breaks every operation the design's identity system exists to
> support.
>
> Threads are the case that catches people: a thread's replies are invisible to
> a read of a Slack channel's top-level messages, so watching a Slack channel and
> watching a thread inside it are two different subscriptions, not a whole and a
> part of it.

## Background

> [!IMPORTANT]
> **"Channel" is overloaded here and the ambiguity is dangerous.** A *botwatch
> channel* is a stream of events that can be waited on and selected over. A
> *Slack channel* is one kind of thing a botwatch channel can watch. This issue
> says "Slack channel" whenever it means the chat kind, and "conversation" for
> the Slack API's own umbrella term covering a Slack channel, a DM, and a
> thread.

Three conversations, three botwatch channels *(sketch)*:

```yaml
channels:
  - key: dev-slack             # a Slack channel
    type: slack
    conversation: C0123456789

  - key: alerts-dm             # a direct message
    type: slack
    conversation: D0246813579

  - key: kickoff-thread        # one thread inside dev-slack
    type: slack
    conversation: C0123456789
    thread: "1785600000.000200"
```

Each has its own `key`, its own recorded cursor, its own `meta`, and its own
retirement. `kickoff-thread` and `dev-slack` point at the same Slack channel and
are still two independent botwatch channels — which is the point.

### The seam that looks wrong and is right

One `dev-slack` entry that *also* watched four threads inside it looks
economical: one entry instead of five, one API client instead of five, one
cursor to keep. It is the wrong seam, and the reason is that keys, state,
retirement, and `meta` are all per-botwatch-channel:

| The caller wants to… | With one entry per conversation | With one entry covering five |
| --- | --- | --- |
| stop watching one thread | remove its entry; the rest are untouched | edit a list inside an entry, and hope the shared cursor still means something |
| annotate one thread ("reply in #ops") | `meta` on that entry | maintain a parallel lookup table — the exact thing `meta` exists to delete |
| re-add a thread later | resumes from its retained cursor | there was never a cursor of its own to retain |
| see which one broke | that channel's `last_error` | one `last_error` for five conversations |

If the per-conversation cost ever turns out to matter, that is a question for
the driver's insides — instances of a type may share a client behind the
interface — and not a reason to coarsen the config.

### The thread trap

```text
#dev  ├─ 09:00  "shipping the parser today"          ← top-level
      ├─ 09:02  "kickoff thread"                     ← top-level, has replies
      │           ├─ 09:05  "taking the lexer"       ← reply: NOT in the
      │           └─ 09:31  "lexer's green"          ←   channel-level read
      └─ 11:40  "parser's merged"                    ← top-level
```

A conversation-level read of `#dev` returns the three top-level messages and not
the two replies. So a caller that watches `#dev` and expects thread activity
gets silence, and a caller that watches `#dev` *and* the thread gets each
message exactly once from exactly one channel. There is no double-reporting to
suppress and no subset relationship to model.

## Scope

Implements the [Slack](0001.md#slack) channel type of [0001](0001.md) as a
driver conforming to [0005](0005.md).

**Out of scope:** the driver contract and its conformance kit ([0005](0005.md));
the envelope ([0004](0004.md)); anything about what a message *means* — routing,
mentions, commands — which is the consuming agent's job.

## The rules this implements

- **One botwatch channel per Slack conversation** — a Slack channel, a DM, or a
  single thread. Not one botwatch channel enumerating several. ([Slack](0001.md#slack))
- **A thread is its own subscription**, not a subset of its Slack channel's.
- **The cursor is a message timestamp**, which is a Slack-native, source-ordered
  identity and doubles as the event `id`.
- **Transport is the driver's own business.** One client per instance is a
  perfectly reasonable implementation and the right place to start; sharing one
  behind the interface is an option the contract deliberately leaves open and
  neither requires.
- All five [driver obligations](0001.md#the-channel-driver-contract), verified
  through [0005](0005.md)'s conformance kit rather than restated here.
- The [non-goal's deliberate crack](0001.md#non-goals): a variant that expects a
  particular header format in top-level messages, emits the parsed fields
  alongside the raw payload, and filters out messages that do not match — opt-in,
  per-channel, and clearly labelled.

## Acceptance

*Each criterion names the implementation it falsifies. A criterion that the
design's rejected alternative also passes is not coverage.*

Plus: **the driver passes [0005](0005.md)'s conformance kit in full**, which is
where the five obligations are checked.

- **Two keys on one conversation stay independent.** Two botwatch channels
  configured on the same Slack conversation with different keys keep separate
  cursors, are retired and returned independently, and carry their own `meta` on
  their own events — and a message in that conversation is reported once on each.
  *Falsifies:* coalescing instances by conversation id "since they are the same
  source", which silently couples two channels the caller deliberately
  separated, and makes removing one of them affect the other.

- **A Slack channel and a thread inside it partition the traffic.** With one
  botwatch channel on a Slack channel and another on a thread within it: a
  top-level message is reported on the first and **not** the second; a reply
  posted in that thread is reported on the second and **not** the first.
  *Falsifies:* modelling the thread as a subset of the Slack channel, which
  double-reports the reply or drops it depending on which way the containment is
  read; and a conversation-level read that silently misses thread replies, which
  no test watching only a Slack channel would ever detect.

- **Re-pointing a channel does not carry the cursor across.** Changing
  `conversation` on an existing key: the driver sees a differing `prev_config`
  and does not resume from a timestamp recorded against the previous
  conversation.
  *Falsifies:* resuming on the strength of `prev_state` alone. A Slack timestamp
  from another conversation is a perfectly valid-looking cursor — it is just a
  time — so this failure produces no error, only a wrong starting point.

- **`ts` is the message's time and `id` is stable across a replay.** An event's
  `ts` is the Slack message timestamp, not when the run noticed it; the same
  message re-reported on a later run (after a failed run discarded the cursor)
  carries the same `id` both times.
  *Falsifies:* stamping `ts` with the observation time, which agrees with the
  source's clock in any live test and is wrong for every replay and backfill.

- **A burst is one run.** Ten messages posted within the boarding window are
  reported by a single run, in source order.
  *Falsifies:* a driver that ends its stream after draining one page, which
  turns each message into its own run.

- **An expired token localises.** An auth failure on this channel produces a
  failure record, leaves its recorded cursor untouched, and leaves every other
  channel in the run reporting normally.
  *Falsifies:* raising past the runtime, and catching the failure and ending the
  stream cleanly — the second being worse, since it reports "nothing further
  this run" and so produces no failure record and no `last_error` at all.

- **A message the caller has already seen, edited and re-reported, is not
  silently dropped.** A message reported on one run and edited before the next
  is rendered according to [0004](0004.md)'s answer on what `id` identifies —
  so a caller deduplicating on `id` alone either sees the edit or is
  documentedly never sent it, and never receives a record it discards as a
  replay.
  *Falsifies:* re-reporting an edited message under the original message
  timestamp as its `id`, which is the natural implementation here because the
  timestamp *is* the Slack-native identity and doubles as the cursor — and
  which a conforming caller drops without a trace.

- **The parsing variant is additive and off by default.** With header parsing
  enabled, events carry the parsed fields **alongside** the unmodified raw
  payload and non-matching messages are filtered; with it disabled — the default
  — every message is reported and no payload is altered.
  *Falsifies:* a driver that filters or reshapes by default, which makes
  `botwatch` decide what content means on the caller's behalf.

## Decisions this issue owes

1.  **Which Slack surface.** Polling `conversations.history` /
    `conversations.replies` is the straightforward implementation and fits the
    pull model exactly. Socket Mode is a genuine push and would deliver events
    in milliseconds — but it makes this driver behave like [0012](0012.md)
    rather than like a poller, which is entangled with the per-channel timing
    question ([0006](0006.md), open question 3). Worth deciding deliberately
    rather than by whichever is easier to authenticate.
2.  **What "start from now" means for a conversation.** The current server
    timestamp, the newest message currently visible, or the moment the run
    started — they differ by whatever is in flight, and the difference is a
    dropped or duplicated message on a channel's very first run.
3.  **How Slack's mutations are rendered.** Edits, deletions, and reactions are
    changes to a message that already has an `id`, so they run into the
    envelope's promise that `id` is stable across replays. **The contract half
    of that question is not decided here** — whether a changed resource is a
    distinct event, and therefore whether `id` identifies a resource or an
    occurrence, is owed by [0004](0004.md), which owns the envelope, because it
    is a promise made to every caller of every channel type rather than a
    property of this source. [0011](0011.md) meets the same question from the
    GitHub side.

    What is decided here is the **rendering**: which Slack field marks a
    revision (`edited.ts` is the obvious candidate), whether a deletion and a
    reaction are worth reporting at all or are noise for this source, and what
    `kind` each carries. Those answers are Slack's and nobody else's — and they
    are only writable once 0004 has said what an `id` means, which the
    dependency graph already sequences ahead of this issue.
4.  **Credentials.** Token acquisition and storage stay outside the repo; the
    driver reads from the environment or a path, and nothing about a token
    reaches the config, the state file, an event, or a failure record's
    `payload`.
