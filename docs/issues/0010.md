> Watching a git repository means watching a small set of named pointers — the
> branches and tags — and noticing when one of them starts pointing somewhere
> else. That covers "something landed upstream", which is the signal an agent
> collaborating on a codebase most needs.
>
> There are two flavours and both are useful. A **remote** repository, reached
> over the network, shows what has been pushed. A **local** one, on disk, shows
> that plus work in progress: commits made and not yet pushed, branches created,
> a rebase happening.
>
> They are the same idea — a set of refs and the commit each points at — with
> different transports, so the working assumption is one driver rather than two.
> The way that assumption fails is worth stating up front: a ref that moves
> *backwards*, or sideways onto rewritten history, is not a smaller version of a
> ref that moves forwards, and a driver that reports "what is new since the last
> commit I saw" reports nothing at all when history is rewritten.

## Background

Two channels, one repository *(sketch)*:

```yaml
channels:
  - key: upstream-main         # remote: what has been pushed
    type: git
    remote: git@github.com:example/project.git
    refs: [refs/heads/main]

  - key: workspace             # local: also sees work in progress
    type: git
    path: /home/agent/src/project
    refs: [refs/heads/*, refs/tags/*]
```

The recorded position is a map from ref to the SHA it pointed at last time:

```yaml
driver:
  refs:
    refs/heads/main: 3f9a1c2e...
    refs/tags/v1.4.0: 91c4d7ab...
```

and a run compares that map against what the repository says now. The remote
case is `git ls-remote` (or a fetch); the local case reads the repository's own
refs. The concept is identical and only the transport differs, which is the
argument for one driver with a `remote:` key rather than two drivers with a
shared state schema they have to keep in sync by hand.

### The four ways a ref map differs, only two of which are obvious

```text
                   previous run          this run          what happened
refs/heads/main    3f9a1c2e              7b02fe11          moved forward
refs/heads/topic   —                     c41d0a83          created
refs/heads/old     55ab9e02              —                 deleted
refs/heads/wip     a19f7c30              6d8e2b44          force-pushed:
                                                           6d8e2b44 is not a
                                                           descendant of a19f7c30
```

A driver written as "diff the values of the keys present in both maps" reports
the first and the fourth and silently misses the second and third — and a driver
written as "list the commits reachable from the new SHA but not the old" reports
the first and misses the fourth entirely, because after a rewrite there may be no
such commits at all. Both are natural implementations. Both pass a test suite
built by pushing commits to a branch.

### Where the one-driver assumption would break

If the local variant grows a genuinely different *capability* — watching the
working tree or the index, which have no remote analogue — that is the moment to
split. Until then the split would buy two config shapes and two state schemas
for one concept.

## Scope

Implements the [Git](0001.md#git) channel type of [0001](0001.md) as a driver
conforming to [0005](0005.md), covering both the remote and local transports.

**Out of scope:** pull requests, reviews, comments, and check runs — none of
those are refs, and stretching "a ref moved" to cover them is exactly what
[0011](0011.md) exists to avoid; the driver contract itself ([0005](0005.md)).

## The rules this implements

- **Remote and local are both supported**, and both are valuable: remote is the
  "something landed upstream" signal, local additionally sees work in progress.
  ([Git](0001.md#git))
- **One driver, with a `remote:` key**, on the RFC's leaning — the concept is a
  set of refs and their SHAs, only the transport differs, and one driver keeps
  the config simple and the state schema shared. **Split when the local variant
  grows a capability with no remote analogue**, not before.
- **The cursor is the ref→SHA map** — a cursor like any other.
- All five [driver obligations](0001.md#the-channel-driver-contract), verified
  through [0005](0005.md)'s conformance kit.
- **Overlap with [0011](0011.md) is deliberate and not to be suppressed**: both
  can report a commit, and a caller wanting both simply configures both.

## Acceptance

*Each criterion names the implementation it falsifies. A criterion that the
design's rejected alternative also passes is not coverage.*

Plus: **the driver passes [0005](0005.md)'s conformance kit in full.**

- **Creation and deletion are reported alongside a move, and a stationary ref is
  not.** In one run: a ref that moved, a ref that appeared, a ref that was
  deleted, and a ref that did not move. The first three produce events,
  distinguishable from one another; the fourth produces nothing.
  *Falsifies:* diffing only the keys present in both maps, which misses creation
  and deletion — the single most common way this driver is written, and one that
  passes any test that only ever pushes to an existing branch.

- **A force-push is reported and is distinguishable from a fast-forward.** A ref
  moved to a commit that is **not** a descendant of its previous SHA produces an
  event carrying both SHAs and marked as not-fast-forward; a ref moved forward
  produces an event marked as one.
  *Falsifies:* computing "commits reachable from new but not old" and reporting
  that. After a rewrite that set can be empty, so the run reports **nothing** —
  a rebase or an amended commit lands upstream and the agent never hears about
  it.

- **Widening `refs:` does not reset the ones already watched.** Adding a pattern
  between runs: refs already in the recorded map keep their SHAs and report only
  genuine movement, while newly matched refs establish their current SHA as a
  starting point rather than reporting their entire history.
  *Falsifies:* rebuilding the map from scratch when the config changes, which
  replays every watched ref; and treating newly matched refs as "moved from
  nothing", which floods a caller with one event per existing branch the first
  time a pattern is widened.

- **Local and remote on one repository are independent, and see different
  things.** Two channels on the same repository — one `remote:`, one local — hold
  separate ref maps. A commit made locally and not pushed is reported by the
  local channel and **not** by the remote one; after a push, the remote channel
  reports it.
  *Falsifies:* a one-driver implementation that lets the two transports share
  any resolved state. This is also the criterion that **tests** the
  one-driver-with-a-`remote:`-key decision rather than assuming it: if the two
  cannot be kept independent inside one driver without contortion, that is the
  evidence for splitting.

- **An unreachable remote localises.** A network failure or a rejected key
  produces a failure record, leaves the ref map untouched, and leaves every other
  channel reporting.
  *Falsifies:* letting a `git` subprocess failure escape the driver, which takes
  the run down over one unreachable host.

- **A ref pattern that matches nothing is not a failure.** A config whose `refs:`
  currently matches no ref in the repository produces no events, no failure
  record, and a stream that stays open.
  *Falsifies:* treating an empty match as an error (which produces a spurious
  `last_error`) and treating it as "nothing further this run" by ending the
  stream — the latter removing the channel's arm from the select on every run.

## Decisions this issue owes

1.  **What `ts` means for a ref move.** The envelope defines `ts` as *when it
    happened at the source*, and a ref move has no single obvious answer: the
    commit's author date, its committer date, or the moment the move was
    observed. They can differ by a lot — a ref moved to a six-month-old commit
    is an ordinary rebase or revert. This is a real gap in the design as it
    stands and should be settled here, then reflected in [0001](0001.md)'s
    envelope table if the answer needs to generalise.

    **This is the same decision as *how much of the object graph the driver
    obtains*, below**, seen from the other side: every commit-date answer needs
    the commit object, which `ls-remote` does not return. That decision settles
    that the driver has the object graph, so what is left here is genuinely the
    *semantic* choice between author date, committer date and observation
    time — not the availability question it reads as today. Whoever picks up
    one picks up both.
2.  **Ref matching syntax.** `refs: [refs/heads/main]` is exact; the sketch above
    assumes globs. Whether patterns are globs, prefixes, or `git`'s own refspec
    syntax, and whether a pattern and an exact ref can be mixed.
3.  **How much of the object graph the driver obtains — no longer *whether*.**
    `ls-remote` gives SHAs without transferring anything, and that is not
    enough: the acceptance criterion above requires every ref move to be marked
    fast-forward or not, which is an ancestry test that needs the commit graph.
    **That criterion settles the availability question in the affirmative for
    both transports**, deliberately and not by accident — a remote channel that
    reports nothing when history is rewritten is the exact failure the
    criterion's own *Falsifies* clause describes, and "which transport did you
    configure" is not a reason for an agent to stop hearing about force-pushes.

    What is genuinely open is the *how*: how much of the graph to obtain and at
    what depth, whether the local transport may take a cheaper path since it
    already has the objects, and whether some cheaper mechanism than a full
    fetch can answer the ancestry question. The requirement is stated in terms
    of the graph rather than of `git fetch` so that a cheaper answer is not
    ruled out by the wording. How this lands is still a point of evidence for or
    against the one-driver decision. See also *what `ts` means for a ref move*,
    above, which this settles half of.
4.  **Local repository liveness.** Whether the driver watches the filesystem
    (inotify and friends) or polls the ref files, and what it does with a
    repository that disappears mid-run.
