# 0002 — Load the config and enforce the channel key contract

**Status:** Open
· **Kind:** Feature
· **Parent:** <a href="0001.md" title="0001 — botwatch: a one-shot `select` over many event sources">0001</a>
· **Feeds:**
  <a href="0003.md" title="0003 — Persist run state atomically, with a channel lifecycle that survives reconfiguration">0003</a>,
  <a href="0006.md" title="0006 — Wait on every channel at once: the select, the two clocks, and the departure guards">0006</a>
· **Related:**
  <a href="0007.md" title="0007 — Add `botwatch inspect` for reading a state file's health out of band">0007</a>

> `botwatch` is handed a file naming the sources it should watch. Everything it
> later promises rests on reading that file correctly: which sources exist, what
> identity each keeps across runs, and how long the run is willing to wait.
>
> None of that exists yet. No code parses the document, nothing rejects two
> sources that claim the same name, and nothing keeps a name usable as a
> directory component if the state layout ever needs one.
>
> The part most likely to be got wrong is not the parsing but the **error
> boundary**: some malformed input must stop the whole run, and some must stop
> exactly one source and leave the others working. Putting a case on the wrong
> side of that line either wedges a caller's loop over one bad line, or lets a
> broken name silently take over another source's history.

## Background

A `botwatch` config names the sources to watch and the timing the run should
use *(sketch)*:

```yaml
version: 1

defaults:
  quiet_timeout: 20m
  boarding_window: 2s

channels:
  - key: dev-slack
    type: slack
    conversation: C0123456789

  - key: upstream-main
    type: git
    remote: git@github.com:example/project.git
    refs: [refs/heads/main]

  - key: build-events
    type: pubsub
    subscription: projects/example/subscriptions/builds
    meta:
      notify: "#builds"
```

Three fields belong to `botwatch` — `key`, `type`, and `meta`. **Everything
else under a channel belongs to the driver for that `type`**, and `botwatch` is
not qualified to judge it: it has never heard of `conversation`, `refs`, or
`subscription`, and adding a driver must not mean teaching the loader a new
schema.

`key` is the load-bearing one. It is how a channel is recognised as *the same
channel* on the next run, when the list has been reordered, a channel inserted
above it, and its driver fields rewritten. Position cannot do that job and the
driver fields cannot either, since changing them is one of the cases that has to
keep working. It is the same problem as `key` on a React element, and it has the
same solution.

**Now the case that decides this issue's shape.** These configs are expected to
be written by a language model, so one malformed channel out of ten is routine
rather than exotic. Two failures that look equally like "bad config" have to end
differently:

```yaml
channels:
  - key: dev-slack           # ← duplicate: two channels claiming one identity
    type: slack
    conversation: C0123456789
  - key: dev-slack
    type: slack
    conversation: C0987654321
```

```yaml
channels:
  - key: dev-slack
    type: slack
    conversation: 12345      # ← the Slack driver wants a string, not an int
  - key: upstream-main       # ← nine other channels, all fine
    type: git
    remote: git@github.com:example/project.git
```

The first breaks **identity**, which every other guarantee is matched through,
so there is no coherent "the other nine still work" to fall back on: the run
cannot be constructed, and it exits non-zero having run no driver. The second
breaks one channel's own fields, which only its driver could have judged in the
first place, so it localises — a failure record on stdout, the other nine
watching normally, exit `0`.

Getting the **localised** case wrong is worse than it sounds. Made fatal, it is
an unattended caller's loop stuck on a non-zero exit with nothing on stdout and
an explanation only a human reading stderr will ever find — indistinguishable,
from the caller's side, from `botwatch` itself being broken.

## Scope

Implements the [Configuration](0001.md#configuration) section of
[0001](0001.md), plus the `botwatch`-side half of the
[exit-code boundary](0001.md#exit-codes).

**Out of scope:** validating driver-specific fields (that is the driver's, per
[0005](0005.md)); the state file's schema, including the copy of the config it
embeds ([0003](0003.md)); how the parsed timing is *used* ([0006](0006.md)).

**Sequencing note.** The repository currently contains no code at all, so
whichever issue lands first also stands the project up — the package layout, the
dependency manifest and lockfile, the test runner, the formatters, and the CI
jobs that run them. This issue is the natural first, having no dependencies of
its own. That work is scaffolding rather than a component of the design, so it
carries no acceptance criteria here beyond "the checks that will guard every
later issue exist and run".

**One exception to "no dependencies of its own":** this issue's handling of
channel-level *timing* keys is provisional until the **per-channel timing
overrides** question is answered (see *Open questions from 0001* below). The
answer is [0006](0006.md)'s to make, but making it needs no runner — so it must
be pulled ahead of 0006's implementation position rather than waiting for it, or
this issue ships a field-handling rule before the decision that determines what
it should be. Everything else here stands on its own.

## The rules this implements

From [0001](0001.md), stated normatively there:

- **YAML, and JSON for free.** JSON is valid YAML, so a caller that would rather
  emit JSON simply does and nothing changes. ([Format](0001.md#format))
- **No config schema versioning.** `version: 1` is written but unenforced —
  nothing reads it and a mismatch is undefined. It is carried so that the first
  real version bump does not have to guess what an absent field meant.
  ([Versioning and stability](0001.md#versioning-and-stability))
- **`defaults` sets the run's timing**; channels may override where a driver can
  meaningfully honour it. ([Shape](0001.md#shape))
- **A channel is `key`, `type`, `meta`, and the driver's own schema.** The
  loader validates the first three and passes the rest through untouched.
  ([Shape](0001.md#shape))
- **Keys are unique, caller-chosen, identifier-shaped, and filesystem-safe** —
  proposed `[A-Za-z0-9._-]{1,64}`, no leading `.`. A duplicate is a hard error,
  not last-one-wins. `botwatch` never invents a key.
  ([Stable keys](0001.md#stable-keys))
- **`meta` is opaque and preserved verbatim.**
  ([Caller payload](0001.md#caller-payload))
- **Structurally invalid config is fatal; a driver rejecting its own channel is
  not.** The line is whether `botwatch` can construct a coherent run without
  asking a driver anything. ([Exit codes](0001.md#exit-codes))

The filesystem-safe charset deserves its own note, because nothing in the design
as it stands *needs* it — state is a single file, so any string would do. The
argument is one-directional: loosening a constraint later is harmless,
tightening one later breaks every config already written. If a future state
*directory* arrives (for drivers that must persist more than a cursor), the
obvious layout is one subdirectory per key, which is only safe if keys were
fs-safe from the first day.

## Acceptance

*Each criterion names the implementation it falsifies. A criterion that the
design's rejected alternative also passes is not coverage — it is a criterion
that will still be green when the rule is broken.*

- **A duplicate key is fatal, before any driver exists.** A config with two
  channels sharing `key: dev-slack` exits non-zero, writes nothing to stdout,
  and instantiates **no** driver — including the drivers for the other,
  well-formed channels.
  *Falsifies:* last-one-wins, which exits `0` and quietly watches one of the
  two; and "validate after construction", which would have run nine drivers
  before noticing.

- **A structural fault is fatal; a driver's rejection of its own channel is
  not — in the same test.** An unparseable document, and a channel missing
  `key` or missing `type`, each exit non-zero with an empty stdout. A channel
  whose *driver-specific* fields the driver rejects exits `0`, produces a
  failure record for that channel, and leaves the other channels reporting
  normally with their recorded positions untouched.
  *Falsifies:* both one-sided readings — "all validation is fatal" fails the
  second half, "all validation localises" fails the first. Either alone passes
  a test that exercises only one flavour of bad config.

- **The key charset is enforced at both edges.** `a/b`, `.hidden`, a 65-character
  key, an empty key, and a key containing a space are each rejected as
  structural faults; `dev-slack`, `a`, `x.y_z-2`, and a 64-character key are
  each accepted.
  *Falsifies:* a loader that accepts any string (fails the reject half) **and**
  an over-tight rule such as `[a-z-]+` (fails the accept half). The accept half
  is the one usually missing.

- **Unknown channel fields pass through; missing `botwatch` fields do not.** A
  channel carrying fields the loader has never heard of loads without complaint
  and those fields reach the driver structurally unchanged, including nested
  maps and lists. The same run rejects a channel with no `type`.
  *Falsifies:* a closed whole-channel schema, which would reject the unknown
  fields and force the loader to learn every driver's schema; and a loader that
  passes everything through, which would accept the typeless channel.

- **`meta` survives intact.** A `meta` containing a nested mapping, a list, and
  a key literally named `channel` reaches the driver's channel config with its
  structure and its keys unchanged.
  *Falsifies:* a loader that flattens `meta`, drops keys it does not recognise,
  or reserves envelope field names inside it.

- **`version` is present and unenforced.** `version: 1`, `version: 99`, and a
  config with no `version` key at all produce the same in-memory config and the
  same run.
  *Falsifies:* a loader that validates the value (the field is documented as
  unread) and one that requires the key (configs without it must work).

- **JSON input is not a separate path.** The same document written as JSON loads
  to an in-memory config equal to its YAML form's, field for field.
  *Falsifies:* a YAML-only reader, and a "detect the format and branch"
  implementation whose two paths can drift.

- **The channel order in the file is not identity.** Inserting a new channel at
  the top of the list, and reordering the list, leave every existing channel
  matched to its own previous state (verified via [0003](0003.md)).
  *Falsifies:* positional matching, which passes every test that never reorders.

## Decisions this issue owes

The RFC does not settle these, and the loader cannot ship without an answer:

1.  **Duration syntax.** `20m` and `2s` appear in the sketch; nothing says what
    the grammar is, whether `1h30m` is legal, or what a bare number means.
    Proposed: a small explicit grammar, and a bare number is a structural error
    rather than "seconds, probably". **Settle it with [0007](0007.md)**, which
    *renders* durations (`136h12m`, `24h0m`) and owes the matching decision: the
    two have to agree for a caller to read and write the same language, and
    settling them apart means one re-deriving a grammar the other already chose.
2.  **Unknown *top-level* keys.** Unknown keys under a *channel* belong to the
    driver, but there is no driver to own an unknown key beside `defaults` and
    `channels`. Proposed: reject, since `botwatch` owns that level entirely and
    a typo there is silent otherwise.
3.  **An absent `defaults`.** Whether it is required, or whether built-in
    defaults apply.

## Open questions from [0001](0001.md)

- **Per-channel timing overrides** ([question 3](0001.md#open-questions)) — the
  *decision* belongs to [0006](0006.md), which owns the timing model and the run
  context. This issue implements the answer; it does not choose it. But the
  question cannot be implemented as the RFC leaves it, for a reason that is
  this issue's own:

  **A channel-level timing key belongs to nobody.** Two rules in
  [0001's `Shape`](0001.md#shape) collide on it, in consecutive sentences of one
  paragraph — "individual channels may override where a driver can meaningfully
  honour it", immediately followed by "everything under a channel beyond `key`,
  `type`, and `meta` is the driver's own schema, validated by the driver".
  A channel carrying `boarding_window` or `quiet_timeout` is a
  runner setting by the first rule and driver schema by the second. Under the
  second it reaches the driver and the runner never sees it, so the override
  cannot function at all — and the runner is the only party that honours a
  boarding window, since both clocks are properties of the *run*.

  The fix is a fourth category, and it is a change to `0001`: a channel's fields
  are `key`, `type`, `meta`, **the run-level timing keys**, and the driver's own
  schema. The alternative is to close this question by deciding that per-channel
  overrides do not exist, which removes the category by removing the case.
  Either way it is an amendment to the merged RFC rather than something this
  issue can settle, so it is recorded here and reported rather than fixed.

  **What each answer means for the loader**, once the category exists:

  - **"Reject at validation"** is a **structural** fault by this issue's own
    boundary rule — whether `botwatch` can construct a coherent run without
    asking a driver anything — so it exits non-zero with no driver instantiated.
    The loader is the only party that can know a key is a timing key; a driver
    has never heard of `boarding_window`, and the unknown-fields criterion above
    requires it to load without complaint and reach the driver structurally
    unchanged. There is no reading on which a conforming driver rejects it.
  - **"Ignore it"** and **"the window is global"** each need the fourth category
    to mean anything. Without it, "the loader accepts it and passes it on" means
    passing it to the *driver*, which delivers a timing value into driver config
    as though it were the driver's own schema — the outcome
    [0006](0006.md) rules out by name.

  **Ordering.** 0006 lands fifth and this issue lands first, so the decision has
  to be pulled forward; see the sequencing note under *Scope*. Until it is, this
  issue's channel-level field handling is provisional.
