# 0012 — Add the Pub/Sub driver, making `botwatch` push-capable

**Status:** Open
· **Kind:** Feature
· **Parent:** <a href="0001.md" title="0001 — botwatch: a one-shot `select` over many event sources">0001</a>
· **Builds on:**
  <a href="0005.md" title="0005 — Define the channel driver contract and ship a conformance kit every driver must pass">0005</a>,
  <a href="0006.md" title="0006 — Wait on every channel at once: the select, the two clocks, and the departure guards">0006</a>

> Every source `botwatch` can watch so far is fundamentally a *pull* with good
> manners: something asks the source what is new, politely and not too often.
> A message queue subscription is a genuine *push* — the event arrives because
> it was sent, in milliseconds, through the same wait as everything else.
>
> That changes what the tool can be used for rather than merely how fast it is.
> The example that motivates it: a button in a chat message. The button hits an
> HTTP endpoint, the endpoint publishes to a topic, and a `botwatch` that was
> already waiting returns instantly with the event. An agent becomes something a
> person can *press*, rather than something they wait for.
>
> It also puts pressure on two of the design's assumptions in a way no other
> source does — the recorded position for this channel does not live in the
> state file at all, and a boarding window has nothing to collect for a source
> that pushes.

## Background

A subscription as a botwatch channel, alongside the pull-based sources, in the
same config and the same wait *(sketch)*:

```yaml
channels:
  - key: dev-slack
    type: slack
    conversation: C0123456789

  - key: build-events
    type: pubsub
    subscription: projects/example/subscriptions/builds
    meta:
      notify: "#builds"
```

```text
person presses a button in a chat message
        │
        ├─► HTTP endpoint publishes to a topic
        │
        └─► the waiting botwatch run's `build-events` arm fires
            → event on stdout in milliseconds
            → the boarding window opens, the run departs, the agent acts
```

Nothing new is needed from the model to make that work. An acknowledgement id is
a cursor like any other, and nothing stops a driver's event stream being fed by a
long-lived streaming pull, since the consumer's close is what ends it.

### Where the analogy stops, and why it matters here

"An acknowledgement id is a cursor like any other" is true about its *shape* and
not about *where it lives*. Every other driver's position is a value written
into the state file, so leaving it untouched after a failure is a matter of not
writing it. An acknowledgement is held by the broker, and acknowledging is an
**effect**, not a record:

| | pull-based driver | this driver |
| --- | --- | --- |
| where the position lives | the state file | the broker's ack state |
| "leave it untouched on failure" means | don't write the cursor | **don't ack** |
| who can undo it | the next run | nobody |
| what a crash before the write costs | a replay | nothing, if acks are honest |

So obligation 4 — *a driver that fails leaves its recorded position untouched* —
lands differently: there is no recorded position to leave, and the equivalent
discipline is to acknowledge a message only after it has been yielded, never on
receipt. Get that backwards and a crash mid-window loses messages permanently,
which is the one outcome at-least-once delivery is supposed to make impossible.

### The other pressure point

A boarding window exists so a burst collapses into one run instead of one run
per event, and it is measured from the first event because the first event
should not have to wait. For a push source that is still useful — a burst of
published messages is exactly the case it helps — but a channel that overrode
`boarding_window` to zero, saying "I have nothing to wait for", would read the
**run-wide** value out of the run context rather than its own. That is the open
question the timing model owes an answer to, and this driver is the concrete
case to decide it against.

## Scope

Implements the [Pub/Sub](0001.md#pubsub) channel type of [0001](0001.md) as a
driver conforming to [0005](0005.md), against Google Cloud Pub/Sub.

**Out of scope:** the timing model and the decision on per-channel overrides
([0006](0006.md)); the publishing side — the HTTP endpoint in the motivating
example is the caller's, not `botwatch`'s; webhook bridges generally, which
reach `botwatch` *through* this driver and need nothing of their own.

## The rules this implements

- **A subscription is a botwatch channel**, selected over alongside every other
  kind. ([Pub/Sub](0001.md#pubsub))
- **An acknowledgement id is the cursor.**
- **A long-lived streaming pull may feed the event stream**, because the
  consumer's close is what ends it — which is the same property every other
  driver relies on, applied to a connection that stays open.
- All five [driver obligations](0001.md#the-channel-driver-contract), verified
  through [0005](0005.md)'s conformance kit. Obligation 3 — *report state
  consistent with what was yielded* — is the load-bearing one here, in its
  acknowledge-after-yield form.
- **Cleanup runs under cancellation** and must be short, local, and tolerant of
  not finishing — which for an open streaming pull means the close cannot wait
  on a graceful server round-trip.

## Acceptance

*Each criterion names the implementation it falsifies. A criterion that the
design's rejected alternative also passes is not coverage.*

Plus: **the driver passes [0005](0005.md)'s conformance kit in full.**

- **A message published mid-wait arrives without a poll.** After a run has been
  waiting quietly for minutes, a message published to the subscription reaches
  stdout in well under a second, and the driver made no periodic request while
  idle.
  *Falsifies:* a `pull`-with-an-interval implementation, which satisfies "the
  message eventually arrives" and reintroduces exactly the polling latency this
  channel type exists to remove. The minutes of prior idleness is what makes the
  criterion bite — a poller tested immediately after startup looks instant.

- **Nothing is acknowledged before it is yielded.** A run killed mid-boarding-
  window leaves every message it had not yielded unacknowledged, and they are
  redelivered to the next run. A message that *was* yielded before the kill may
  also be redelivered — that is at-least-once and is fine — but no message is
  lost.
  *Falsifies:* acknowledging on receipt, which is the natural shape when a
  client library hands you a batch, and which silently loses everything in the
  batch when the process dies. It is invisible in any test that lets the run
  finish.

- **Closing the stream does not acknowledge, and does not hang.** Closing while
  the streaming pull is open runs the driver's cleanup, leaves messages that
  were received but never yielded unacknowledged (nacked or left to expire), and
  completes promptly even when the broker connection is unresponsive.
  *Falsifies:* acking on close "to tidy up", which drops the un-yielded
  messages; and a cleanup that waits for a graceful server round-trip, which
  runs under cancellation and can hang the whole run — the one remaining way a
  driver can do that.

- **An unavailable subscription localises.** A missing subscription, an expired
  credential, and a permission failure each produce a failure record, leave the
  broker's ack state untouched, and leave every other channel reporting.
  *Falsifies:* raising past the runtime; and — specific to this driver —
  "cleaning up" by acknowledging outstanding messages on the way out of an error
  path, which converts a localised failure into permanent message loss.

- **A subscription with nothing on it keeps its arm in the select.** A channel
  whose subscription receives no messages for the length of a quiet timeout has
  a stream that is still open at the end of the run.
  *Falsifies:* ending the stream when a streaming pull's connection is
  re-established or when a receive call returns empty — which removes the arm
  from the select and, for a push source, means the button press that arrives
  four seconds later is not seen at all.

## Decisions this issue owes

1.  **What, if anything, goes in the state file.** The position lives at the
    broker, so this driver's `driver:` block may legitimately be empty — which
    is worth confirming rather than discovering, because an empty block
    interacts with `prev_state is None` and therefore with the
    fifth-case/startup-position rule in [0005](0005.md). If the block is always
    empty, this driver is permanently in the "no position to resume from" case,
    and the contract should say that is legal rather than suspicious.
2.  **Whether `get_state()` needs to be `async`.** If anything about the ack
    watermark has to be read back over the network, the synchronous signature in
    the contract sketch does not fit — see [0005](0005.md)'s owed decisions.
3.  **Ack deadline management.** A message yielded early in a boarding window
    that the run then holds — because a departure guard sent it back to the
    quiet timeout — may outlive its ack deadline. Extending the deadline is
    background work inside a driver, which is allowed but wants stating.
4.  **Ordering.** Obligation 1 asks for source order *where the source has one*.
    Pub/Sub has one only with ordering keys enabled, so this driver should state
    plainly which it is rather than leaving a caller to infer it.
5.  **Emulator-based testing.** Every criterion above needs a broker; the Pub/Sub
    emulator is the obvious answer and should be wired into `scripts/ci` rather
    than left to a developer's own project.

## Open questions from [0001](0001.md)

- **Per-channel timing overrides** ([question 3](0001.md#open-questions)) — the
  decision belongs to [0006](0006.md), but **this issue is the evidence it
  should be decided against**. A genuine push source is the RFC's own example of
  a driver that "cannot honour a boarding window meaningfully", and this is the
  driver that makes the abstract case concrete: does a `pubsub` channel that
  sets `boarding_window: 0` get rejected at validation, silently ignored, or
  told that the window is run-wide and not its to set — and what does its driver
  see in the run context either way?
