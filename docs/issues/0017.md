# 0017 — Acknowledge delivery, and keep printed events until it is acknowledged

**Status:** Open
· **Kind:** RFC
· **Parent:** <a href="README.md" title="Issues">Issues</a>
· **Related:**
  <a href="0015.md" title="0015 — Watch many sources in one blocking run, each carrying its own state">0015</a>,
  <a href="0016.md" title="0016 — (reserved) Retire sources that have gone quiet, with a heads-up one run ahead">0016</a>,
  <a href="0012.md" title="0012 — Add the Pub/Sub driver, making `botwatch` push-capable">0012</a>

> botwatch can't tell whether its caller got what it printed. It saves its
> place only when a run ends normally, and treats that end as delivery. A run
> that is killed saves nothing, so the next run prints the same events again.
> A run that ends normally moves on even if its output never reached the
> caller.
>
> Repeats cost an AI agent a wake for news it has already seen. Printing them
> again also only works because Slack and GitHub can be read again. A source
> that consumes from a queue can't re-read what it consumed, so it can't be
> built at all.
>
> The proposal is to keep every printed event in the state file until the caller
> acknowledges it, and to save as the run goes rather than only at its end. The
> caller acknowledges by naming the last event it handled when it starts its next
> run. This is a discussion document: the design is a recommendation, and the
> open questions at the end are genuinely open.

## Background

### How a run delivers today

botwatch is one-shot: a run waits on every configured source, prints what
happened, saves its place and exits, and the caller runs it again. A source is
an async generator of updates. Each update carries zero or more events and the
source's full state after them. The run handles each update whole: it prints
the events, then keeps the state, so the state it saves accounts for exactly
the events it printed.

```text
# one run, today (sketch)
load the config and the state file
start every source from its saved state
until `linger` after the first event, or `quiet_timeout`:
    for each update a source yields:
        print its events to stdout, one JSON line each, flushed
        keep its state in memory
save the state file atomically          # reached only by a normal end
exit 0
```

That save is the only point where a run commits to anything. A run that ends
any other way, whether by SIGINT, SIGTERM, a crash or a power loss, leaves the
state file as it was. The next run then starts each source from its previous
place:

```text
run 1   prints E1, E2 … is sent SIGTERM          state file unchanged
run 2   starts from before E1: prints E1, E2 again, then E3
```

This is at-least-once delivery. `docs/design.md` holds the code to it with a
spec, *where a run ends never changes what is emitted*, which holds once readers
drop repeats by `(source, id)`.

### Who reads the output

A run's stdout is rarely read through a pipe as it's written. Two consumers in
real use:

- **An AI-agent harness**, such as Claude Code running botwatch as a background
  command, drains the command's stdout into a file as it's written. It tells
  the model only when the command exits.
- **A wrapper script** sends botwatch's stdout to a plain file, and truncates
  the output it has accumulated at the start of each wait. On SIGTERM it exits
  without printing what it had collected.

```text
botwatch ──stdout──► a file ──when the command exits──► the agent
```

Every write succeeds at once, whether or not anyone will ever look at it. That
the bytes left botwatch says nothing about delivery. Neither does a normal end:

```text
run 1    prints E1, ends normally, saves its place after E1
wrapper  is sent SIGTERM before printing its file      E1 never reaches the agent
run 2    starts after E1                               E1 is gone
```

A caller's natural acknowledgement is starting its next wait after reading the
last output. botwatch can't see that either. A restart after a kill, or a
watchdog starting a wait, looks exactly the same from botwatch's side.

### Where this falls short

- **Destructive reads.** A killed run's events can be printed again only
  because Slack and GitHub can be asked again. A source that consumes from a
  queue, such as a Pub/Sub subscription, can't re-read what it consumed. As
  0012 put it, acknowledging a broker is an irreversible effect, not a record.
- **Repeats wake the agent.** A killed run's events are repeated whether or not
  the caller saw them. A repeat counts as news, so it ends the next run's wait
  early. For an agent, each wake is a full turn over its context, and a wake
  made only of repeats is pure cost.
- **A normal end isn't delivery.** A caller that loses the output after
  botwatch exits has lost those events for good, as above.
- **A stalled reader stalls the sources.** Each line is written and flushed
  synchronously on the event loop. If stdout is a pipe that nobody drains, a
  write blocks once the pipe's buffer fills (typically 64 KiB), and every
  source stops polling with it. Neither consumer above does this, but nothing
  rules it out.

## Goals and non-goals

**Goals**
- **Nothing printed is lost**, however a run ends and whatever the caller does
  with its output. An event the caller hasn't acknowledged is printed again from
  the state file, without asking its source.
- **Sources with destructive reads become possible.** The buffering is done
  once, at the output layer, rather than in each source, and a source can go
  further where it needs to.
- **The caller can say exactly what it has handled.** Until it does, nothing is
  taken as delivered, except by callers that choose to keep today's behaviour.
- **Few redundant wakes.** No wake is made only of events the caller has
  acknowledged, and an unacknowledged event's replay wakes the caller at most
  once. Repeats that ride along with a genuine wake are acceptable.
- **A reader that never drains stdout never stalls the sources.**

**Non-goals**
- **A daemon.** All memory between runs stays in the state file the caller
  holds. That includes the buffer, which is saved in the same atomic write as
  the source states. An always-on helper sits outside botwatch.
- **Exactly-once delivery.** Delivery stays at-least-once. A replayed event
  keeps its original `id`, and callers keep deduping on `(source, id)`.
- **Acknowledging events out of order.** An acknowledgement always covers a
  prefix of what was printed.
- **Treating a write to stdout as delivery** for the consumers above (see
  [When acknowledgement happens](#when-acknowledgement-happens)).

## Design

### The buffer

The state file gains a **buffer**: every event printed and not yet
acknowledged, in the order printed. Each event carries its source key and a
sequence number, `seq`, which is unique within the state file and increases in
print order.

```yaml
# state file (sketch)
sources:
  slack:C0123456789:
    type: slack
    after: '1785600123.000100'
buffer:                     # printed, not yet acknowledged, in print order
  - seq: 41
    source: slack:C0123456789
    event: {type: slack.message_posted, id: '1785600123.000100', …}
next_seq: 42
```

The buffer and the source states are one document, saved in one atomic write
(a temporary file, then a rename) as today. The `Update` invariant becomes:
**a source's saved state accounts for exactly the events printed, each either
acknowledged or still in the buffer.** The two stay in step because nothing
moves one without the other:
- An update's events join the buffer in the same save that records its state.
- An acknowledgement only removes events from the buffer. It never touches a
  source's state.
- A replay prints what's in the buffer. It never asks a source.

**Where the buffer lives.** It belongs to the run, at the output layer, so that
no source has to reinvent it and every source gets it. The alternatives were
each source keeping its unacknowledged events in its own state, or a stage
doing it. A stage could keep memory in the update's state, as 0015's planned
settle stage does. But neither a source nor a stage sees the caller's
acknowledgement or the run's saves. Neither could replay every source's events
in one order either. A source can still go further than the buffer: see
[Saving as the run goes](#saving-as-the-run-goes) and the
[Pub/Sub example](#a-pubsub-source).

### Saving as the run goes

This is the central choice. A destructive source may acknowledge its upstream
only once its events are durably in the buffer, and the buffer is durable only
once it has been saved. Today a run saves only at its end. So either the run
saves during the run, or upstream acknowledgements wait for the end.

**Recommended: save each update before asking its source for the next.** The
run handles an update by adding its events to the buffer and saving the state
file. Only then does it print the events and go back to the select.

- **A source learns that its update is safe, with no new API.** turbopipes'
  `aselect` re-arms a source's pull only once its consumer comes back for
  another item. So a source resumed after a `yield` knows the run has finished
  handling that update. Once handling includes the save, the update is also
  saved. A queue-reading source acknowledges its upstream at exactly that
  point. That is well within any deadline, however long the run lingers.
- **Every source benefits.** A killed run loses at most the update it was
  saving. The next run replays the rest from the buffer rather than reading it
  again, so Slack and GitHub sources behave just as a queue-reading one does.
- **Signals need no special handling for correctness**, since everything
  printed has already been saved. Closing the sources on SIGINT and SIGTERM is
  still worth doing, so that a queue-reading source can hand back what it
  received but never yielded.
- **Cost:** one atomic write per update rather than one per run. Updates are
  rare by design: after its starting checkpoint, a source yields only when it
  has events.
- **A lock.** A run holds an exclusive lock on the state file for its whole
  length, so two runs never interleave their saves. A second run waits for the
  first to exit.

**Alternative: save at the end, and acknowledge upstream after that.** This
keeps one write per run. A crash leaves the queue unacknowledged, so the broker
redelivers. But:

- Every message received is held unacknowledged until the run ends. For an
  event that wakes the caller, that's at most the linger. For one that doesn't
  (see [Low-priority events](#low-priority-events)), it can be the whole quiet
  timeout. That is longer than a Pub/Sub acknowledgement deadline, which is ten
  minutes at most, unless the source keeps extending its leases. This is 0012's
  open question 3.
- The acknowledgements come after the sources have closed, so the run needs a
  phase after the save that calls back into each source.
- Killed runs still repeat their events by reading them again, so for kills
  only sources that can be re-read are covered.

### Acknowledgement

A config chooses what acknowledges a run's output:

```yaml
# config (sketch)
ack: explicit     # or exit, the default
```

- **`exit`**, the default and today's behaviour: a run that ends normally
  acknowledges everything it printed, in its final save. The buffer then only
  ever holds events from killed runs.
- **`explicit`:** only the caller acknowledges. It does so when it starts its
  next run, by naming the last event it handled:

  ```console
  $ botwatch run --config watch.yaml --state state.yaml --ack 41
  ```

  `--ack SEQ` drops every buffered event up to and including `SEQ`, before
  anything is printed. `--ack 0` acknowledges nothing. A `SEQ` that the state
  file never issued is an error (exit 2), since only a confused caller could
  have it.

The caller takes `SEQ` from the last line of the output it handled. Every run
prints the whole buffer before anything new (see
[Replay and departure](#replay-and-departure)). So every event still buffered
up to the last one the caller read was in what it read, and acknowledging that
prefix is exact. A caller that stopped reading part way acknowledges just what
it read. A stale `SEQ` acknowledges less, never more.

```bash
# a loop with explicit acknowledgement (sketch)
ack=0
while true; do
  events="$(botwatch --config watch.yaml --state state.yaml --ack "${ack}")" || break
  [ -n "${events}" ] || continue
  my-agent --handle "${events}" || continue    # not acknowledged: printed again
  ack="$(tail -n 1 <<<"${events}" | jq .seq)"
done
```

An agent under a harness does the same. It reads the output, acts on it, and
starts its next wait with `--ack` set to the last `seq` it read.

### When acknowledgement happens

| When | Unambiguous? | Writers of the state file | Verdict |
| --- | --- | --- | --- |
| At a normal end (`exit`, today) | No. The output can still be lost after the run ends, as in the wrapper case. | One | Kept as the default, for callers that keep today's behaviour |
| When the next run starts, implicitly | No. A restart after a kill, or a watchdog starting a wait, looks the same. | One | Rejected |
| `botwatch ack SEQ`, a command of its own | Yes | Two. It races a live run, so it needs the run's lock. | A possible later addition, for acknowledging without starting a wait, e.g. on shutdown |
| `run --ack SEQ`, named on the next run | Yes | One | **Recommended** |
| As each line is written to stdout | No. A write proves only that the pipe or file took it. | One | Rejected for these consumers. A streaming reader is better served by owning the state. |

The flag costs a looping caller nothing it doesn't already run. It also keeps
the run as the state file's only writer: `add`, `defaults` and `remove` never
touch the state file.

Counting each line as acknowledged once written would make delivery
at-most-once at the pipe. A reader that dies with lines still in the pipe's
buffer would lose them. A reader that can durably record what it reads is
better off holding the state itself, as in the child-process protocol below.
Then there's nothing left to acknowledge.

### Replay and departure

A run prints the buffer first, before any new event. It keeps the buffer's
order, and each event keeps its original `seq` and `id`. New events follow with
new `seq`s. So a source's events always come out in source order, and the
`seq`s in a run's output always increase.

A replay counts as events, because the caller may never have seen what's
replayed. A run that starts with a non-empty buffer therefore departs `linger`
after it starts, rather than at the quiet timeout.

To keep a caller that never acknowledges from spinning, a replay wakes the
caller only once for each event. Once a run that replayed an event has ended
normally, the event rides along with later wakes until it is acknowledged,
rather than starting one. Under `exit`, a replaying run's normal end
acknowledges the event anyway, so this only matters under `explicit`.

```yaml
# a buffered event, after one replay (sketch)
- seq: 41
  source: slack:C0123456789
  replayed: true      # a run that replayed it has ended normally: no more waking
  event: {…}
```

A replay never makes an event more urgent than it was. An event that didn't
wake the caller when first printed doesn't wake it when replayed either.

### What isn't buffered

`botwatch.source_failed` isn't buffered or replayed. It gets a fresh `id` each
time, so a replay would read as a new failure. It describes the run it happened
in, and the next run retries the source and reports again if it's still
broken. It still carries a `seq`, so a caller can acknowledge through it.

### Removed and expired sources

A save drops the state of sources that are no longer configured. Their buffered
events stay until acknowledged, and are replayed like any others. Removing a
source means "stop watching", not "forget what it already reported". For a
queue-reading source, dropping its buffered events would lose them for good.
The same holds for sources that expire, once 0016 lands. A source removed and
added again under the same key starts afresh as today, and its old buffered
events dedupe by `(source, id)` as usual.

### Never stalling on stdout

Each update is saved before it's printed, so printing no longer has to keep pace
with the select. The run hands each line to a writer that drains to stdout off
the event loop, and goes back to the select as soon as the update is saved. A
reader that stops draining a pipe then holds up only the run's exit, never its
sources. A normal end waits for the writer to finish before its final save. If
the run is killed while it waits, whatever it hadn't printed is still in the
buffer and is replayed.

### Low-priority events

These are related and could be folded in: events that are printed without
starting the linger, chosen per source or per event type, such as reactions
outside working hours. The buffer gives them the same durability as any other
event, and the departure rule already has the hook, since a run departs only on
events that wake the caller. What's left is policy and shape:
- The update has to say which of its events wake the caller. That could be set
  by a stage, like `exclude`, over event types and times.
- The output should mark them, so that a wrapper can treat a run with only
  low-priority events as quiet. Under `explicit`, the wrapper just doesn't
  acknowledge them, and they ride along with the next wake.

### The output and state contracts

The output is validated against a closed union of records (`Record` in
`_run.py`). This RFC changes the contracts:
- **Output.** Every record gains a `seq`:

  ```json
  {"seq": 41, "source": "slack:C0123456789", "event": {"type": "slack.message_posted", "id": "1785600123.000100", …}}
  ```

- **State.** The state file gains `buffer` and `next_seq`. An older botwatch
  can't read a state file written by the new one, since `StateFile` forbids
  unknown keys. The new one reads an older state file fine.
- **Config and command line.** The config gains `ack`, and `run` gains `--ack`.

A reader that ignores unknown JSON fields needs no change. A reader that
validates records strictly needs one, and so does a tool that reads the state
file. The release's upgrade notes cover both, along with the caveat about
downgrading.

### What changes in docs/design.md

- **The three properties.** *Nothing lost* becomes: however a run ends, and
  whatever its reader does with the output, no event is skipped, and an event
  the caller hasn't acknowledged is printed again.
- **Sources, updates and events.** The state bullet's invariant becomes
  "accounts for exactly the events written, each either acknowledged or still
  buffered". The lifetime bullet adds that a source resumed after yielding an
  update can count on that update having been saved.
- **The run**, rewritten:

  ```text
  1. Load.    Load and validate the config and the state file, and lock the
              state file. Apply --ack: drop the buffered events up to its seq.
  2. Start.   Create every source from its stored state.
  3. Replay.  Print the buffer, in order. If it holds an event that may still
              wake the caller, the linger starts now.
  4. Select.  For each update: add its events to the buffer and save the state
              file, then hand the events to the writer and go back to the select.
  5. Depart.  As today: `linger` after the first event that wakes the caller,
              or the quiet timeout.
  6. Save.    Once the writer has finished, save each source's latest state.
              Under `ack: exit`, a normal end acknowledges what it printed.
              Under `explicit`, it marks the events it replayed as replayed.
  ```

- **Failures** aren't buffered, and each carries a `seq`.
- **Delivery** is at-least-once, with acknowledgement. Under `exit`, a normal
  end acknowledges; under `explicit`, the next run's `--ack` does. Every run
  prints the unacknowledged events again, first, until they are acknowledged.
- **Editing the watch set.** The next run drops a removed source's state, but
  not its buffered events.
- **The spec**, as below.

### The spec

*Where a run ends never changes what is emitted* extends to cover how much of
each run's output the caller reads:

> For every source whose state has been saved, or that has a `start_after`,
> and given the same activity at that source, the events successive runs emit
> for it form the same sequence however each run ends, a crash included, and
> however much of each run's output the caller acknowledges, once repeats are
> dropped by `(source, id)` and `botwatch.*` events are ignored. Every later run
> emits an event again until it is acknowledged, and those repeats come first,
> in their original order. Only unacknowledged events are repeated, and no event
> is ever skipped.

The caveat for GitHub stays as it is. The paragraph about new sources changes
in one place: a new source's state is first saved as soon as the source
delivers its first update, rather than by a run that ends normally after that.
Replay order can be fixed because botwatch adds no nondeterminism of its own
beyond the linger and expiry.

The test, `test_run_once__where_a_run_ends_never_changes_what_is_emitted`,
keeps the state from a killed run's last save rather than discarding it. It
also gains a parameter for how much of each run's output the simulated caller
acknowledges: none, all, or a prefix.

## Examples

These examples show how the design fits two kinds of source. Neither is a
commitment to build.

### A child process

This is a source that runs a command. The command prints update lines on
stdout: each line is a JSON object holding zero or more events and the child's
full state after them, the same shape as an `Update`.

```text
# the child-process protocol (sketch)
parent: starts the child, writing its stored state (or null) to the child's stdin
child:  {"events": [], "state": {…}}                         # first, a checkpoint
child:  {"events": [{"type": "…", "id": "…", "time": "…", …}], "state": {…}}
…
parent: sends SIGTERM when the run departs
child:  exits 0, promptly
```

- **The child holds no state.** The parent keeps the child's state in its own
  state file and hands it back at start. Each line is an update, so the run
  saves it and its events in the buffer as it goes, as for any other source.
- **Lifecycle.** The child runs until it's signalled, and exits 0 promptly on
  SIGINT or SIGTERM. Any other exit, or a line that isn't a valid update, is a
  `botwatch.source_failed`. There are no special exit codes.
- **Events.** The output union is closed, so the child's events would travel
  inside one generic event model, carrying the child's own type and data,
  rather than extending the union.
- **The gap between runs is the child's problem.** While no run is live, the
  child isn't running, so it observes nothing. It must read from something that
  keeps a backlog, such as an API with history, a queue, or a file it tracks by
  an offset in its state, and resume from the state it's handed. A child that
  watches a live-only feed misses whatever happens between runs. That's why
  0015 rejects Slack's Socket Mode.
- **Destructive reads in the child.** A line written to the parent's pipe
  proves nothing. So a child that consumes from a queue can't tell from its
  writes whether the parent has saved an update. It would need a return path,
  such as the parent writing to the child's stdin after each save (see
  [Open questions](#open-questions)).

**A nested botwatch** is one such child, for example to watch as a second
identity, which a single run doesn't (0015). It needs a mode that never departs
by itself, and that takes its state on stdin. It prints update lines carrying
its whole state, rather than events plus a state file of its own, and exits 0
on SIGTERM. It needs no buffer of its own, since the parent's covers it.

### A Pub/Sub source

This is a source over a Pub/Sub subscription. It reads through a streaming
pull, so a published message wakes the run without a poll.

- **Events.** Each message is an event. Its `id` is the message's ID, which
  Pub/Sub keeps across redeliveries, and its `time` is the publish time. The
  source's state can be empty, since the position lives at the broker.
- **Custody passes to the buffer.** The source yields the message's update, and
  the run saves it into the buffer. When the source is next resumed, it
  acknowledges the message to the broker. A run killed before the save leaves
  the message unacknowledged, so the broker redelivers it. A run killed between
  the save and the broker acknowledgement has the message in both places. The
  run replays it and the broker redelivers it under the same ID, which callers
  already drop as a repeat.
- **Never acknowledge early.** As in 0012: not on receipt, not on close, and
  not on failure. When the source is closed or fails, any messages it received
  but never yielded are nacked, or left unacknowledged to expire.
- **Tying the broker to the caller.** A source could go further and acknowledge
  the broker only once the caller has acknowledged the event, which means
  something now that the caller's acknowledgement is unambiguous. But that
  acknowledgement arrives with the next run, possibly an hour later. By then
  the broker's deadline has long passed, and no live process was there to
  extend it. So the buffer takes custody, and the caller's acknowledgement
  clears the buffer, not the broker.

## Open questions

1. **The default.** `explicit` is the only unambiguous mode. Should it become
   the default before 1.0? If so, a caller that doesn't pass `--ack` would get
   each event a second time, in one extra wake. Or should `exit` stay the
   default, with the README's loop switched to `explicit`?
2. **What the caller echoes back.** This RFC proposes a `seq` on every record,
   acknowledged as a prefix. The alternative raised in review is a run ID on
   every record, which acknowledges everything that run printed. A run ID has
   the same value on every line. But botwatch would then keep a table of what
   each run printed, and a caller that read only part of a run couldn't
   acknowledge that part. Either way, should a replayed record say that it's a
   replay, so that an agent with no dedupe store can tell it may already have
   seen it?
3. **The one waking replay.** Is once the right bound? It costs one redundant
   wake when a caller handled an event but restarted without `--ack`. It also
   delays an event the caller lost twice running, until the next genuine wake
   or the quiet timeout.
4. **Bounding the buffer.** Under `explicit`, a caller that never acknowledges
   grows the buffer without limit. Is it enough for `botwatch show` to report
   the buffer's size and its oldest event? Or does the buffer want a cap, and if
   so, what happens when it's reached?
5. **Low-priority events.** Should they be folded into this work, or follow
   it? Who decides what's low priority: the config, per source and event type,
   or a stage that looks at times as well?
6. **A return path for child processes.** Should the child-process protocol
   tell the child when an update has been saved, so that a child can read
   destructively? Or should such children stay out of scope?
