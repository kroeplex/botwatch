# 0001 — botwatch: a one-shot `select` over many event sources

**Status:** Open
· **Kind:** RFC
· **Parent:** <a href="README.md" title="Issues">Issues</a>

> An autonomous agent that reacts to the outside world has to remember *what it
> has already seen* — per source, across invocations. Doing that inside the
> agent is expensive and unreliable: it spends tokens on bookkeeping instead of
> work, and cursor arithmetic is exactly the sort of fiddly detail a language
> model gets subtly and silently wrong.
>
> The usual escape hatch is a polling loop, which is worse. It costs a full
> wake-up per source per tick whether or not anything happened, and it adds
> latency proportional to the tick interval to every event that does.
>
> `botwatch` is the missing primitive: **one process, run on demand, that waits
> on many sources at once and reports only what is new.** The caller runs it,
> reads the events off stdout, and acts. All memory between runs lives in a
> state file the caller holds — `botwatch` itself keeps nothing.

## Background

Consider an agent that watches a team chat workspace. It should notice new
messages in a handful of conversations, notice pushes to a couple of
repositories, and act on them — and it should do that without a human poking
it.

**What that looks like today**, written as the agent's own loop *(sketch)*:

```text
every 2 minutes:
    for each conversation I care about:
        fetch recent messages
        compare against the timestamp I wrote down last time
        decide which ones are new
        write down the new timestamp
    for each repository I care about:
        fetch refs
        compare against the SHA I wrote down last time
        ...
    if nothing was new:  go back to sleep
```

Three things are wrong with it, and they compound:

1.  **The bookkeeping is the agent's problem.** "The timestamp I wrote down
    last time" has to be stored, re-read, and reasoned about on every tick, in
    natural language, by a model. Every source has its own notion of a cursor —
    a message timestamp here, a commit SHA there, an acknowledgement ID
    somewhere else — and each is one plausible-looking mistake away from
    silently skipping events or replaying them forever.

2.  **Idle ticks cost the same as busy ones.** The loop above wakes fully,
    reasons about every source, and finds nothing, over and over. A quiet
    afternoon costs hundreds of wake-ups and produces nothing.

3.  **Latency is bounded below by the tick interval.** Shorten the interval to
    react faster and the idle cost rises in exact proportion. There is no
    setting that is both cheap and responsive.

**The workaround people reach for is a daemon** — a long-running process that
holds subscriptions open and pokes the agent when something happens. That fixes
the latency and the idle cost, and introduces a new class of problem: something
has to supervise it, its in-memory state diverges from anything on disk when it
crashes, and the agent now depends on a second system being healthy.

**`botwatch` is the third option.** It is a plain command. It is given a config
and a state file, it blocks until something happens or a timeout elapses, it
prints what is new, it advances the state file, and it exits. The same loop
becomes:

```text
forever:
    events = run botwatch --config watch.yaml --state state.yaml
    if events:  act on them
```

The agent no longer knows what a cursor is. There is no daemon. And because
`botwatch` blocks rather than polls-and-returns, an idle stretch costs one
process that sits quietly, while an event is reported the moment it appears.

## Concepts and terminology

### Channel

> [!IMPORTANT]
> **A *channel* here is not a chat channel.** It is a channel in the
> concurrency sense — a stream of events that can be waited on and selected
> over, as in Go, CSP, or an actor mailbox.
>
> A chat channel is *one kind of* botwatch channel. So is a direct message, a
> single chat thread, a git repository, and a pub/sub subscription. When this
> document means the chat kind it says **"Slack channel"** explicitly, and so
> should everything else in this repository.

A channel is the unit of configuration, the unit of state, and the unit of
identity. Everything else in the design hangs off it.

### Driver

The code that knows how to watch one *kind* of source. A driver is instantiated
once per configured channel and is responsible for: turning that channel's
config plus its previous state into an
[event stream](#the-channel-driver-contract) of what is new, and reporting the
state that should be recorded for next time.

### Select

`botwatch` waits on every configured channel **simultaneously**, and returns
when any of them produces something — the same shape as Go's `select` over
several channels with a timeout arm:

```go
select {
case ev := <-slackConversation:  // one arm per configured channel
case ev := <-upstreamRepo:
case ev := <-buildEvents:
case <-time.After(quietTimeout): // the "nothing happened" arm
}
```

The whole tool is that statement, plus the bookkeeping needed to make it
resumable across process lifetimes.

### One-shot

`botwatch` runs, does one wait, and exits. It does not loop. Looping — deciding
*whether* to watch again, and what to do with what it found — belongs to the
caller, who is the only party that knows.

This is what keeps the tool small. There is no supervision, no restart policy,
no reconnection backoff spanning invocations, no health endpoint, and no
question of what happens when the config changes underneath a running process:
the config is read once, at startup, every time.

### Stateless

`botwatch` stashes nothing anywhere of its own choosing. Its entire memory
between runs is the state file whose path the caller supplies. Nothing lives in
`~/.cache`, no lock directory is invented, no database appears.

The consequence worth stating plainly: **from the outside, `botwatch` is a pure
function of (config, state, world) → (events, state′).** The caller can copy a
state file to test against, throw one away to re-read everything, keep one per
context, or generate one via process substitution. None of that requires
`botwatch`'s cooperation, because there is nothing else to keep in sync.

## The execution model

### The wait

The interesting behaviour is what `botwatch` does with *time*, and it is the
part most likely to be got wrong by a reimplementation.

Two intervals govern a run:

| Interval | Typical | Meaning |
| --- | --- | --- |
| **Quiet timeout** | ~20 min | How long to wait when *nothing at all* is happening. Elapses → exit cleanly, no events. |
| **Boarding window** | ~2 s | Once the *first* event arrives, how much longer to keep collecting before departing. |

The naive designs both lose:

- **Return on the first event.** A burst of ten messages costs ten
  invocations, each with its own process startup, config parse, and — for an
  agent caller — its own full wake-up. Bursts are the common case, because
  people type in bursts and CI pushes in bursts.
- **Always wait a fixed window.** Now a burst is one invocation, but the first
  event of an otherwise-idle day is delayed by the whole window, and the window
  has to be short to keep that tolerable, which brings back the first problem.

**`botwatch` does neither.** The quiet timeout and the boarding window are
different clocks serving different purposes:

```text
run starts
│
├─ nothing happening ──────────────────────────────►  quiet timeout (~20 min)
│                                                     elapses → exit, no events
│
├─ every stream has ended ─────────────────────────►  quiet timeout runs anyway
│                                                     elapses → exit
│
└─ first event detected at T
   │  → written to stdout immediately
   │
   ├─ boarding window opens: [T, T + ~2s]
   │     any further events are detected and written as they arrive
   │
   └─ window closes
      │
      ├─ every event came from a stream that has since errored
      │                       ─────────────────────────────────►  back to the
      │                                                           quiet timeout
      │
      └─ otherwise → close the streams → write state → exit
```

The analogy that names it: **the train waits at the station.** It does not
depart the instant the first passenger boards, and it does not sit for an hour
on the off-chance. The first passenger starts a short, bounded countdown, and
everyone already walking up the platform gets on.

**When every stream has ended, the run waits out the quiet timeout anyway.** A
driver that ends its stream has asserted that its channel will produce nothing
further this run, so a run with no streams left has nothing to wait *on* — and
the naive answer, which is also what a `select` over an empty set does
naturally, is to exit at once. That is wrong here. The caller's loop relaunches
as soon as `botwatch` returns, so an immediate exit turns a total outage into
the hot poller this design exists to replace: one process per failed attempt,
as fast as the machine can spawn them. Waiting out the timeout costs nothing
anybody is using, and it keeps the caller's pacing identical whether its
sources are quiet or broken. What tells the caller which of those it is looking
at is the [failure records on stdout](#failure-records), not the timing.

**A departure is abandoned if every event collected in the window came from a
stream that has since ended in an error.** When the window closes, the run
departs only if at least one of the events it collected came from a stream
that has not by then failed; otherwise it goes back to waiting out the quiet
timeout. Whatever was already written stays written — records are flushed as
they are produced, so a streaming caller has them either way.

The scope is every event collected, not the one that opened the window. A run
where a broken channel yields first and then errors, while a healthy channel
yields into the same window, **departs** — the healthy channel's event is what
the window is for, and holding it back would delay an event whose own stream
never failed and which no later run would replay.

This is the same rule as the two guards above, applied to the door between
them. A driver that fails *before* yielding is covered, because a
[failure record](#failure-records) does not open the window. A run whose
streams have all ended is covered, because it waits the timeout out. But a
driver that yields and *then* fails walks between the two: its events are
genuine, so they open the window, and its stream is only one of several, so the
run is not out of streams. Since `botwatch`
[discards the state of a stream that ended in an error](#the-channel-driver-contract),
those same events are yielded again on the next run — so without this guard, a
single paging source whose token expires before page two would make every run
depart seconds after starting, indefinitely, and drag every other channel's
wait down with it. That is precisely the hot poller
[Background](#background) opens by rejecting, and the sentence above — pacing
stays identical whether the sources are quiet or broken — is what decides the
case.

**What it costs is latency for one kind of caller**, and it is worth naming: a
caller that waits for process exit gets genuinely-new events late when a stream
fails after yielding them, which includes the ordinary transient blip and not
just the pathological case. That is the right side of the trade, because the
state for that channel was discarded regardless, so those events are
re-reported on the next run anyway — the loss is latency, not delivery — and it
is bounded by the quiet timeout, which is the pacing the caller chose. A caller
that reads stdout streamingly is unaffected.

**This is faster *and* cheaper, which is the counterintuitive part.** Against a
naive poller it wins on latency, because the wait is a genuine block rather
than a sleep between ticks — an event is noticed when it happens, not at the
next tick boundary. And it wins on overhead, because a burst collapses into one
invocation instead of one per event. Designs usually trade these against each
other; here the trade is made against a third axis — process count — that
nobody was spending anyway.

**Events are written as they are detected, not batched at exit, and stdout is
flushed after each record.** Within the boarding window, each event hits stdout
the moment its driver yields it. A caller that reads streamingly can begin work
on the first event while the window is still open, and a caller that waits for
exit is unaffected. It also means a crashed run leaves behind whatever it had
already reported, rather than nothing — see
[at-least-once](#delivery-semantics) below.

**The flush is part of the contract, not an implementation detail**, because
both of those sentences are claims about what an *external* observer sees, and
the default for a piped stdout in most runtimes is block buffering. A few
hundred bytes of JSONL would then sit in a multi-kilobyte buffer until the
buffer filled or the process exited — inside a two-second boarding window, the
exit — so a streaming caller would get everything at once at the end, and a
`SIGKILL` would take the unflushed buffer with it, leaving a crashed run
behind having reported nothing at all. The failure is also invisible in
interactive testing, since a terminal is line-buffered: it works perfectly by
hand and stops working under the pipe a caller actually reads. Hence: flushed
after every record, terminal or pipe.

**The boarding window is a fixed departure, not a sliding one.** It is measured
from the first event and does not extend when more arrive. A sliding window is
tempting — it would coalesce a long ragged burst into a single run — but it has
no upper bound in the presence of a chatty source, and an unbounded run defeats
the point of being one-shot.

**Sliding is deferred, not rejected outright**, and it is worth recording what
would bring it back so the next person to have the idea does not have to
re-derive it. The shape it would take is a *capped* slide: `boarding_window`
restarts on each event, and a second setting — `max_boarding` — bounds the
total, so the run still has a guaranteed departure time. An unbounded slide is
not on the table at any point.

What would reopen it is **evidence, not argument**: an observed burst pattern
that the fixed window demonstrably mishandles — a source whose events arrive in
trains ragged enough to split across several runs where one would have done.
Until such a pattern shows up in a real workload, the fixed window is the
decision rather than a placeholder for one.

### Exit codes

| Code | Meaning |
| --- | --- |
| `0` | Ran to completion. Events may or may not have been emitted; the quiet timeout elapsing is success, not failure. Individual channels may have failed, so long as each failure localised. |
| non-zero | The run could not be constructed or could not be completed: an unreadable or structurally invalid config, unwritable state, a driver that failed in a way it could not localise. |

"No events" is deliberately **not** distinguished from "some events" by exit
code. The caller already knows — it read stdout. Overloading the exit code
would tempt callers into branching on it and get the empty case wrong.

**A structurally invalid config is fatal; a channel a driver rejects is not.**
The line between them is whether `botwatch` can construct a coherent run
without asking a driver anything. Unparseable YAML, a
[duplicate key](#stable-keys), a channel missing `key` or `type` — `botwatch`
sees each of these for itself, before any driver exists, and each breaks the
run as a whole rather than a part of it. The duplicate key is the sharpest
case: it breaks *identity*, which every other guarantee is matched through, so
there is no coherent "the other nine still work" left to fall back on.

Once the structural config parses, every remaining error is per-channel by
construction, and **a driver rejecting its own channel's fields localises** —
a [failure record](#failure-records) on stdout, `last_error` in that channel's
metadata, the other channels undisturbed, exit `0`. Everything under a channel
beyond `key`, `type`, and `meta` is [the driver's own schema](#shape), so a
driver is the only party that can reject it, and what it rejects is one
channel. The rejected channel's recorded position is left untouched like any
other localised failure, so correcting the config resumes rather than skips.

That case is worth settling explicitly because it is not rare: the expected
author of these configs is [a language model](#format), which makes one
malformed channel out of ten a routine event rather than an exotic one. Made
fatal, it is a caller's loop wedged on a non-zero exit, with nothing on stdout
and an explanation only a human reading stderr will find — for an unattended
watcher, indistinguishable from the tool itself being broken. Localised, it is
one more record on the stream the caller is already reading, naming the channel
and the validation error, while the other nine keep working.

### Delivery semantics

**`botwatch` is at-least-once, and callers must tolerate duplicates.**

State is advanced and written **at exit**, after events have been emitted. If
the process is killed mid-run, or the machine dies, the state file still
reflects the *previous* run, so the next run re-reports whatever was in flight.
The alternative — advancing state before or as events are emitted — would make
a crash silently swallow events, which is far worse: a duplicate is visible and
annoying, a dropped event is invisible and wrong.

**That guarantee holds only if the write is atomic, so the write is
specified.** The state file is written by creating a temporary file in the same
directory and renaming it over the target, so an observer sees either the
previous run's file or this one's and never a partial one. The obvious
implementation — open the path, serialise, close — does not have that property:
killed mid-write it leaves truncated YAML, which is neither run. The blast
radius is the whole file rather than one channel, because the design
deliberately writes every cursor plus the embedded config copy as a single
document. The next run would then either refuse to parse it, leaving the
caller's loop stuck on a file only a human can repair, or read a truncated
prefix and treat every channel below the tear as new — start from now, on all
of them, silently. That second outcome is the total, invisible gap this whole
section exists to rule out, arriving by a mechanism the at-least-once argument
does not otherwise cover.

This belongs in the design rather than the implementation because it is part of
the contract: the caller is told to keep this file between runs and to back it
up, and "you never observe a partially-written state file" is one of the things
it is entitled to assume.

**At-least-once must be stated loudly in the caller-facing docs**, because the
failure mode is rare enough to go unnoticed in testing and specific enough to
matter in production. Consumers that take irreversible action on an event need
their own idempotency key; the event envelope carries enough identity to build
one.

## Configuration

### Format

**YAML**, for two reasons and one nuance.

The reasons: it is comfortable for humans to read in review, and it is easier
for an *agent* to write correctly than JSON — no counting commas, no matching
brackets across a nested structure, no trailing-comma trap. Given that the
primary author of these config files is expected to be a language model, that
is not a small consideration.

The nuance: **JSON is valid YAML.** A caller that would rather emit JSON simply
does, and no code changes. The documentation uses YAML because it reads better;
the parser does not care.

### Shape

```yaml
# botwatch config (sketch)
version: 1

defaults:
  quiet_timeout: 20m
  boarding_window: 2s

channels:
  - key: dev-slack
    type: slack
    conversation: C0123456789

  - key: dev-prs-slack
    type: slack
    conversation: C0987654321

  - key: kickoff-thread
    type: slack
    conversation: C0123456789
    thread: "1785600000.000200"

  - key: upstream-main
    type: git
    remote: git@github.com:example/project.git
    refs: [refs/heads/main]

  - key: build-events
    type: pubsub
    subscription: projects/example/subscriptions/builds
    meta:
      notify: "#builds"
```

Top-level `defaults` set the timing for the run; individual channels may
override where a driver can meaningfully honour it. Everything under a channel
beyond `key`, `type`, and `meta` is the driver's own schema, validated by the
driver — and a driver rejecting its own channel's fields
[localises to that channel](#exit-codes) rather than failing the run.

### Versioning and stability

**There is no config schema versioning, and a config is not guaranteed stable
across long timeframes.** Set one aside for a week and it will very probably
still do the right thing — but nothing promises that, and it should not be
relied on. Being able to promise it is a goal for later, not a property of the
first version; until then, a config is best treated as something written for
the `botwatch` that is installed right now.

`version: 1` nonetheless appears in this sketch, and in the
[state file](#state-file) sketch below, **present but unenforced**. Nothing
reads it, and what happens on a mismatch is undefined for now. It is carried
anyway because a field that exists from the first day costs nothing, while
retrofitting one onto configs already in the wild would force the first real
version bump to guess what an absent field meant. That is the cheap half of
versioning without any of the machinery, and it is what keeps the stability
goal above reachable.

**None of that answer carries over to the state file**, and "undefined on a
mismatch" above is the config's answer rather than a shared one. A config is
authored by a human or an agent who can open it and rewrite it, so "written for
the `botwatch` installed right now" is a fair thing to ask of it. The
[state file](#state-file) is authored by `botwatch` itself, is required to
survive between runs, and its holder is explicitly told to back it up. What an
upgraded `botwatch` does when it meets a state file it wrote under an older
schema is therefore a question of its own, and it is
[left open](#open-questions) rather than settled here.

### Stable keys

**Every channel carries a caller-assigned `key`, and that key is its identity
across runs.**

This is the one piece of the config the caller must think about, and the reason
is that a config is not constant. Channels get added, removed, retimed, and
re-pointed between runs, and `botwatch` has to match up "the state I recorded
last time" with "the channel I am looking at now" through all of it. Position
in the list cannot do that job — inserting a channel would silently shift every
subsequent one onto the wrong state. Nor can the driver-specific fields, since
*changing* them is precisely one of the cases that has to keep working.

It is the same problem, and the same solution, as `key` on a React element:
without it the framework matches by position and re-renders the wrong thing;
with it, identity survives reordering, insertion, and mutation.

**Rules:**

- **Unique** within a config. A duplicate key is a hard error, not a
  last-one-wins.
- **Caller-chosen.** `botwatch` never invents one. There is no rule about what
  a key should *say* — the caller knows what these channels mean, and
  `botwatch` does not.
- **Short and identifier-shaped.** Not a sentence, and not a paragraph of
  prose; a key is a name, not a description. Free-form annotation belongs in
  `meta`.
- **Constrained to a filesystem-safe character set** — proposed:
  `[A-Za-z0-9._-]{1,64}`, no leading `.`.

That last rule deserves its justification, because nothing in the design as
described *needs* it. State is a single file today, so any string would do.

The argument is one-directional: **loosening a constraint later is harmless,
tightening one later breaks every existing config.** And there is a concrete
thing on the horizon that would want the constraint — a future state *directory*
rather than a state file, for drivers that must persist more than a cursor
(intermediate artifacts, cached blobs, a partial clone). If that arrives, the
obvious layout is one subdirectory per channel named by its key, which is safe
only if keys were fs-safe from the beginning. Paying a trivial cost now to keep
a door open is the right trade; discovering later that half the deployed keys
contain `/` is not.

### Caller payload

The `meta` field on a channel is **opaque to `botwatch`** and preserved
verbatim: it is copied into the state file and echoed on every event emitted by
that channel.

This exists so the caller can avoid keeping a second lookup table. An agent
that wants "when something happens on this channel, respond in *that* place"
can hang that on the channel itself, and read it straight off the event, rather
than maintaining a parallel map keyed by channel key and hoping the two stay in
sync. `botwatch` neither validates nor interprets it.

## State file

### Format and audience

**YAML**, matching the config — partly for symmetry, and partly because the
state file wants to be readable when something has gone wrong.

The caller is **not** expected to read or write it in normal operation; it is
`botwatch`'s working memory, and its schema is `botwatch`'s business. But
"machine-owned" and "opaque binary" are different things, and a state file a
developer can open in an editor while debugging a driver is worth a great deal
during exactly the sessions where the tool is hardest to reason about. Where
callers legitimately need facts *about* a state file, that is
[`botwatch inspect`](#inspecting-state)'s job, not a licence to parse it.

### Shape

```yaml
# botwatch state (sketch)
version: 1

created: 2026-07-28T09:00:00Z      # when this state file was first written
updated: 2026-08-02T01:12:44Z      # when this run wrote it

# A complete copy of the config this run was given.
config:
  version: 1
  defaults: {...}
  channels: [...]

channels:
  dev-slack:
    created: 2026-08-01T22:10:00Z  # when this key was first seen
    updated: 2026-08-02T01:12:44Z
    last_event: 2026-08-02T01:12:41Z
    last_error: null               # healthy as of the last run
    meta: {}
    driver:                        # opaque to botwatch; the driver's own
      cursor: "1785633161.000000"  # the ts of the last message seen

  upstream-main:
    created: 2026-08-01T22:10:00Z
    updated: 2026-08-02T01:12:44Z
    last_event: null               # nothing has ever fired here
    last_error: "ssh: connect to host github.com: timed out"
    last_error_at: 2026-08-02T01:05:31Z
    failing_since: 2026-08-01T23:41:12Z  # broken since before the last run
    meta: {}
    driver:
      refs:
        refs/heads/main: 3f9a1c2e...

  old-experiment:                  # retired: kept, config and all
    created: 2026-07-28T09:00:00Z
    updated: 2026-08-01T18:00:00Z
    last_event: 2026-08-01T17:52:10Z
    last_error: null
    retired: 2026-08-01T18:00:00Z
    meta: {}
    config:                        # its config as it stood when last configured
      key: old-experiment
      type: git
      remote: git@github.com:example/experiment.git
      refs: [refs/heads/main]
    driver:
      refs:
        refs/heads/main: 91c4d7ab...
```

### Why the state file embeds the whole config

**A driver frequently needs to know not just its current config but its
previous one.** The config is therefore copied into the state file wholesale on
every write, and handed back to drivers on the next run.

The cases this serves:

- **A new channel.** The key is absent from the previous config *and* has no
  state, so the driver is being started fresh and must decide where to begin —
  usually "now", not "the beginning of history", since a newly-watched source
  should not immediately dump its entire past at the caller.
- **A reconfigured channel.** The key is present but the driver fields changed
  — a Slack conversation re-pointed, a ref list widened, a subscription
  swapped. Only the driver can say whether its recorded cursor is still
  meaningful under the new config, and it can only say so by comparing.
- **A removed channel.** The key is in the previous config but not the current
  one. See [retirement](#retired-channels).
- **A returning channel.** The key is absent from the previous *run's* config
  but present in the state file — a channel that was retired and has now been
  configured again. Its cursor was retained and is still there, so the driver
  resumes from it rather than starting fresh, and `prev_config` is the config
  it last ran under, [retained in its own state block](#retired-channels).
- **A channel that has never established a position.** The key is present in
  the previous config and has no state — a channel whose driver
  [failed on its first run](#the-channel-driver-contract), and so recorded
  nothing to resume from. It is not new, not reconfigured, and not returning,
  but what it needs is what a new channel needs: to decide where to begin.

> [!IMPORTANT]
> **`prev_state`, not `prev_config`, is what distinguishes a channel with a
> position to resume from one without.** A driver that keys "am I new?" off
> `prev_config is None` gets the fifth case above exactly backwards — that
> channel has been configured before and has nothing to resume from, and it
> arises from nothing more exotic than a driver failing on its channel's first
> run. The same key also gets the returning case wrong wherever a config was
> not retained: a state file written under an older schema, a hand-repaired
> one. Starting from now is precisely the silent gap retirement exists to
> prevent. The division of labour is: **state** answers *do I have a position
> to resume from*, and **config** answers *what has changed about how I am
> configured*. Only the second is a comparison.

Storing a diff, or a hash, or a few selected fields would each be smaller and
each would eventually be wrong, because "which fields matter" is a per-driver
question that `botwatch` is deliberately not qualified to answer. The whole
config is a few kilobytes; correctness is worth more.

**Storing all of it and handing all of it to a driver are separate decisions.**
`botwatch` needs the whole previous config for itself — matching keys across
runs, and spotting the new, reconfigured, removed, and returning channels is a
question about the config as a whole. What a driver is given from that copy is
only *its own* channel's slice, as `prev_config`. Whether it should also see
the config for the run as a whole — this run's or the previous one's — is
[deliberately left open](#open-questions).

### Common per-channel metadata

`botwatch` owns and maintains, for every channel:

| Field | Meaning |
| --- | --- |
| `created` | When this key was first observed in a config. Set once, by `botwatch`, when the key appears with no prior state. |
| `updated` | When this run last wrote this channel's state. |
| `last_event` | When this channel last produced an event; `null` if never. |
| `last_error` | Why this channel's driver failed, if it failed on this run; `null` otherwise. Frozen while [retired](#retired-channels). |
| `last_error_at` | When that failure was observed — the most recent observation, refreshed while the channel keeps failing. Absent when `last_error` is `null`. |
| `failing_since` | When the current streak of failures began. Set on a run in which the channel fails and had no *live* streak going into it — its `last_error` was `null`, or it has just returned from [retirement](#retired-channels) — and cleared with `last_error`, so the two timestamps bracket the streak. Absent when `last_error` is `null`. |
| `retired` | When this key stopped appearing in the config; absent while it is configured. See [retirement](#retired-channels). |
| `meta` | The caller's opaque payload, copied from config. |
| `driver` | The driver's own state. Opaque to `botwatch`. |

`created` in particular exists because "how long has this been here, and has it
*ever* done anything" is the question a caller asks when deciding whether a
channel is still worth watching — and mtime cannot answer it, since every write
touches the whole file.

`last_error` is the durable half of a
[localised driver failure](#failure-records), and it is **cleared on the next
run in which that channel is configured and does not fail** — a status field
that outlives the condition it describes misreports, exactly as a stale
`retired` would. "Configured" carries weight there: a
[retired channel](#retired-channels) is never run, so without it the rule would
fire vacuously on the very next run and discard the record of how the channel
stood when it went away.

So a non-`null` `last_error` means "broken as of the most recent run", and
**`failing_since` is what answers "broken since when"** — with `last_error_at`
it brackets the streak, the first observation of the current one and the most
recent. On a channel that has failed once, the two are equal.

**`last_event` cannot answer that question, which is why the field is worth
its place.** It measures silence at the *source*, not driver health, and the
two only track each other on a chatty channel. A channel that has never fired
carries `last_event: null` while being visibly broken — the `upstream-main`
case in the sketch above, which is precisely the case
[`inspect`](#inspecting-state) exists to surface — so reading "since when" off
it would yield no answer at all. A channel whose source is genuinely quiet for
a week and breaks this morning would be dated a week early.

**Carrying a field for it, rather than sending the caller to the event stream,
follows from what this tool is for.** The
[failure records](#failure-records) on stdout are timestamped, so a caller
could keep its own history of them and derive the answer. That is per-source
bookkeeping across invocations, performed by an agent, which is the cost
[Background](#background) opens by refusing to charge the caller — and it would
be charged for a question the caller cannot skip, since
[deciding what a *persistently* failing channel is worth](#caller-responsibilities)
is explicitly its job. The state file is already in this business besides:
`created` is carried so that "how long has this been here" does not have to be
reconstructed, and `inspect` computes `idle` from `last_event` for the same
reason.

These fields are `botwatch`-owned, and `botwatch` writes them for a channel
whose driver failed even though [obligation 4](#the-channel-driver-contract)
leaves that channel's state alone. The two are consistent: what is left
untouched is the `driver:` block — the recorded position — not the common
metadata around it.

### Retired channels

When a key present in the previous config is absent from the current one, the
channel is **retired, not deleted**: its state is kept and marked with a
`retired` timestamp.

The alternative — dropping the state immediately — makes removing a channel
from the config a destructive act, so a caller that removes one temporarily
(or by accident, or via a config-generation bug) silently loses its cursor and
gets a replay or a gap when it comes back. Retention is cheap and reversible;
deletion is neither.

**A retired channel keeps its config as well as its cursor**, in a `config:`
key inside its own state block, holding that channel's config as it stood on
the last run that configured it. Two things depend on it.

The first is an invariant. The state file
[embeds a complete copy](#why-the-state-file-embeds-the-whole-config) of the
config it knows about, and the top-level copy is *this run's*, which by
definition does not mention a retired channel. Without the per-channel copy,
retirement would quietly punch a hole in the one guarantee that section makes.

The second is the point of retirement itself. A returning channel is handed a
real `prev_config` — the config it last ran under — rather than `None`, so it
is not mistaken for a channel that has never been seen. Retaining the cursor
and then handing the driver every signal that says "you are new" would retain
it only to have it ignored, and the caller would get exactly the gap the
retention was bought to avoid.

**Both markers clear when the key returns**: `retired` is removed, and so is
the per-channel `config:` copy, since a configured channel's config is in the
top-level copy where it belongs. A channel that is configured again is live,
and [`inspect`](#inspecting-state) reports `retired`, so leaving it set would
describe a working channel as retired.

**A retired channel's health fields freeze rather than clearing.** No run
exercises a channel that is not configured, so `last_error`, `last_error_at`
and `failing_since` keep whatever they held on its last live run — which is
why [the clearing rule](#common-per-channel-metadata) is scoped to runs in
which the channel *is* configured. The stale-status argument that motivates
that rule does not reach this case: it is about a field outliving the condition
it describes, and a retired channel has no current condition to describe. The
whole block is a frozen record of the last live run — `last_event`, the
`driver:` cursor, and the `config:` copy beside them — and a frozen
`last_error` is no staler than the cursor it sits next to. It is also the fact
a caller re-adding a channel most wants, given that the case this section is
built for is a channel removed by accident or by a config-generation bug.

**On return, the frozen values are not carried forward.** The run in which the
key comes back is evaluated like any other: the channel either fails, dating a
fresh `failing_since` from that run, or it does not, and all three fields
clear. Preserving a streak across the retirement would assert that the channel
was failing throughout a period in which nothing was watching it, which is not
something the state file is in a position to know.

Retired state does not accumulate forever: it is what
[`inspect`](#inspecting-state) surfaces and what a `prune` operation removes,
on the caller's schedule rather than as an invisible side effect. See the
[open questions](#open-questions) on exactly where that boundary sits.

## The channel driver contract

A driver is instantiated **once per configured channel**, per run. This is the
contract, and it is deliberately narrow:

```python
class ChannelDriver(Protocol):           # illustrative, not prescriptive
    def __init__(
        self,
        key: str,                            # the stable key
        config: ChannelConfig,               # this channel's config this run
        prev_config: ChannelConfig | None,   # as last configured, else None
        prev_state: DriverState | None,      # position to resume from, if any
        context: RunContext,                 # the run's shared settings
    ) -> None: ...

    def watch(self) -> AsyncGenerator[Event, None]:
        """The channel's event stream: one event yielded as each is detected.

        Stays open until the consumer stops pulling and closes it, which is
        the normal ending and what runs the driver's cleanup. Ending it
        sooner asserts that this channel will produce nothing further for
        the rest of this run.
        """

    def get_state(self) -> DriverState:
        """The state to record for next time.

        Read once, after the stream has ended by any means other than an
        error — whether the consumer closed it or the driver ended it — and
        not read at all if the stream ended in an error. Must never describe
        more than the events actually yielded; describing exactly them is the
        target, and describing fewer costs a replay.
        """
```

**A driver is an event stream.** It yields events as it detects them, and keeps
yielding for as long as its consumer keeps pulling. It is not handed a callback
to push into, and it is not asked to work out when it is finished: `botwatch` —
the sole consumer of that stream — decides that, because `botwatch` is the only
party that knows about the [quiet timeout and the boarding window](#the-wait),
which are properties of the *run* rather than of any one channel.

**The consumer owns closing the stream**, and closing is the pivot the rest of
the contract turns on. It is what tells the driver that nothing further will be
pulled, so it is what triggers the driver's cleanup; and it is what makes the
final state readable, because until the stream is closed there is no answer to
"which event was the last one" — another may still be coming.

**The contract therefore runs one way.** Events flow out of the driver and
nothing flows in, and the only thing read back is the final state, read once,
after the close. The alternative shape — a driver pushing events through a
callback while the runner pulls state back through a method — runs the contract
in both directions at once for no benefit, and leaves the boundary between
"emitted" and "not yet emitted" as something the driver must track for itself.
A stream removes both problems: an event has been delivered exactly when its
yield has been taken, so producing an event and accounting for it are the same
act.

> [!NOTE]
> **In Python this contract *is* an `AsyncGenerator`, and implementations
> should use one rather than approximate it.** `watch` is an `async def` with
> `yield` in it; the driver's cleanup goes in a `finally:` around the yield
> loop, which the language runs when the generator is closed. On the consumer
> side, each driver's stream is wrapped in
> [`contextlib.aclosing`](https://docs.python.org/3/library/contextlib.html#contextlib.aclosing)
> and the whole set is held in an
> [`AsyncExitStack`](https://docs.python.org/3/library/contextlib.html#contextlib.AsyncExitStack),
> which closes them deterministically, in reverse order of acquisition, on
> every exit path including an exception.
>
> **The order of those two steps matters, and getting it wrong fails on the
> very first shutdown.** To `select` over *N* channels the consumer holds one
> pending `__anext__` per stream, and a generator suspended at an `await`
> *inside* its body is already running: `aclose()` on it raises `RuntimeError`
> instead of closing it, and cleanup falls back to the interpreter's
> end-of-loop asyncgen shutdown — which runs after the exit stack has already
> unwound, not in reverse order of acquisition, and not on every exit path.
> That is precisely the state every waiting driver is in at the moment the
> boarding window closes, which is the normal ending rather than an edge case.
>
> So the consumer **cancels each stream's in-flight pull and awaits its
> completion first**, and only then lets the `AsyncExitStack` unwind. The
> cancellation is what actually reaches the driver: it is delivered to the
> suspension point inside `watch`, and the `finally:` runs from there.
> `aclosing` is then the belt to cancellation's braces, covering any stream
> that happened to be suspended at a `yield` rather than mid-pull, and making
> the close a no-op for the rest.
>
> **The driver-facing consequence:** cleanup in a `finally:` that needs to
> `await` is running under cancellation, and must be written for it — an
> `await` there may itself be interrupted, so cleanup should be short, local,
> and tolerant of not finishing. That is obligation 2's "do not block the
> close on work that can be abandoned", seen from the implementation side.
>
> The contract is *stated* in language-neutral terms — the sketch is
> Python-flavoured pseudo-code, as everything in this document is, but the
> obligations it illustrates do not depend on Python — because a port to a
> compiled language has to be able to read them, and Go and Rust have no async
> generators to point at. That is a constraint on the wording. It is not
> licence to hand-roll `__aiter__`/`__anext__` and a bespoke `close()` in the
> language that ships the thing already.

The obligations, spelled out:

1.  **Yield each new event exactly once per run**, in source order where the
    source has one.
2.  **Stay open until the stream is closed, and release cleanly when it is.**
    A driver's stream stays open for as long as its consumer keeps pulling.
    Ending it sooner is not a way of saying "nothing right now" — it is a
    positive assertion that **this channel will produce nothing further for
    the rest of this run**, and `botwatch` acts on it as such.

    The distinction matters most for the pull-based sources in
    [channel types](#channel-types), where "nothing new" is the ordinary state
    of almost every poll. A driver that falls off the end of its loop when a
    poll comes back empty removes its arm from the `select` on the first tick;
    with every driver written that way the run exits immediately having
    reported nothing, the caller relaunches at once, and the tool has become
    the hot poller [Background](#background) opens by rejecting. Poll again
    instead, and keep the stream open.

    Closing is the *normal* ending — it happens every time the boarding window
    closes with a driver still waiting — and the consumer, not the driver,
    picks the moment. That much the shape guarantees on the driver's behalf:
    there is no shutdown flag for a driver to poll, no shutdown protocol for it
    to opt into, and no way for it to simply not stop. Cancellation has not
    disappeared — it is still the mechanism that reaches a waiting driver — but
    it has moved from something every driver must implement and honour to
    something the consumer performs on the driver's behalf, in one place in the
    runtime rather than in *N* driver implementations.

    What the driver still owes is what happens *during* the close: release what
    it acquired, do not go on yielding, do not block the close on work that can
    be abandoned, and do not leave the state it is about to be asked for
    half-written. Cleanup that has to wait on something is running under
    cancellation and has to be written for that. A driver that swallows the
    close and keeps working is the one remaining way to hang a run.
3.  **Report state consistent with what was yielded.** If the stream was closed
    after three of five available events had been yielded, `get_state()` must
    describe the position after event three. Reporting a further position drops
    events; reporting an earlier one replays them, which is merely wasteful. So
    exactness is the target, and rounding *down* is the tolerable miss.

    The mistake this invites is a paging source that fetches five events,
    records the page's end position, and then yields them one at a time — which
    is the "further position" failure, and it drops events. **A driver's own
    record of "I have yielded this" must be updated before the yield, not
    after**, because the consumer's close arrives *at* the yield and nothing
    after it runs.

    **A stream ends one of three ways, and this obligation covers two of
    them.** The consumer may close it, the driver may end it (obligation 2),
    or it may raise. The first two are the same case here: the consumer closes
    every stream on its way out regardless, so a stream the driver ended has
    still been closed by the time its state is read, and closing an already
    exhausted stream is a no-op rather than a different path. Only the third
    is excluded — a stream that ended in an *error* is obligation 4's case,
    and its state is not read at all.

    Reading the driver-ended case the other way would be worse than the
    exclusion obligation 4 makes deliberately: a driver that did exactly what
    obligation 2 asks — asserting its channel is finished for this run — would
    have its position discarded on every run, and replay from the beginning
    forever.
4.  **Localise its own failures.** A driver that cannot run its channel —
    because it cannot reach the source, or because the channel's config does
    not validate against [its own schema](#shape) — should fail *that channel*,
    leaving its recorded position untouched, rather than taking the run down.
    One unreachable source must not blind the caller to the other nine. An
    error raised out of a stream ends *that* stream and nothing else:
    `botwatch` treats it as a channel that has stopped producing and keeps
    waiting on the rest.

    Reporting the failure is then `botwatch`'s job rather than the driver's,
    and it has two destinations: a [failure record](#failure-records) on stdout
    as it happens, and
    [`last_error` / `last_error_at` / `failing_since`](#common-per-channel-metadata)
    in the channel's common metadata afterwards. What the driver leaves
    untouched is its own `driver:` block.

    **`get_state()` is not read from a stream that ended in an error.** The
    position recorded for that channel is the one it held at the start of the
    run. This is the case of a driver that yields some events and *then* fails
    — page one reads fine, the token expires before page two — which satisfies
    obligation 3's premise and this one's at the same time, and they instruct
    oppositely. It is resolved in favour of this one.

    The reason is that `get_state()` is specified to be read after a *close*:
    an ending the consumer chose, arriving at a point the driver controls. A
    driver that raised did so from an arbitrary point inside its own body, and
    requiring every driver author to make `get_state()` correct after an
    arbitrary exception is a far heavier obligation than requiring it after a
    close — the kind of per-driver burden this contract moves into the runtime
    wherever it can. Advancing a cursor on the word of a driver that has just
    failed risks the invisible gap
    [delivery semantics](#delivery-semantics) ranks as the worst outcome
    available, in order to save a duplicate that the same section already tells
    callers to expect. It is also the answer the rest of this document already
    assumes — this obligation's own "leaving its recorded position untouched",
    and [failure records](#failure-records)' restatement of it — so the
    alternative is not a gap to be filled but two statements to be retracted.

    **What it costs is worth stating rather than leaving to be discovered:** a
    driver that fails at the same point on every run re-reports the same events
    on every run, for as long as the source stays broken. A paging source whose
    token expires before page two is the ordinary way to arrive here.

    The *volume* of that is contained by the caller-side deduplication
    [at-least-once](#delivery-semantics) already requires: these are real
    source events carrying source-native `id`s, so a caller that remembers the
    ids it has acted on drops them. **The run's pacing is not contained by
    it**, and that is the larger cost. `botwatch` cannot tell a replay from a
    first sighting — it advanced no cursor, so from its side these are simply
    events a driver yielded — and [the wait](#the-wait) is otherwise
    unconditional, so replayed events would open the boarding window and the
    run would depart on it. Every run then departs seconds after starting, for
    as long as the source stays broken, and takes every *other* channel's wait
    with it, because the window is run-wide.

    That outcome is the hot poller this design exists to replace, so
    [the wait](#the-wait) rules it out with a third departure guard rather than
    accepting it as a documented cost.
5.  **Interpret nothing.** A driver reports that something happened and carries
    the payload; it does not decide what the payload *means*. (See
    [non-goals](#non-goals) for the deliberate crack left open here.)

### The run context

`context` carries the facts about the run as a whole that a driver may
legitimately need — the run-wide **settings** themselves, rather than a
reference to the config they came out of:

```python
class RunContext(Protocol):              # illustrative, not prescriptive
    defaults: Defaults                   # the run-wide timing settings
```

Without it, a top-level setting that some driver cares about has only one place
to go: copied into every channel of that type by hand, and then kept in sync by
hand. `defaults` is the one already visible in the config sketch — a driver
that would behave differently under a two-second boarding window than under a
two-minute one has to be able to see which it is — and it is unlikely to be the
last. Whatever joins it joins here.

**The context is the settings, not the config.** Handing over a reference to
the whole `Config` would serve the same use case, and would also hand every
driver every other channel's config — access with no job attached to it,
restrained only by a written rule that nothing enforces. That is the same trade
the [open question](#open-questions) on the overall config settles below, and
it is settled the same way here: widening a narrow contract on a guess is how
it stops being narrow. It is also one-directional, exactly as with the
[key charset](#stable-keys) — widening later breaks nothing, while narrowing
later breaks every driver in the wild that had reached through the wide type.
If a driver turns up that genuinely needs to know something about the config as
a whole — how many channels are configured, say — that is evidence, and it can
widen this then.

**The channel-level `config` and `prev_config` stay explicit arguments** rather
than being reached through the context. They are what a driver touches on every
call, and making it navigate a context to find *its own* config would charge
indirection to the common path in order to save it on a rare one. The context
carries what is genuinely shared; the arguments carry what is genuinely this
channel's.

The config for the run as a whole — this run's or the previous run's — is
therefore not reachable from a driver at all; see
[open questions](#open-questions).

### One instance per channel, and what goes on underneath

Ten channels of type `slack` in a config means ten driver instances. What those
instances do about transport is **entirely their own business, and the simplest
answer is a good one.**

**A driver that gives each instance its own client is a perfectly reasonable
implementation**, and the obvious place to start. It is easy to write, easy to
reason about, and easy to test. Its only cost is efficiency — ten instances
means ten sets of API calls where a cleverer arrangement might make fewer — and
efficiency is not the first problem worth solving.

*Should* that cost ever start to matter, one option among several is for
drivers of a type to share a private client behind the interface: a lazily
obtained singleton that coalesces its instances' requests into fewer calls and
fans the results back out, in the manner of the "loader" pattern from GraphQL
servers. **This is a suggestion for later, not a recommendation for now.**
Nothing in this document asks for it, and an implementation that never does it
is not deficient.

What the contract *does* care about is not painting the option out of
existence, which costs the simple implementation nothing. Two shapes would, and
both are easy to write by accident:

- A **synchronous** `poll()` returning a list. Ten sequential blocking calls
  cannot be overlapped at all, by any arrangement, and undoing that means
  breaking the interface.
- A driver whose **transport lifecycle is a public step of its own** —
  connecting in `__init__`, closing in a `close()` the runner must remember to
  call alongside closing the stream — pins one connection per channel into the
  interface, for every driver, forever.

The contract above avoids both without asking for anything. The event stream is
asynchronous because concurrency across channels is required regardless, and
transport ownership is simply not mentioned, which leaves it private to the
driver: closing the stream is the single cleanup hook, and *what* is cleaned up
there is the driver's own business. A naive one-client-per-instance driver
closes its client and satisfies the contract exactly as written; an instance
borrowing a shared client releases its borrow and leaves the client alone, and
satisfies it just as exactly.

## Event output

**JSONL on stdout: one JSON object per line, written as each event is
detected.**

This is the [robustness principle](https://en.wikipedia.org/wiki/Robustness_principle)
applied asymmetrically, and the asymmetry is the design:

- **Input is YAML** — generous, human- and agent-friendly, and accepts JSON for
  free.
- **Output the caller consumes is JSON** — the least-common-denominator format
  every language parses identically, one self-delimiting record per line, safe
  to read incrementally without a streaming YAML parser.
- **Internal data the caller does not consume** (the state file) **is YAML**,
  where readability during debugging is worth more than parser ubiquity.

Multi-document YAML on stdout was considered and rejected: it would be
symmetrical with the input for its own sake, at the cost of making every
consumer reach for a YAML library to read a stream that JSONL handles with
`json.loads` per line — and of making partial-line reads during streaming
meaningfully harder to reason about.

### Envelope

Every event shares a `botwatch`-owned envelope and carries a driver-owned
payload:

```json
{"channel":"dev-slack","type":"slack","kind":"message","id":"1785633376.000000","ts":"2026-08-02T01:16:16Z","meta":{},"payload":{"...":"driver-specific"}}
```

| Field | Owner | Meaning |
| --- | --- | --- |
| `channel` | botwatch | The stable key. |
| `type` | botwatch | The channel type, copied from config. |
| `kind` | driver | What sort of event this is within that type (`message`, `commit`, `pull_request`, …). The single value `error` is reserved for [`botwatch`'s own failure records](#failure-records). |
| `id` | driver | Source-native identity, stable across replays. The basis for caller-side deduplication. On [failure records](#failure-records) it is `botwatch`-generated and deliberately fresh per observation, so those do **not** collapse. |
| `ts` | driver | When it happened at the source, RFC 3339. Distinct from when `botwatch` noticed — except on [failure records](#failure-records), where it is `botwatch`-owned and is exactly when `botwatch` noticed. |
| `meta` | botwatch | The caller's opaque payload for this channel, echoed verbatim. |
| `payload` | driver | Everything else, driver-specific. `botwatch`-owned on [failure records](#failure-records), where it carries the error. |

`id` is what makes [at-least-once](#delivery-semantics) tolerable rather than
merely honest: a caller that records the ids it has acted on can drop a replay
without understanding what any of it means. Failure records are the deliberate
exception, and the table says so on the row, because that technique does not
fail loudly against them — it simply never matches.

**Diagnostics go to stderr**, never stdout. A caller parsing stdout must never
have to skip a line.

### Failure records

A driver failure that [localises correctly](#the-channel-driver-contract) is
otherwise invisible through every structured surface a caller has. The exit
code is `0`, because the failure was localised and the run completed. The
state file's recorded position is unchanged, by obligation 4's own
instruction. And [`inspect`](#inspecting-state) reports the channel as idle,
which is exactly what it reports for a channel where genuinely nothing
happened. A Slack token that expired on Tuesday and a quiet week look
identical.

So `botwatch` writes a record of its own whenever a channel fails — its stream
ends in an error, or its driver
[rejected the channel's config](#exit-codes) before a stream ever started:

```json
{"channel":"upstream-main","type":"git","kind":"error","id":"upstream-main@2026-08-02T01:05:31Z","ts":"2026-08-02T01:05:31Z","meta":{},"payload":{"error":"ssh: connect to host github.com: timed out"}}
```

`kind: error` is the one value of that field `botwatch` owns rather than the
driver, and `id` and `ts` are `botwatch`-generated here too — `ts` is when the
failure was observed, and `id` is derived from the channel key and that
timestamp. The point of keeping the same envelope is that this costs a caller
nothing: it is one more line of the same shape, with the same `channel` and the
same `meta`, and a caller that ignores kinds it does not recognise is
unaffected. What it buys is that an agent reading the stream sees the failure
*while the run is still going*, rather than inferring it from a silence.

Every failure record gets a fresh `id`, so a caller deduplicating by `id` does
not collapse them: a channel that has failed on twenty consecutive runs has
reported twenty records. That is the honest count — each is a separate
observation of a source still being unreachable, not a replay of the first
one.

**A failure record does not open the boarding window and does not set
`last_event`.** It is not an event from the source; it is `botwatch` reporting
about the source. Were it to count as one, a channel that fails immediately at
startup would open the window on every run, and each run would depart two
seconds after starting — which would abolish the quiet timeout for anybody with
one broken channel. The run
[waits out the quiet timeout](#the-wait) instead, and a caller that reads
streamingly has the failure in hand long before it returns.

That guard covers a driver that fails *before* yielding anything. A driver that
yields and then fails is covered by
[the third departure guard](#the-wait), which abandons the departure when every
event in the window came from a stream that has since errored — otherwise the
replayed events would open the window on every run and reintroduce exactly the
outcome this paragraph rules out.

The durable half of the same fact is
[`last_error`, `last_error_at` and `failing_since`](#common-per-channel-metadata)
in the channel's state. **Durable** there means *readable out of band*, not
*surviving recovery*: a record on stdout is seen only by whoever was reading
the stream as it went past, whereas the state file answers "is this channel
broken, and since when" to anyone who runs [`inspect`](#inspecting-state)
between runs, hours later. All three fields clear together on the first run in
which the channel is configured and does not fail, because at that point the
condition they describe has ended.

## Caller responsibilities

`botwatch` is deliberately incurious, which means the caller owns everything it
declines to:

1.  **The state file.** Where it lives, that it survives between runs, that it
    is backed up if it matters, that it is eventually deleted. Also: that
    **only one `botwatch` runs against it at a time** — nothing enforces that,
    and doing it anyway is
    [explicitly undefined](#concurrent-runs-against-one-state-file).
2.  **Duplicate tolerance.** At-least-once means what it says. Anything with an
    irreversible effect needs the caller to remember `id`s it has acted on.
3.  **Deciding whether to run again.** `botwatch` never loops. The caller's
    loop is where "should I still be watching this?" is answered.
4.  **Config authorship, including keys.** Their uniqueness, their stability
    over time, and their meaning.
5.  **Garbage collection.** Retired channel state, and state files for contexts
    that no longer exist.
6.  **Noticing that a channel is broken.** Localising a failure is what keeps
    the other nine channels working, and the price is that a broken source and
    a quiet one both exit `0`. [Failure records](#failure-records) on stdout
    say so as it happens; `last_error` / `last_error_at` / `failing_since` via
    [`inspect`](#inspecting-state) say so afterwards, and the last of those is
    what makes *persistently* a question the caller can answer without keeping
    its own history. Reading either surface, and deciding what a persistently
    failing channel is worth, is the caller's — `botwatch` will keep reporting
    the failure indefinitely and will never escalate it.

### Inspecting state

Garbage collection and health both need facts about a state file that the
caller cannot get otherwise. `mtime` is not one of them — it is updated by
every run including runs that found nothing, it is destroyed by copying, and
it says nothing at all about individual channels.

So `botwatch` offers a read-only subcommand:

```console
$ botwatch inspect state.yaml
created: 2026-07-28T09:00:00Z
updated: 2026-08-02T01:12:44Z
age: 136h12m
channels:
  dev-slack:
    created: 2026-08-01T22:10:00Z
    last_event: 2026-08-02T01:12:41Z
    idle: 24h0m
    last_error: null
  upstream-main:
    created: 2026-08-01T22:10:00Z
    last_event: null
    idle: null
    last_error: "ssh: connect to host github.com: timed out"
    last_error_at: 2026-08-02T01:05:31Z
    failing_since: 2026-08-01T23:41:12Z
    failing_for: 25h31m
  old-experiment:
    created: 2026-07-28T09:00:00Z
    retired: 2026-08-01T18:00:00Z
    last_event: 2026-08-01T17:52:10Z
    last_error: null
```

`upstream-main` there is the case the design would otherwise hide: a channel
that has never produced an event and is also broken, which without `last_error`
is indistinguishable from one nobody has spoken in. It is also the case that
shows why [`failing_since`](#common-per-channel-metadata) has to be a recorded
field rather than an inference — `last_event` is `null`, so there is nothing
beside the error to date it from, and `failing_for` is the "how long has this
been down" that a caller would otherwise reconstruct for itself.

**Retired channels render their recorded facts but not the computed ones.**
`old-experiment` shows `last_event` and `last_error` as they stood on its last
live run, and omits `idle` deliberately: `idle` is measured against *now*, and
"how long has it been quiet" means nothing for a channel nobody is watching.
`failing_for` is omitted for the same reason, while a frozen `failing_since`
is still shown when set, because it records when something happened rather than
how long ago it was.

YAML by default to match the state file, `--json` for programmatic consumers,
per the same asymmetry as everywhere else. `inspect` never writes.

## Channel types

Ordered by how soon they matter, not by how interesting they are.

### Slack

**Near term. The first driver, and the one the design was pressure-tested
against.**

One botwatch channel per Slack *conversation* — a Slack channel, a DM, or a
single thread. Not one botwatch channel that enumerates several conversations
of interest.

That is a real decision and worth defending, because the opposite is tempting:
one `#dev` botwatch channel that also watches four threads inside `#dev` looks
economical. It is the wrong seam. Keys, state, retirement, and `meta` are all
per-channel, so a botwatch channel covering several conversations means the
caller can no longer add, remove, retire, or annotate one of them
independently — the exact operations the key system exists to support. If the
per-conversation cost ever turns out to matter, that is a question
[for the driver's insides](#one-instance-per-channel-and-what-goes-on-underneath)
rather than a reason to coarsen the config.

Threads are their own case worth noting: a thread's replies are invisible to a
conversation-level read of top-level messages, so watching a Slack channel and
watching a thread in it are genuinely different subscriptions, not a subset
relationship.

### Git

**Near term. Both local and remote, and both are valuable for different
reasons.**

- **Remote** — `git ls-remote` / `git fetch` against a URL. Watches for refs
  moving: pushes to a branch, new tags. This is the "something landed
  upstream" signal.
- **Local** — watching refs in a repository on disk, which additionally sees
  work in progress: commits made locally, branches created, a rebase happening.

The open design question is whether these are one driver with a `remote` field
or two drivers. Leaning toward **one**: the concept is identical (a set of refs
and the SHAs they point at) and only the transport differs, so a single driver
with a `remote:` key that defaults to the local path keeps the config simple
and the state schema shared. If the local variant grows a genuinely different
capability — watching the working tree or the index, which have no remote
analogue — that is the moment to split.

### GitHub

**Near term, and deliberately separate from git.**

`git` sees refs. GitHub has pull requests, reviews, issue comments, and check
runs, none of which are refs and all of which are the events an agent
collaborating on a repository actually cares about. Modelling them as a git
channel would mean stretching "ref moved" past breaking point.

There is deliberate overlap: a GitHub driver could report commits, and so can
the remote git driver. That is fine — a caller wanting both simply configures
both, and the two channels are independently keyed and independently retired.
Suppressing the overlap would cost more in complexity than it saves.

### Pub/Sub

**Medium term, and the one that changes what is possible rather than what is
convenient.**

A Google Cloud Pub/Sub subscription as a botwatch channel makes the whole
system **push-capable**. Everything above is fundamentally a pull with good
manners; a pub/sub channel is a genuine push, arriving in milliseconds, through
the same `select`.

The example that motivates it: an interactive widget in a chat message with a
button on it. The button hits an HTTP endpoint, the endpoint publishes to a
topic, and a waiting `botwatch` returns instantly with the event. An agent
becomes something a human can *press*, rather than something they wait for.

Notably it needs nothing new from the model — an acknowledgement ID is a cursor
like any other, and nothing stops a driver's event stream being fed by a
long-lived streaming pull, since the consumer's close is what ends it.

### Local file

**Speculative.**

Watch a file for modification, or a directory for changes. No compelling use
case is in hand, which is exactly why it should not be designed in detail yet —
the interesting question (a file? a directory? recursive? content or just
mtime?) is unanswerable without one. Listed so that the model can be
sanity-checked against it: a file is a source with a cursor, and it fits.

### Further out

Named to check the model's generality, not to be built:

- **Issue trackers** (Jira and friends) — new tickets, transitions, comments.
- **RSS/Atom** — the cursor is an entry id or timestamp; nearly trivial.
- **Email**, via a replication-to-git pipeline — mail lands as commits in a
  repository, and the *git* driver watches it. "Replicate to git, watch git"
  generalises: any source with an exporter needs no botwatch driver at all.
- **Webhook bridges generally** — anything that can `POST` can reach pub/sub,
  and therefore reach `botwatch` without a bespoke driver.

## Non-goals

- **No content interpretation.** `botwatch` reports that something happened and
  hands over the payload. What it *means* is the consuming agent's job, and the
  agent is far better equipped for it.

  The crack deliberately left open: a *driver* may legitimately do bounded,
  declared parsing where it is the only thing positioned to — a specialised
  variant of the Slack driver that expects a particular header format in
  top-level messages, emits the parsed fields alongside the raw payload, and
  filters out messages that do not match. That is opt-in, per-channel, and
  clearly labelled. It is not `botwatch` growing opinions about content.

- **No daemon, no background process, no supervision.** See
  [one-shot](#one-shot).

- **No delivery guarantee beyond at-least-once.** Exactly-once across a process
  boundary is not achievable without the consumer participating, and the
  consumer here is an agent. Better to be honest and give callers the `id` they
  need.

- **No orchestration.** `botwatch` does not decide what to do about an event,
  does not route, does not retry the caller's work, and has no notion of a
  handler.

- **No multi-consumer fan-out.** One state file, one caller, one run at a time.
  Two agents interested in the same source keep two state files, which costs a
  little duplicate polling and saves an entire coordination problem. The "one
  run at a time" half of that is assumed rather than enforced — see
  [below](#concurrent-runs-against-one-state-file).

### Concurrent runs against one state file

**Running two `botwatch` processes against the same state file is undefined
behaviour**, and that is a decision rather than an omission. There is no
advisory lock, no contention detection, and no waiting for another run to
finish. Not doing it is the caller's responsibility — and the caller is the
party that can honour it, since it is the one deciding when to run.

> [!WARNING]
> "Undefined" here does not mean "unspecified, pick something sensible". The
> failure is real and silent: two runs sharing a state file last-write-wins
> each other's cursors, and every event covered by the losing write is dropped
> with no diagnostic, no non-zero exit, and nothing left in the state file to
> show that it happened.

The alternative considered was an advisory lock, and it is a bad trade: one
paragraph in a design document, a long tail of platform-specific misery in an
implementation, and a fresh question of its own — fail fast on contention, or
wait? — all to guard against something the caller can simply not do.

## Open questions

Genuinely unresolved; flagged rather than quietly decided.

1.  **Where retirement ends.** Retired state is retained, but for how long, and
    who removes it? Options: never automatically (caller runs `prune`); after a
    configurable age; on the run that first observes the absence. Leaning
    toward the first, because automatic removal reintroduces the destructive
    behaviour that retirement exists to avoid — but it does mean state files
    grow without bound if nobody ever prunes.

    That leaning carries a dependency worth stating outright: `prune` is
    referred to here and in
    [caller responsibilities](#caller-responsibilities) and is specified
    nowhere — no flag, no subcommand, no behaviour. Since
    [acceptance](#acceptance) calls this RFC complete once every open question
    is answered or explicitly deferred, this one cannot close on its preferred
    answer until `prune` is specified somewhere for it to close *onto*.

2.  **State files written under an older schema.** The state file is
    `botwatch`'s own artifact, it is required to survive between runs, and its
    holder is told to back it up — so an upgraded `botwatch` will sooner or
    later meet a state file it wrote under a schema it no longer uses. Both
    obvious outcomes are bad. A run that cannot start leaves the caller's loop
    wedged on a file only a human can repair. A silent reset to "start from
    now" on every channel is a total, invisible gap, which is the failure this
    design ranks as its worst available. Migrating in place, refusing loudly
    and telling the caller what to do, and rebuilding only what can be rebuilt
    are all on the table. `version: 1` is already written into every state
    file, unread; what reads it, and what it does when it does not like the
    answer, is the question.

3.  **Per-channel timing overrides.** The config sketch permits them. Some
    drivers cannot honour a boarding window meaningfully (a genuine push source
    has nothing to wait for), and it is not obvious whether the right answer is
    "ignore it", "reject it at validation", or "the run's window is global and
    channels never override it".

    Whichever way it goes, it is entangled with the
    [run context](#the-run-context), which carries `defaults` — the *run-wide*
    settings. A driver on a channel that overrides `boarding_window` would read
    the run-wide value there rather than its own, which is that section's own
    motivating example turned around. Answering this question means saying what
    such a driver sees.

4.  **Startup position for a new channel.** "Start from now" is the proposed
    default, but some sources make "now" ambiguous and some callers genuinely
    want backfill. Should this be a per-channel config option
    (`start: now | beginning | <cursor>`), or is that a driver concern?

5.  **Access to the *overall* config, current or previous.** A driver gets the
    config for its own channel, this run's and the previous run's; the
    [run context](#the-run-context) carries the run-wide settings and nothing
    else. Neither the current nor the previous config for the run as a whole is
    reachable. No use for either turned up that the channel-level `config` and
    `prev_config` did not already serve, and widening a narrow contract on a
    guess is how it stops being narrow. The first driver that genuinely wants
    one should arrive as the evidence that settles this, rather than the field
    arriving first in case someone eventually does.

## Acceptance

This RFC is complete when it has been reviewed and the
[open questions](#open-questions) have been either answered or explicitly
deferred with a note. Implementation issues then follow from it, one per
component: the runner and its timing model, the config and state schemas, the
driver contract, and one issue per driver.

The design itself is validated when the following hold of an implementation:

- A run with an empty state file and a config of *N* channels creates state for
  all *N*, reports events from none of them retroactively, and exits on the
  quiet timeout.
- A burst of *M* events arriving within the boarding window is reported by a
  **single** run, in one process — and a burst that is still arriving when the
  window closes is *split* across runs rather than extending it, since the
  window is measured from the first event and does not slide.
- The first event of an idle period is written to stdout — **measured through a
  pipe**, not a terminal — in well under a second, without waiting out either
  interval.
- Adding, removing, re-adding, and reconfiguring channels between runs each
  preserve or reset the affected cursor as documented, and disturb no other
  channel. In particular, a channel removed for one run and configured again on
  the next resumes from its retained cursor and reports what arrived while it
  was away, rather than starting from now.
- A run killed mid-boarding-window leaves the state file at its previous
  position, and the next run re-reports the in-flight events.
- A run killed *during the state write* leaves a state file that parses, and
  that is either the previous run's or this one's — never a partial document.
- Closing a driver's event stream while it is still waiting runs that driver's
  cleanup, and leaves `get_state()` describing the events already yielded — no
  more. Exactness is the target; an earlier position is a tolerated replay, a
  later one is a failure.
- A driver that ends its *own* stream has `get_state()` read and recorded like
  any other clean ending, rather than discarded as an error would be. The three
  endings are distinguished: consumer-closed and driver-ended both record,
  errored does not.
- One unreachable source does not prevent the other channels from reporting,
  and its failure is visible both on stdout as it happens and through `inspect`
  afterwards.
- A run in which *every* channel's driver fails immediately still waits out the
  quiet timeout rather than exiting at once, and exits `0`.
- A driver that yields events and *then* fails leaves that channel's recorded
  position unchanged, and the next run re-reports those events. A driver that
  fails at the same point every run re-reports them every run, indefinitely.
- A run whose only events came from a stream that subsequently errored waits
  out the quiet timeout rather than departing on the boarding window, and the
  events it already wrote stay written. Repeated against a source that fails at
  the same point every time, the caller's runs stay paced by the quiet timeout
  rather than collapsing to the length of the window.
- A run in which one channel yields and then fails while another yields and
  stays healthy **departs** on the boarding window rather than waiting out the
  quiet timeout — including when the failing channel is the one that opened the
  window. The guard is scoped to every event collected, not to the event that
  opened it.
- A channel that fails on several consecutive runs reports a `failing_since`
  fixed at the first of them and a `last_error_at` that advances with each; the
  first run in which that channel is configured and does not fail clears both.
  A channel retired while failing keeps both unchanged for as long as it stays
  retired — and a channel retired while failing, configured again, and failing
  again on its return dates `failing_since` from the *return* run, not from
  before the retirement.
- A channel whose config its own driver rejects produces a failure record,
  leaves every other channel's reporting undisturbed, and exits `0`; a
  structurally invalid config — unparseable, or carrying a duplicate key —
  exits non-zero without running any driver.
