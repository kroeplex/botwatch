# 0014 — A watched source is a dynamic set of ordered sub-streams

**Status:** Open
· **Kind:** RFC
· **Parent:** <a href="0001.md" title="0001 — botwatch: a one-shot `select` over many event sources">0001</a>
· **Supersedes:**
  <a href="0005.md" title="0005 — Define the channel driver contract and ship a conformance kit every driver must pass">0005</a>,
  <a href="0006.md" title="0006 — Wait on every channel at once: the select, the two clocks, and the departure guards">0006</a>
· **Feeds:**
  <a href="0015.md" title="0015 — Slack driver: threads are discovered sub-streams">0015</a>

> The current core models a watched source as **one ordered stream**: a driver
> yields events "in source order where the source has one," and state is one
> cursor per channel. Most real sources are not shaped like that. A Slack channel
> carries a top-level conversation *and* a thread under each message; a git
> repository carries many refs; a GitHub repository carries many pull requests.
> Each of those parts has its own order and its own position, they are **created
> and abandoned while the watch runs**, and no caller controls when.
>
> The Slack-driver design ([0009](0009.md)) hit this and forced a bad choice:
> either make every thread its own top-level channel — so the config explodes and
> has to be edited every time somebody starts a thread — or watch the channel and
> silently miss every reply. Both are wrong, and the wrongness is not Slack's; it
> is the one-stream-per-source frame.
>
> This RFC reframes the core: **a source is a dynamic set of ordered
> sub-streams.** The driver discovers the sub-streams, yields each one's new
> events in its own source order, and keeps a cursor per sub-stream. It
> supersedes the driver contract ([0005](0005.md)) and the select
> ([0006](0006.md)), carrying their sound parts forward under the new frame.

## Background

### What the current core says, and where it holds

[0005](0005.md) defines a driver as one instance per configured channel with a
`watch()` that yields events and a `get_state()` that reports a resume position,
and pins five obligations: yield each event once in source order, stay open until
closed, report state consistent with the yields, localise failures, interpret
nothing. [0006](0006.md) defines the runtime that multiplexes those drivers — the
`select` with its **quiet timeout** (leave when nothing happens) and **boarding
window** (once something does, wait a beat for more), plus the guards that stop a
run departing early and busy-looping.

**Almost all of that is right and this RFC keeps it.** The `select`, the two
clocks, the departure guards, the conformance-kit idea, four of the five
obligations — none of that is the problem. The problem is a single assumption
underneath obligation 1 and the state model: **that a source has one order and
one position.**

### Where it breaks

A Slack channel read (`conversations.history`) returns top-level messages and
*not* the replies inside threads; a reply is only visible through
`conversations.replies(thread_ts)`. So "the events of this source, in source
order" is not one sequence — it is one sequence per thread, plus the top-level,
and **the set of threads grows on its own** as people reply.

[0009](0009.md) tried to fit this into one-stream-per-source by making each
thread a separate configured channel with its own key, cursor, and `meta`. That
is correct about the *cursor* (a thread does need its own) and wrong about the
*declaration*: threads appear faster than a config can be edited, so enumerating
them in config cannot work. The tell that the frame is wrong: the fix keeps
fighting it (see [0009](0009.md)'s amendment history and
[the discussion on its PR](https://github.com/kroeplex/botwatch/pull/6)).

### The generalisation

The Slack case is not special. Name the parts:

| Source | Sub-streams | Appear / vanish because… |
| --- | --- | --- |
| Slack channel | top-level + one per thread | someone starts a thread |
| git repository | one per ref (branch/tag) | a branch is pushed or deleted |
| GitHub repository | one per PR / issue timeline | a PR is opened or closed |
| Pub/Sub subscription | one (or one per ordering key) | a new key is seen |

In every case the source is **a set of independently-ordered sub-streams whose
membership changes over time, outside the caller's control.** That is the thing
to model directly.

## The model

**A source (one botwatch channel) is watched by one driver instance. The driver
presents the source as a set of *sub-streams*. Each sub-stream has a source
order and its own cursor. The set is dynamic: the driver discovers sub-streams as
it runs.**

A sub-stream is identified by a **sub-key** that is stable and source-native — a
Slack `thread_ts` (with a reserved sub-key for the top-level), a git ref name, a
PR number. The botwatch channel's `key` plus the sub-key identifies a position.

### The driver contract, restated

The five obligations from [0005](0005.md), generalised — the change is confined
to 1 and 3, and it is "per source" → "per sub-stream":

1. **Yield each new event exactly once per run, in source order *within its
   sub-stream*.** Cross-sub-stream order is unconstrained: a source with several
   active sub-streams has no single total order, and inventing one (e.g. by
   global timestamp) is a claim the source does not make.
2. **Stay open until the stream is closed, and release cleanly when it is.**
   Unchanged.
3. **Report state consistent with what was yielded — per sub-stream.** State is a
   **map of sub-key → cursor**, not a single cursor. Closed after yielding
   through position 3 of sub-stream A and position 1 of sub-stream B, `get_state()`
   describes exactly that. Rounding a sub-stream's cursor *back* replays (merely
   wasteful); forward drops — same rule as before, now per entry.
4. **Localise its own failures.** Unchanged — a failing source fails its own
   channel. (Whether one sub-stream's failure can localise *within* a channel is
   an open question below.)
5. **Interpret nothing.** Unchanged.

The interface shape from [0005](0005.md) is unchanged except that `DriverState`
is a sub-key→cursor map and each `Event` carries the sub-key it belongs to.

### State: a dynamic cursor map, and losing it is normal

- **State is `{sub-key: cursor}`**, and its membership is discovered, not
  declared. A first run has an empty map; the driver discovers the current
  sub-streams and starts each at its **start position** (below).
- **A sub-stream not seen this run keeps its cursor** (it may simply be idle) —
  bounding that growth is [0008](0008.md)'s `prune`, now applied per sub-stream.
- 🔑 **Losing the whole state file costs a re-read of each sub-stream's start
  window, never correctness.** This is a property, not an accident: it is what
  lets [kroebot drop the state file across an operator
  handoff](https://github.com/kroeplex/kroebot/blob/main/docs/issues/0005.md)
  rather than committing and carrying it, and it survives a crash or a lost disk.
  Nothing may depend on a cursor having persisted.

### Start position — per sub-stream, and it settles 0006's deferred key

When a sub-stream is first seen, where does its cursor begin? Three answers, and
the source/config picks:

- **`now`** — report nothing already in it; watch forward only. The safe default
  and the one [0006](0006.md) already assumes ("a first run reports no history").
- **`<window>`** — start a fixed span back (e.g. 24h), so a fresh run emits that
  much backlog and then continues. This is the case a Slack operator wants on
  startup, and it is exactly the `start` config key [0005](0005.md) **deferred
  until a caller genuinely needed it**. This is that caller.
- **`beginning`** — the whole sub-stream. Rarely wanted; named for completeness.

**This resolves the contradiction the [0009](0009.md) PR review surfaced.** The
old core said "start from now, report no history"; the Slack design wanted a 24h
window. They are not in conflict once start position is a per-sub-stream choice
with `now` as the default and `<window>` as an adopted option rather than a
forbidden one.

### The select, the two clocks, and departure — carried forward

[0006](0006.md)'s runtime is unchanged in shape and this RFC keeps it whole: one
run holds every channel open, returns when any produces an event, waits out the
**quiet timeout** when nothing does, and holds the **boarding window** open once
something arrives. The departure guards stand. The only refinement: a run
collects across **sub-streams within a channel** as well as across channels, so
the boarding window must cover a burst that spans several threads of one channel,
not only several channels.

### Ordering across a batch is emergent, not a mode

When a run has more than one event ready — replies in two sub-streams, or a
sub-stream and the top-level — it emits them **grouped by sub-stream** (each
sub-stream's ready events contiguous, in that sub-stream's order), because that
is the only order the model actually guarantees; there is no cross-sub-stream
order to honour.

⚠️ **This is what "yield each sub-stream in its own order" produces whenever a
batch accumulates — a fresh run, a run after the caller slept, a reconnect, a
burst — not a special "backfill mode."** A mode keyed on startup gets every other
batch wrong. A live tail with one event ready emits one event; nothing to group.

## What this carries forward, and what it changes

**Kept from [0005](0005.md):** the driver interface shape; obligations 2, 4, 5
verbatim; "one instance per channel, transport private"; `context` carries run
settings not the whole config; cleanup runs under cancellation; and — centrally —
**the conformance kit**, every criterion of which still applies, now phrased per
sub-stream where it spoke of "the source's order."

**Kept from [0006](0006.md):** the `select`, the quiet timeout, the boarding
window, and all the departure guards, whole.

**Changed:** obligation 1 (order is per sub-stream), obligation 3 (state is a
cursor map), and start position promoted from 0005's deferred `start` key to a
first-class per-sub-stream setting with `now` / `<window>` / `beginning`.

## Adjustments owed to issues this does not supersede

Left standing, because their substance is sound; each needs the sub-stream field
threaded through, and that is a smaller change than a rewrite:

- **[0003](0003.md) (state persistence & lifecycle)** — the atomic write and the
  reconfiguration lifecycle stand; the per-channel cursor becomes a per-sub-stream
  cursor **map**, and lifecycle now has a within-channel layer (a sub-stream
  discovered, gone idle, pruned).
- **[0004](0004.md) (JSONL envelope)** — the envelope gains a **sub-key** field
  so a consumer can tell which sub-stream an event belongs to; `id` stability is
  now per (channel, sub-key, event).
- **[0007](0007.md) (`inspect`)** — must render sub-streams under their channel,
  or "what am I watching?" is unanswerable for a source whose watch set grew on
  its own.
- **[0008](0008.md) (`prune`)** — must bound **sub-stream** growth within a
  channel (idle threads accumulate), not only retired channels.
- **[0001](0001.md)** — its Slack section still describes one-conversation-per-
  channel-including-threads; a forward-pointer to [0015](0015.md) is added there.

Per the tracker's nature, these are noted rather than edited here: an unbuilt
issue is discussion, and a contradiction between it and this RFC is tolerable
until someone builds one of them. Recording the owed change is what keeps it from
being rediscovered from scratch.

## Acceptance

*Each criterion names the implementation it falsifies.*

- **A source with two active sub-streams keeps two cursors, advanced
  independently.** Yielding through sub-stream A and closing does not advance B's
  cursor; the next run resumes B where it was and does not replay A.
  *Falsifies:* a single per-channel cursor, which advancing for A skips B (or
  the reverse) on resume.
- **Order holds within a sub-stream and is not asserted across them.** Events of
  one sub-stream arrive in source order; the runtime imposes no total order on
  events from different sub-streams beyond grouping them.
  *Falsifies:* a global-timestamp sort across sub-streams, which manufactures an
  order the source never had and which pagination cannot even reconstruct
  consistently.
- **A newly discovered sub-stream starts at its configured start position.** With
  `start: now` it reports nothing already present; with `start: <window>` it
  reports exactly the window and then continues; with either, a **lost state
  file** re-reads that same window and no more.
  *Falsifies:* starting a discovered sub-stream at `beginning` unconditionally
  (dumps all history), or at `now` unconditionally (silently drops the backlog a
  `<window>` caller asked for).
- **A burst spanning several sub-streams of one channel is one run.** Replies in
  three threads within the boarding window are reported by a single run, each
  thread in its own order.
  *Falsifies:* a run that departs after the first sub-stream drains, turning each
  thread into its own wake-up.
- **The conformance kit still passes for a single-sub-stream driver.** A source
  that genuinely has one order (a plain Pub/Sub subscription) is the degenerate
  case: one sub-stream, and every [0005](0005.md) criterion reads exactly as
  before.
  *Falsifies:* a model that only works for multi-sub-stream sources and breaks
  the simple ones.

## Open questions

- **Can a sub-stream's failure localise within a channel**, or does any
  sub-stream failure fail the whole channel? Obligation 4 localises per channel;
  whether a single unreachable thread should fail just that sub-stream (and let
  the rest report) is a finer grain that may not be worth it.
- **Does a caller ever need to name a sub-stream in config** — e.g. a specific
  thread whose parent predates the discovery window and so cannot be discovered?
  [0015](0015.md) says yes for Slack; whether that belongs in the core contract
  or stays a per-driver affordance is undecided.
- **What bounds the discovered set** — is `prune`'s idle-eviction ([0008](0008.md))
  enough, or does a driver need a "stop watching a sub-stream idle for N" of its
  own? Bears on the per-run poll cost, which grows with the live sub-stream count.
- **Whether the sub-key belongs in `get_state()`'s map only, or also on every
  `Event`** — it is on both above, but the envelope change ([0004](0004.md)) is
  where that is really decided.
