# 0014 — Notice change, not only arrival: edits and thread growth by re-scanning a window

**Status:** Open
· **Kind:** RFC
· **Parent:** <a href="0001.md" title="0001 — botwatch: a one-shot `select` over many event sources">0001</a>
· **Builds on:**
  <a href="0009.md" title="0009 — Add the Slack driver, one botwatch channel per conversation">0009</a>
· **Related:**
  <a href="0004.md" title="0004 — Emit events as JSONL with a stable envelope, and report channel failures on the same stream">0004</a>,
  <a href="0011.md" title="0011 — Add the GitHub driver for pull requests, reviews, and check runs">0011</a>

> botwatch as first built notices **arrival**: a message whose timestamp is later
> than the cursor. It is blind to **change** — an edit, a reply landing in a
> thread it has already scrolled past, a deletion — because none of those give
> the changed message a new timestamp, and the cursor only ever moves forward
> past timestamps already emitted.
>
> Three gaps that look separate are one gap. Edits are invisible. A reply to a
> thread whose parent has passed the cursor is invisible. And the workaround for
> the second — remember every thread forever and re-poll each — is the "no
> pruning" wart. All three are *"the source changed something we already passed,"*
> and one mechanism answers all three: each run, re-scan a bounded recent window
> and diff it against what was last seen, instead of only reading forward from a
> cursor.
>
> This issue proposes that mechanism, and settles the envelope question it forces
> — the one <a href="0009.md">0009</a> parked and handed to <a href="0004.md">0004</a>:
> an edit is a distinct **occurrence**, so `id` identifies an occurrence, not a
> resource.

## Background

<a href="0009.md">0009</a> already saw this coming. Its decision #3 names
`edited.ts` as the obvious revision marker and then stops short, because the half
of the question that matters — *is a changed message a new event, or the same
event again?* — is a promise the envelope makes to **every** channel type, not a
property of Slack, and so is owed by <a href="0004.md">0004</a>. Its decision #1
— poll `conversations.history`/`.replies`, or take a Socket Mode push — was left
"to decide deliberately." Both are now decidable, because the Slack API's actual
behaviour is no longer a guess.

### The two facts that decide this

Verified against the live Slack Web API:

1. **An edit mutates in place.** The message keeps its original `ts` — its
   identity, and its position in the timeline — and gains an `edited` object
   whose own `ts` is *when* the edit happened; the `text` now holds the new
   words. Slack reports *that* a message changed and *when*, never what it said
   before.

2. **`oldest` bounds creation, not change.** `conversations.history` and
   `.replies` filter on the message `ts` — when it was posted. An edit, a new
   reply, a reaction, a deletion: none move that `ts`. So a read bounded
   `oldest = <last cursor>` never returns anything created before the cursor,
   however recently it changed. **Reading forward from a cursor is structurally a
   "what has *arrived*" query; it cannot be made a "what has *changed*" query** —
   there is no modification-time filter to make change-detection cheap.

And the fact that turns those two from a dead end into a design:

3. **A window read carries the current state.** The *same* message, read within an
   `oldest` that predates it, comes back bearing its current `edited.ts`,
   `reply_count`, and `latest_reply`. One `conversations.history` pass over a
   window therefore reveals, for every message in it, both whether it was edited
   (its `edited.ts`) and whether its thread has grown (its `latest_reply`) — the
   two signals the mechanism below runs on.

### The scenario this is really for

Someone posts, then twenty seconds later fixes a typo, hoping you catch the fix
before you answer. Among people this editing dance is a real side channel, and
for kroebot to take part, botwatch has to (a) wait long enough to see the edit
and (b) notice it at all. The waiting is already handled — the boarding window
(<a href="0006.md">0006</a>) is exactly "once the first event lands, keep
collecting for a while," and setting it to ~1m buys the leeway. The *noticing* is
what is missing, and what a re-scan supplies: within that same minute, the run
re-reads the window, sees the `edited.ts` appear, and emits the edit — so kroebot
receives post-then-edit together, deliberates on the settled text, and answers a
beat later like a person rather than firing on the keystroke.

## The mechanism: a windowed re-scan

Each run, per watched conversation:

1. **Re-read the window** — `conversations.history` with `oldest = now − W`, the
   whole recent window, not `oldest = cursor`. `W` is the horizon of change
   botwatch promises to catch.
2. **Diff against the snapshot** the driver persisted last run — a small record
   per message in the window: its `ts`, its `edited.ts` (or none), its
   `latest_reply` (or none), and, for a thread being followed, its reply cursor.
   - `ts` unseen → **arrival** → a `message` event.
   - `ts` seen, `edited.ts` changed or newly present → **edit** → an `edit` event.
   - `latest_reply` advanced or newly present → the thread grew → fetch
     `conversations.replies` since that thread's reply cursor, emit each new
     reply, advance the reply cursor. (A parent seen *before* it had any reply is
     now caught the moment it grows — no reliance on it already bearing replies.)
   - *(optional, see decisions)* `ts` previously seen but absent now → **deletion**.
3. **Advance the snapshot**, and **drop entries older than `now − W`** — which is
   the whole of pruning: threads and messages fall out of attention by aging out
   of the window, with no per-thread bookkeeping that grows without bound.

The state stays opaque to the core (<a href="0003.md">0003</a>): the whole
snapshot lives in the driver's block. It is bounded by the window's size, not by
how long the process has run.

### The envelope consequence: `id` identifies an occurrence

An edit has to be a *different* event from the post, or a consumer deduplicating
on `id` (<a href="0004.md">0004</a>) drops it as a replay — which is precisely the
trap 0009's acceptance called out. So this issue proposes the answer 0004 owed:

**`id` identifies an occurrence, not a resource.** A post is one occurrence; its
edit is another; a second edit, a third. Each carries an `id` that folds in the
mutation's own timestamp — a post is `<ts>`, its edit is `<ts>@<edited.ts>` — so
both survive dedup, and `kind` (`message` vs `edit`) says which is which. The
edit's payload carries the new message and points back at the original `ts`, so a
consumer can tie the two together without having kept the original.

This is deliberately the opposite of treating the message `ts` as *the* identity
(natural, since it doubles as the cursor) — that choice is what would silently
drop every edit. <a href="0011.md">0011</a> meets the same fork from the GitHub
side (a review that changes state, a re-requested review) and should resolve the
same way, since the promise is the envelope's, not any one source's.

### Why re-scan (pull), not Socket Mode (push)

There are two ways to learn a message changed. **Pull:** re-scan the window and
diff — this proposal. **Push:** Socket Mode or the Events API delivers
`message_changed`, `message_deleted`, and thread replies as they happen. Push
catches a change of *any* age and is cheap per change — but it needs a listener
that is *always on*, holding a socket or a public endpoint. That is a daemon, and
**botwatch is a one-shot `select` — wake, drain, leave** (<a href="0001.md">0001</a>).
The windowed re-scan fits that shape exactly; a push listener does not. If a true
push source is ever wanted it is a different tool with the shape of
<a href="0012.md">0012</a>'s Pub/Sub driver, not this one.

The cost of the pull choice is the honest boundary `W` draws: a change to
something *older* than `W` is not caught, by design. That matches what the
watcher is for — the last-second edit, the reply to a still-recent message — and
not "notice an edit to a week-old post," which no polling watcher can afford.

### What this changes about the Slack driver as built

The first cut of the Slack driver reads forward from a cursor and, for threads,
keeps a per-thread reply cursor discovered when a parent is *first seen already
bearing replies*. That has two documented gaps — an edit is never seen, and a
thread that gains its first reply after its parent passed the cursor is never
followed — and one wart, the per-thread map that only grows. The window model
subsumes all three: edits and late-first-replies both surface from the re-scan,
and pruning is the window's trailing edge. The per-conversation cursor stays for
arrival (it is still the cheap, exact "what's new" signal); the snapshot is added
beside it for change.

## Scope

Amends the [Slack](0001.md#slack) driver of <a href="0009.md">0009</a>, and
resolves the envelope question <a href="0009.md">0009</a> handed to
<a href="0004.md">0004</a> (what `id` identifies) in the direction of
*occurrence*.

**Out of scope:** what an edit *means* to the agent — whether kroebot treats it as
actionable, or as a correction to something already acted on — which is the
consuming agent's call, not botwatch's; the same change-detection for the git and
GitHub drivers (<a href="0010.md">0010</a>, <a href="0011.md">0011</a>), which
inherit the envelope decision here but render their own mutations.

## The rules this implements

- **A change to a watched message within the window is an event.** An edit is an
  `edit`; a new reply is a `reply`; both reach the same stream as arrivals do.
- **`id` identifies an occurrence.** The post and each of its edits carry distinct
  `id`s; a consumer deduplicating on `id` sees every one.
- **`W` is the promised horizon of change,** and the honest limit: nothing older
  than `W` is watched for change. Pruning is `W`'s trailing edge, not a separate
  mechanism.
- **The snapshot is opaque driver state** (<a href="0003.md">0003</a>), bounded by
  the window, never by uptime.
- **An edit's `ts` is the source's, not the observation's.** An `edit` event's
  time is `edited.ts`; a replay renders identically.

## Acceptance

*Each names the implementation it falsifies.*

- **An edit within the window is emitted, once, as its own event.** A message
  reported on one run and edited before the next produces, on the next run, an
  `edit` event whose `id` differs from the original and whose payload carries the
  new text and the original `ts`. *Falsifies:* re-sending the message under its
  original `ts` as `id` (a conforming consumer drops it as a replay), and never
  emitting the edit at all (the cursor-only reader — silent, and the current
  behaviour).

- **A late first reply is caught.** A parent seen with no replies, then replied to
  while still inside `W`, has its reply reported. *Falsifies:* discovering threads
  only from a parent already bearing replies when first read — which never learns
  of this thread.

- **Attention is bounded by the window, not by uptime.** A thread that falls
  outside `W` leaves the snapshot; the state a long-lived channel carries is
  bounded by the window's contents. *Falsifies:* a per-thread cursor map that
  accumulates every thread ever seen.

- **A change older than `W` is out of scope, not a bug.** An edit to a message
  older than `now − W` is not reported, and this is documented, not silent
  breakage. *Falsifies:* claiming to catch edits generally, which sets an
  expectation the pull model cannot meet.

- **Arrival is unregressed.** New top-level messages and their ordering are
  reported exactly as before the snapshot was added. *Falsifies:* a re-scan that
  re-emits already-reported arrivals as new because it stopped tracking the
  forward cursor.

## Decisions this issue owes

1. **`W`, and its relationship to the two clocks.** `W` is a change horizon, not a
   departure clock — distinct from the quiet timeout and the boarding window
   (<a href="0006.md">0006</a>), which decide when to *leave*. Is `W` a single
   default, a per-channel option, or derived (e.g. "the boarding window plus a
   margin" for the edit dance, versus "an hour" for catching a reply to a
   still-recent message)? They are different jobs and may want different `W`.

2. **Re-scan every poll, or a cheaper cadence.** Re-reading `W` of history on
   every `poll_interval` is wasteful on a busy channel. The likely shape is a
   hybrid: the cheap forward read (`oldest = cursor`) every poll for *arrival*,
   and a full window re-scan on a slower cadence for *change*. Worth pinning down,
   with the cost stated rather than left implicit.

3. **Deletions and reactions — reported or noise?** A deletion is detectable (seen
   last scan, absent now); a reaction changes a message without touching `text`.
   0009's decision #3 left "worth reporting at all?" to Slack's call. An edit is
   clearly worth it; a deletion probably; a reaction likely noise for this source
   — but this should be decided, with the `kind` each carries.

4. **Edits to replies.** An edit to a message *inside* a thread is the same
   phenomenon one level down, and needs the snapshot to remember replies'
   `edited.ts`, not just the parent's `latest_reply`. In scope for the model;
   worth stating whether v1 implements it or defers it.

5. **Whether this retires 0009's "a thread is its own channel."** 0009 modelled a
   thread as its own botwatch channel (its own config entry). The as-built driver
   already departed from that toward auto-discovery within one channel; the window
   model deepens that departure. Does the per-thread-channel option still earn its
   place for the caller who wants to watch exactly one known thread, or does
   auto-discovery within the conversation subsume it?
