# 0015 — Watch many sources in one blocking run, each carrying its own state

**Status:** Open
· **Kind:** Enhancement
· **Parent:** <a href="README.md" title="Issues">Issues</a>

> An agent that reacts to outside activity, such as chat messages or review
> comments, usually polls. It wakes on a timer, checks every source, and mostly
> finds nothing. Each wake costs a full turn, and each event waits up to a whole
> interval before the agent sees it.
>
> `botwatch` replaces the poll with a block. One run waits on every source at
> once, writes what happened as JSON lines, and exits. The caller acts on that
> output and runs it again. Everything botwatch remembers between runs lives in
> a state file the caller holds.
>
> The PRs that build this update it wherever they find something better.

## Background

```text
# polling (sketch)
every few minutes:
    wake up                          # a full turn, whatever it finds
    for each conversation:
        fetch recent messages
        compare with what I saw last time
    nothing new?  go back to sleep

# with botwatch (sketch)
forever:
    events = botwatch --config watch.yaml --state state.yaml   # blocks
    act on events
```

Under botwatch, an idle stretch costs one blocked process, and a burst of
messages costs one wake rather than one per message. The agent keeps no cursors
of its own.

## Proposal

### Sources

A **source** watches one thing and is an async generator of **updates**. The
thing might be one Slack conversation's top level, one Slack thread, or later
one pull request.

```python
@dataclass(frozen=True)  # sketch
class Update[StateT, EventT: Event]:
    events: tuple[EventT, ...]
    """Zero or more events, in source order."""

    state: StateT
    """The source's full state after these events."""
```

- **Creation.** You create a source by calling its generator function with its
  previous state, or with none to start from now. Its first update is always a
  checkpoint: no events, just its starting state. That way a run in which
  nothing happens still records where the source began.
- **Lifetime.** A source yields forever. Its consumer decides when to stop and
  closes it. Closing is the only shutdown signal, and the source's cleanup runs
  on the way out. A source fails by raising.
- **State.** A source's state is whatever it needs to resume and to detect
  change: a position now, and later a snapshot of recent messages. Each source
  type defines its own state model, and the rest of botwatch stores it without
  looking inside.
- **Updates are handled whole.** The consumer writes an update's events, then
  keeps its state. The state always travels with the events it accounts for, so
  there's no separate step that reads state after closing and could get it
  wrong.

Inside, a source is a poll loop around a pure step,
`(state, observation) → (state, events)`. All change detection lives in that
step, where it's tested without I/O.

- **Poll interval.** Each source sets its own in its config. A push source has
  none.
- **Rate limits.** Retries of transient API errors (rate limits, server errors,
  network) live in the API client underneath. So does any future sharing of an
  API's rate budget between sources. A source that raises has hit something
  persistent.

**One source watches one thing.** Watching a Slack channel and three of its
threads means four sources. A source's identity, its **key**, is derived from
what it watches: `slack:C0123456789` for a conversation's top level,
`slack:C0123456789/1785600000.000200` for a thread. So a key can never point at
another source's state.

Slack's history of a conversation doesn't include thread replies. A reply in a
thread with no source of its own therefore surfaces nowhere; the caller adds a
source for each thread it cares about.

Several sources may call the same API redundantly. Batching those calls is an
implementation concern and never changes this model.

### Events

Each kind of event is a model with a `type` literal, such as
`slack.message_posted`. The literal is namespaced by its source type, or by
`botwatch` for events the run itself emits. The set of types is closed: the
union of those models. Output and state are validated against that union, so
an unknown or colliding type fails validation instead of passing through.

Every event carries these fields, plus its type's own:

| Field | Meaning |
| --- | --- |
| `type` | Which event model this is. |
| `id` | This occurrence, unique within its source and stable across replays. Callers dedupe on `(source, id)`. |
| `time` | When it happened at the source. |

Slack's event models are botwatch's own and carry what an agent needs:
conversation, message and thread `ts`, author and text. Slack's API response
objects stay internal.

When a source fails, the run emits a `botwatch.source_failed` event for it,
with a fresh `id` each time.

### The run

One `botwatch` invocation:

1. reads the config, and the state file if it was given one. Either failing
   validation exits non-zero before any source is created;
2. creates every configured source from its stored state;
3. selects over all of them, using turbopipes' `aselect`, and writes each
   update's events to stdout as JSON lines, flushed per line;
4. departs on two clocks: it waits up to `quiet_timeout` for the first update
   with events, then exactly `linger` more, counted from that update;
5. closes every source, writes the state file atomically, and exits.

A failed source is reported and keeps its previous state. It stays down for the
rest of the run. Its failure event, like every `botwatch.*` event, never counts
toward departure.

A run with nothing to report waits out the full quiet timeout, whether its
sources are quiet or failing. A caller looping on botwatch is therefore paced
by that timeout rather than spinning.

Delivery is at-least-once. The state is written at exit, so after a crash the
next run replays whatever the crashed run had already written. Callers dedupe
on `(source, id)`.

### Stages

A stage wraps a source and is itself a source.

The first stage is `exclude`. It drops the events that match the caller's
rules, for example to skip the caller's own posts. Slack rules can match the
author's user ID, a bot ID, a custom username, or a text regex. The stage keeps
each update's state, so excluded messages still advance the source. An update
whose events are all excluded becomes a plain checkpoint and doesn't count
toward departure.

A stage that needs memory of its own keeps it in the update's state, beside its
source's state (see settle, below).

### Config, state and output

```yaml
# config (sketch); JSON is YAML, so either works
quiet_timeout: 55m
linger: 5s
sources:
  - type: slack
    conversation: C0123456789
    exclude:
      - user: U0123BOT
  - type: slack
    conversation: C0123456789
    thread: '1785600000.000200'
```

```yaml
# state (sketch): written by botwatch, one entry per configured source
slack:C0123456789:
  type: slack
  after: '1785633161.000000'
slack:C0123456789/1785600000.000200:
  type: slack
  after: '1785600123.000100'
```

```json
{"source": "slack:C0123456789", "event": {"type": "slack.message_posted", "id": "1785633376.000000", "time": "2026-08-02T01:16:16.000Z", "conversation": "C0123456789", "ts": "1785633376.000000", "thread_ts": null, "user": "U0456ABC", "text": "..."}}
```

Every config, state and output shape is a closed, typed model. Where a shape
varies by source type, it's a union discriminated on `type`.

When botwatch writes the state file, it drops entries for sources that are no
longer configured. A source removed and later re-added therefore starts from
now; a caller keeps its place by keeping the source configured.

The Slack token comes from the environment.

### Rollout

Each step is a PR that is useful on its own:

1. **Slack sources as a library.** Create one for a conversation or a thread,
   and `async for` over it.
2. **The orchestrator.** Select over sources with the two clocks.
3. **The `botwatch` command.** Config in, JSON lines out, no state yet. This is
   already useful as "block until the next message".
4. **The state file.** This step also declares the design spec below.
5. **`exclude`.**
6. **A descriptive design doc**, `docs/design.md`, written from the code once a
   real agent loop has run on botwatch for a while. This issue then resolves
   into it.

### Planned extensions

The contracts above are shaped so these need no redesign:

- **Edits and reactions.** Each poll re-scans a recent window and diffs it
  against a snapshot kept in the source's state. It emits
  `slack.message_edited`, `slack.reaction_added` and so on.
  - Slack keeps a message's `ts` when it's edited, and its reads filter by
    creation time. A forward-only position therefore can't see an edit, but a
    window re-scan can.
  - Events gain a `subject`: what they're about, such as a message's `ts`. A
    post and its edits share a subject but not an id.
  - The same re-scan can emit `slack.thread_replied` when a message's latest
    reply moves, so a caller can add a source for that thread.
- **Settle.** A stage that holds a new subject for a configurable time, counted
  from its first event in source time. It then emits the subject once, with
  early edits applied.
  - The held events live in the state. A run that ends mid-hold delays the
    event to the next run rather than losing or splitting it.
  - An update may later carry a "holding until" hint, so the run can choose to
    wait for a held event.
- **Restarting a failed source** within the run, from its last state, after a
  backoff.
- **More source types:** GitHub pull requests, a git repository's refs, a local
  file that other tools append to, and a Pub/Sub subscription fed by Slack's
  Events API.
- **Exit codes** that distinguish events, timeout and error.
- **A reason on each event** saying why it should wake the caller, such as a
  direct mention.
- **Filter profiles**, e.g. direct mentions only, outside working hours.
- **Shared fetching.** First, batching sources within one process that hit the
  same API. Later, a shared consumer per bot identity.

### How Slack can be watched

| Mechanism | Fit |
| --- | --- |
| `conversations.history` / `conversations.replies` (Web API, pull) | **Used.** It's the only option that also covers the gaps between runs, because Slack holds the backlog. Internal apps get about 50 requests a minute per method. |
| Events API over HTTP (push) | Needs an always-on public endpoint and keeps no backlog. Viable behind a queue: the endpoint publishes to Pub/Sub, which holds events between runs. |
| Socket Mode (push over a WebSocket) | Events that arrive while no run is connected are lost. Slack also spreads one app's events across its open connections, so concurrent runs for one bot would each miss some. Fits only an always-on helper. |
| `search.messages` | Needs a user token, its index lags, and its date filters only go down to the day. |
| Real-time Search API | With a bot token, each call needs an action token taken from an incoming message event, which a polling run never receives. |
| RTM API, outgoing webhooks | Legacy, and unavailable to current Slack apps. |

### Design spec (proposed)

One property here should bind the code for as long as botwatch exists:

> **Where a run ends never changes what is emitted.** Given the same
> observations from the sources, successive runs emit the same sequence of
> source events, `botwatch.*` events aside, however each run ends: timeout,
> linger, any later exit rule, or a crash. A crash may repeat events but never
> skips one.

The gap between two runs is a stretch in which nothing is observed. Several
changes made inside it can therefore surface as one, just as they would with a
slower poll.

The state-file PR declares the spec, with a test that replays scripted
observations under different exit points.

### Non-goals

- **A daemon.** botwatch runs, waits and exits. Any always-on helper sits
  outside it.
- **One run watching as several identities.** Each identity, such as each Slack
  token, gets its own runs.
- **Interpreting what an event means.**
- **Exactly-once delivery.**

### Open questions

- Should a run wait for a held (settling) event, and if so, for how long at
  most?
- The exit-code values.
