# 0015 — Slack driver: threads are discovered sub-streams

**Status:** Open
· **Kind:** RFC
· **Parent:** <a href="0001.md" title="0001 — botwatch: a one-shot `select` over many event sources">0001</a>
· **Supersedes:**
  <a href="0009.md" title="0009 — Add the Slack driver, one botwatch channel per conversation">0009</a>
· **Builds on:**
  <a href="0014.md" title="0014 — A watched source is a dynamic set of ordered sub-streams">0014</a>

> The Slack driver was the source the whole design was pressure-tested against,
> and it is the one that broke the old frame. [0009](0009.md) modelled a thread
> as its own botwatch channel, named in config — which cannot work, because a
> channel's threads are opened by everyone posting in it, constantly, and a
> config cannot be edited that fast.
>
> Under [0014](0014.md)'s model the driver is simple to state: **one botwatch
> channel watches one Slack channel (or DM); its sub-streams are the top-level
> conversation and one per thread; the driver discovers the threads as it runs.**
> A thread's cursor lives in state, not config, exactly like every other
> sub-stream.
>
> This RFC supersedes [0009](0009.md). Its per-thread-cursor instinct was right
> and is kept; its per-thread-*config-entry* mechanism is dropped. It also records
> two Slack API behaviours, confirmed against the live workspace, that a naive
> implementation gets wrong.

## Background

### The thread trap (why threads must be watched at all)

```text
#dev  ├─ 09:00  "shipping the parser today"          ← top-level
      ├─ 09:02  "kickoff thread"                     ← top-level, has replies
      │           ├─ 09:05  "taking the lexer"       ← reply: NOT in the
      │           └─ 09:31  "lexer's green"          ←   channel-level read
      └─ 11:40  "parser's merged"                    ← top-level
```

`conversations.history` returns the three top-level messages and **not** the two
replies. Replies are reachable only through `conversations.replies(thread_ts)`.
So a source's events are one sub-stream per thread plus the top-level — precisely
[0014](0014.md)'s shape — and the thread set grows on its own.

### What [0009](0009.md) got right and wrong

Right: a thread needs **its own cursor**, independent resume, and isolation. All
of that is [0014](0014.md)'s per-sub-stream state, kept intact. Wrong: that the
cursor implies a **config entry**. It does not — the cursor lives in state and
the sub-stream is discovered. Dropping the enumeration is the whole point.

## The driver

**One botwatch channel → one Slack channel or DM (a *container*). Its sub-streams
are the top-level (a reserved sub-key) and one per thread (`thread_ts` as
sub-key). Threads are discovered from top-level messages that have replies, or
named explicitly for the case discovery cannot reach.**

### Two config controls

- **`watch_threads: auto` (default)** — when a top-level message in the watched
  window has, or grows, replies, the driver picks up that thread as a sub-stream
  and watches it. This is the ordinary case: watch a channel and everything said
  beneath it, naming no thread.
- **`threads: [<ts>, …]`** — an explicit list, and **structural, not a
  convenience.** `conversations.history` returns a thread's parent at the
  parent's *original* timestamp, so a thread whose parent predates the watch
  window is **invisible to discovery however far back the window reaches**. A
  reply this morning to a three-week-old message can be watched only by naming
  its thread. Auto-discovery and the explicit list compose.

A container may also want its threads and **not** its top-level chatter (the
`#dev-prs` case: an operator watches its own announcement threads, not every
operator's announcements). Expressed as `watch_top_level: false` alongside a
`threads` list and/or `watch_threads: auto`. *(This subsumes [0009](0009.md)'s
bare-thread-as-its-own-channel form; see open questions.)*

### Two Slack behaviours a naive driver gets wrong

Both confirmed 2026-08-24 against the live workspace while building
[`slack_read --all`](https://github.com/kroeplex/kroebot/pull/47):

- 🔑 **`conversations.replies` repeats the thread parent at the top of *every*
  page.** Paginating a thread and concatenating pages double-counts the parent
  once per page. The driver must dedupe (the parent's `ts` is its identity).
- 🔑 **When limited, `conversations.replies` returns the *newest* replies first,
  then walks its cursor *backward*.** So page order is not chronological, and a
  driver that treats "fetch order" as "source order" yields a thread's replies
  scrambled. Source order within a thread is `ts` ascending; the driver sorts to
  it, it does not assume the API delivered it.

*(`slack_read --all` handles both by deduping on `ts` and re-sorting per method —
the same normalise a driver needs, verified byte-for-byte against a single large
page down to one message per page.)*

### Start position and ordering come from the core

- **Start position is [0014](0014.md)'s per-sub-stream setting.** The common
  Slack operator start is `start: 24h` (or similar) on the container, so a fresh
  run — and a run after a lost state file — emits the last day across the
  top-level and every discovered thread, then continues. `start: now` is the
  no-backlog default.
- **A newly discovered thread backfills from its start.** Because discovery sees
  the parent inside the window, a discovered thread naturally backfills from the
  parent forward. An **explicitly named** thread whose parent is far older is the
  case where "how far back" is a real choice — see open questions.
- **Grouped-by-sub-stream emission** ([0014](0014.md)) means a burst across
  several threads reports each thread's replies contiguous, not interleaved by
  global timestamp — which Slack's own order does not define across threads
  anyway.

### Rendering Slack's mutations

Edits, deletions, and reactions are changes to a message that already has an
`id`, so they meet the envelope's `id`-stability question — owed by
[0004](0004.md), unchanged by this RFC. What is Slack's to decide: `edited.ts`
marks a revision; whether a deletion or a reaction is worth an event or is noise
for this source; and what `kind` each carries. Deferred to the same place
[0009](0009.md) deferred it.

## What "what am I watching?" now means

The config says *this container, auto-watch on, plus thread X*; the **state**
holds a cursor for the top-level and one per discovered-or-named thread. The full
watch set is therefore a state question, answered by
[`inspect`](0007.md) (which [0014](0014.md) notes must render sub-streams) or the
state file — not the config. The watch set is *supposed* to grow on its own.

## Acceptance

*Beyond [0014](0014.md)'s conformance kit, which this driver passes as a
multi-sub-stream source.*

- **Auto-watch reports a thread's replies with no thread named.** A reply to a
  top-level message in the window is reported under a sub-key distinct from the
  top-level, with `threads` empty; `watch_threads: off` stops new pickups and
  leaves the top-level cursor untouched.
  *Falsifies:* discovering threads but folding them into the top-level cursor, so
  a resume after a reply skips a top-level message or the reverse.
- **A named thread with an out-of-window parent is watched.** A `threads` entry
  whose parent predates the window is watched and its new replies reported.
  *Falsifies:* implementing `threads` as a filter over discovered threads, which
  can only narrow the discovered set and never reach what discovery cannot see.
- **A paginated thread is deduped and ordered.** Reading a thread across several
  pages yields each reply once, in `ts`-ascending order, with the parent counted
  once.
  *Falsifies:* concatenating `conversations.replies` pages in fetch order, which
  duplicates the parent and scrambles the replies (both confirmed live).
- **`watch_top_level: false` watches only the named/auto threads.** A container
  so configured reports thread events and no top-level messages.
  *Falsifies:* a driver that always watches the top-level, which cannot express
  the `#dev-prs` operator's "my announcement threads only."

## Open questions

- **Backfill depth for an explicitly named thread** — its whole history, or only
  within the window? The lean is the whole thread (you named it because you want
  it), probably configurable; a discovered thread differs (its parent is in the
  window), so the two may not want the same default. ([0014](0014.md) open
  question on start windows.)
- **Whether `watch_top_level: false` + `threads` fully subsumes a bare-thread
  channel**, or whether pointing a botwatch channel straight at a thread is still
  worth having as a shorthand. Same question [0014](0014.md) raises about naming
  a sub-stream directly.
- **Poll cost of a large thread set.** Slack has no channel-wide "recent replies"
  read, so each watched thread is its own `conversations.replies` call per run;
  the set grows on its own, so a channel with dozens of live threads fans out
  dozens of reads per run. Bears on [0006](0006.md)'s boarding window (all must
  complete in a run) and on rate limits (the retry/backoff
  [`slack_read` gained](https://github.com/kroeplex/kroebot/pull/47) is the
  per-request half; a bound on the *set* is [0008](0008.md)'s `prune` or a
  driver-level idle cutoff).
