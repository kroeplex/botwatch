# 0007 — Add `botwatch inspect` for reading a state file's health out of band

**Status:** Open
· **Kind:** Feature
· **Parent:** <a href="0001.md" title="0001 — botwatch: a one-shot `select` over many event sources">0001</a>
· **Builds on:**
  <a href="0003.md" title="0003 — Persist run state atomically, with a channel lifecycle that survives reconfiguration">0003</a>
· **Feeds:**
  <a href="0008.md" title="0008 — Specify `prune` and bound retired-channel growth">0008</a>
· **Related:**
  <a href="0002.md" title="0002 — Load the config and enforce the channel key contract">0002</a>

> A source that has quietly broken and a source where nothing is happening look
> identical from outside a `botwatch` run: both exit `0`, both leave the
> recorded position alone, and both report nothing. A Slack token that expired
> on Tuesday and a quiet week are the same picture.
>
> The information that separates them exists — it is written into the state file
> every run — but callers are explicitly told not to parse that file, because
> its schema is `botwatch`'s business and parsing it would make every future
> schema change a breaking one.
>
> So there needs to be a sanctioned reader: a read-only subcommand that answers
> "how long has this been here", "has it ever done anything", and "is it broken,
> and since when" without the caller ever opening the file.

## Background

The state file records, per channel, when the key was first seen, when it last
produced an event, and — if it is failing — what the error was, when it was last
observed, and when the current streak began. `inspect` renders that, adding the
durations a caller would otherwise compute *(sketch)*:

```console
$ botwatch inspect state.yaml
created: 2026-07-28T09:00:00Z
updated: 2026-08-02T01:12:44Z
age: 136h12m
channels:
  dev-slack:
    created: 2026-08-01T22:10:00Z
    last_event: 2026-08-02T01:12:41Z
    idle: 24h0m
    last_error: null
  upstream-main:
    created: 2026-08-01T22:10:00Z
    last_event: null
    idle: null
    last_error: "ssh: connect to host github.com: timed out"
    last_error_at: 2026-08-02T01:05:31Z
    failing_since: 2026-08-01T23:41:12Z
    failing_for: 25h31m
  old-experiment:
    created: 2026-07-28T09:00:00Z
    retired: 2026-08-01T18:00:00Z
    last_event: 2026-08-01T17:52:10Z
    last_error: null
```

`upstream-main` is the case the whole subcommand exists for. It has **never**
produced an event and it is **also** broken. Without `last_error` beside it, it
is indistinguishable from a channel nobody has spoken in — and because
`last_event` is `null`, there is nothing to date the breakage from either, which
is why "broken since when" has to be a recorded field rather than an inference.

`old-experiment` shows the other rule. It is retired — nobody is watching it —
so it renders the facts that were **recorded** about it (`last_event`,
`last_error`, and a frozen `failing_since` when one is set) and omits the ones
**computed against now**. "How long has it been quiet" means nothing for a
channel nothing is watching, so `idle` is absent; `failing_for` is absent for the
same reason.

**What `mtime` cannot do**, and why this is not just `ls -l`: mtime is updated by
every run including runs that found nothing, it is destroyed by copying the file,
and it says nothing at all about individual channels.

## Scope

Implements [Inspecting state](0001.md#inspecting-state) of [0001](0001.md).

**Out of scope:** removing anything — `inspect` never writes, and the removal
tool is [0008](0008.md); the schema itself and the rules that decide what those
fields *contain* ([0003](0003.md)).

## The rules this implements

- **`inspect` is read-only and never writes.** ([Inspecting state](0001.md#inspecting-state))
- **It is the sanctioned reader.** Where callers legitimately need facts about a
  state file, this is how they get them, rather than parsing a file whose schema
  is `botwatch`'s business. ([Format and audience](0001.md#format-and-audience))
- **It reports the recorded fields** — `created`, `updated`, `last_event`,
  `last_error`, `last_error_at`, `failing_since`, `retired` — and **computes**
  `age` from the top-level `created`, `idle` from `last_event`, and
  `failing_for` from `failing_since`.
- **Retired channels render their recorded facts but not the computed ones.**
  `idle` and `failing_for` are omitted; a frozen `failing_since` is still shown
  when set, because it records when something happened rather than how long ago
  it was.
- **`idle` is `null` when `last_event` is `null`** — a channel that has never
  fired has no idle time, which is different from an idle time of zero.
- **YAML by default, `--json` for programmatic consumers**, per the same
  input-generous/output-plain asymmetry as everywhere else.

## Acceptance

*Each criterion names the implementation it falsifies. A criterion that the
design's rejected alternative also passes is not coverage.*

- **`inspect` never writes — and still reads.** After running `inspect`, the
  state file's bytes and its mtime are both unchanged. `inspect` succeeds
  against a file whose containing directory is read-only, and against a file
  opened without write permission. In the same test it produces the expected
  report.
  *Falsifies:* an implementation that round-trips the YAML — parse, re-emit,
  write back — "normalising" it in passing, which is invisible to any test that
  only checks the report; one that opens the path `r+`, which works everywhere
  until the directory is read-only; and a no-op, which would satisfy the
  write-nothing half while answering nothing.
  *(This rule had no criterion in [0001](0001.md).)*

- **Retired channels render recorded facts and omit computed ones.** A retired
  channel whose state carries a non-null `last_event`, a frozen `last_error`,
  `last_error_at` and `failing_since` renders **all four** plus `retired`, and
  renders **neither** `idle` nor `failing_for`. A live channel with the same
  field values renders `idle` and `failing_for`.
  *Falsifies:* rendering every channel identically, which shows a meaningless
  "how long since it was last quiet" for a channel nothing is watching; and
  abbreviating retired channels to just `retired`, which drops exactly the facts
  a caller re-adding a channel most wants — given that the case retirement is
  built for is a channel removed by accident or by a config-generation bug. Both
  halves are needed; each alone is passed by one of the two wrong renderings.
  *(This rule had no criterion in [0001](0001.md).)*

- **Broken-and-silent is distinguishable from merely silent.** A channel with
  `last_event: null` and a non-null `last_error` reports `idle: null`, the
  error, `last_error_at`, and a `failing_for` computed from `failing_since`. A
  channel with `last_event: null` and no error reports `idle: null` and
  `last_error: null` and no `failing_*` fields at all.
  *Falsifies:* deriving "broken since when" from `last_event`, which yields no
  answer at all in the first case and dates a channel that was genuinely quiet
  for a week and broke this morning a week early.

- **`--json` and the default YAML carry the same facts.** For the same state
  file, both renderings contain the same set of channels and the same field
  values; the JSON parses with a plain JSON parser and contains no YAML-only
  constructs.
  *Falsifies:* a `--json` mode that is a separate, thinner projection — the
  usual way these drift is that a field added to one is forgotten in the other.

- **A channel with no computed answer says so rather than guessing.** `idle` is
  `null`, not `0`, and not omitted, when `last_event` is `null`.
  *Falsifies:* rendering `0` (which reads as "active this instant") or omitting
  the key (which makes a never-fired channel indistinguishable from an older
  schema that lacked the field).

## Decisions this issue owes

1.  **Duration rendering and rounding.** `136h12m` and `24h0m` are the shapes in
    the sketch; the grammar, the unit ceiling (hours, never days), and the
    rounding are unstated. Whatever is chosen **must** match the config's
    duration syntax, which [0002](0002.md) owes as a decision of its own, so
    that a caller reads and writes the same language. The two have to be settled
    together or one of them re-derives a grammar the other already chose — which
    is why 0002 is a `Related:` issue in this one's header rather than only a
    mention here.
2.  **A `created`, `last_event` or `failing_since` in the future.** Restored
    backups and clock skew both produce this. Rendering a negative duration
    silently is the wrong answer; the alternatives are clamping to zero or
    saying so explicitly.
3.  **What `inspect` does with a state file it cannot interpret** — an
    unrecognised `version:`. It should almost certainly still report what it
    can, since a caller reaching for `inspect` at that point is debugging, but
    that follows [0003](0003.md)'s answer on **state files written under an
    older schema** ([question 2](0001.md#open-questions)) and should be settled
    with it.
