> This is the part of `botwatch` that decides *when a run ends*, and it is the
> part the design says is most likely to be got wrong by a reimplementation.
>
> Both obvious answers fail. Return as soon as something happens, and a burst of
> ten messages costs ten separate runs — with ten process startups and, for an
> agent caller, ten full wake-ups. Always wait a fixed window instead, and the
> first event of an otherwise-idle day is delayed by the whole window.
>
> The answer is two clocks doing different jobs: a long wait for *nothing
> happening at all*, and a short one that starts only when the first event
> arrives. What makes it genuinely tricky is the set of conditions under which
> the run must **refuse to leave** — because each of them, got wrong, turns the
> tool into the busy polling loop it exists to replace, and it does so at full
> speed.

## Background

One run holds every configured channel open at once and returns when any of them
produces something — the same shape as a `select` with a timeout arm
*(sketch)*:

```go
select {
case ev := <-slackConversation:  // one arm per configured channel
case ev := <-upstreamRepo:
case ev := <-buildEvents:
case <-time.After(quietTimeout): // the "nothing happened" arm
}
```

Two intervals govern it:

| Interval | Typical | Meaning |
| --- | --- | --- |
| **Quiet timeout** | ~20 min | How long to wait when *nothing at all* is happening. Elapses → exit cleanly, no events. |
| **Boarding window** | ~2 s | Once the *first* event arrives, how much longer to keep collecting before departing. |

The analogy that names it: **the train waits at the station.** It does not
depart the instant the first passenger boards, and it does not sit for an hour
on the off-chance. The first passenger starts a short, bounded countdown, and
everyone already walking up the platform gets on. The window is a **fixed**
departure measured from the first event — it does not extend when more arrive,
because a sliding window has no upper bound against a chatty source and an
unbounded run defeats the point of being one-shot.

### The three ways a run must refuse to depart

Each of these looks like a strange edge case and each is the same failure — the
run returns almost immediately, the caller's loop relaunches at once, and one
process per attempt is spawned as fast as the machine allows.

```text
run starts
│
├─ nothing happening ──────────────────────────────►  quiet timeout (~20 min)
│                                                     elapses → exit, no events
│
├─ every stream has ended ─────────────────────────►  quiet timeout runs anyway
│                                                     elapses → exit
│
└─ first event detected at T
   │  → written to stdout immediately
   │
   ├─ boarding window opens: [T, T + ~2s]
   │     any further events are detected and written as they arrive
   │
   └─ window closes
      │
      ├─ every event came from a stream that has since errored
      │                       ─────────────────────────────────►  back to the
      │                                                           quiet timeout
      │
      └─ otherwise → close the streams → write state → exit
```

**Guard one — every stream has ended.** A `select` over an empty set returns
immediately, which is the natural implementation and the wrong answer. A run
with no streams left has nothing to wait *on*, but the caller does not
distinguish "returned because there was nothing to wait on" from "returned
because the timeout elapsed" — it just relaunches. Waiting the timeout out costs
nothing anybody is using and keeps the caller's pacing identical whether its
sources are quiet or broken. What tells the caller which it is looking at is the
failure records on stdout, not the timing.

**Guard two — a failure record does not open the window.** A `kind: error`
record is `botwatch` reporting *about* a source, not an event *from* one. Were
it to count, a channel that fails immediately at startup would open the window
on every run and every run would depart two seconds in — abolishing the quiet
timeout for anybody with one broken channel.

**Guard three — the door between the other two.** A driver that yields and
*then* fails walks between them: its events are genuine, so they open the
window, and its stream is only one of several, so the run is not out of streams.
Because a stream that ended in an error has its state discarded, those same
events are yielded again next run:

```text
run 1   page one reads fine → 5 events yielded → window opens
        token expires → page two raises → stream errors → state discarded
        window closes 2s in → run departs
run 2   ... identical. And run 3. And run 4.
```

Every run departs seconds after starting, indefinitely, and drags every *other*
channel's wait down with it because the window is run-wide. So: **at window
close the run departs only if at least one event it collected came from a stream
that has not by then errored**; otherwise it goes back to waiting out the quiet
timeout, and whatever was already written stays written.

The scope of that condition is *every event the window collected*, not the event
that opened it. A broken channel that yields first and then errors, alongside a
healthy channel yielding into the same window, **departs** — holding it back
would delay an event whose own stream never failed and which no later run would
replay.

### And the shutdown that fails on the very first run

To select over *N* channels the consumer holds one pending pull per stream. A
generator suspended at an `await` inside its body is *already running*, and
`aclose()` on it raises rather than closing it — falling back to the
interpreter's end-of-loop shutdown, which runs after the exit stack has already
unwound, not in reverse order of acquisition, and not on every exit path. That
is precisely the state every waiting driver is in when the boarding window
closes, which is the normal ending rather than an edge case. So the consumer
**cancels each in-flight pull and awaits its completion first**, and only then
lets the exit stack unwind.

## Scope

Implements [The execution model](0001.md#the-execution-model) of
[0001](0001.md) — the select, both clocks, all three departure guards, the
shutdown sequence, the `get_state()` read rules, and the exit-code contract —
plus the CLI entry point that binds `--config` and `--state` to a run.

**Out of scope:** the shape of what is written ([0004](0004.md)); the schema of
what is persisted and when the file is safe to read ([0003](0003.md)); the
driver-side obligations and their kit ([0005](0005.md)).

## The rules this implements

- **One driver instance per configured channel, per run**, constructed from the
  config and the previous state; retired channels are not instantiated.
- **Quiet timeout elapsing is success** — exit `0`, no events.
- **Every stream having ended does not end the run.** The quiet timeout runs
  anyway.
- **The first event is written immediately** and opens a **fixed** boarding
  window measured from it.
- **A failure record does not open the window.**
  ([Failure records](0001.md#failure-records))
- **At window close, the run departs only if at least one event it collected
  came from a stream that has not by then errored.** Otherwise it returns to the
  quiet timeout; already-written records stay written. ([The wait](0001.md#the-wait))
- **Streams are closed by cancelling each in-flight pull and awaiting it, then
  unwinding the exit stack** — in that order, in reverse order of acquisition,
  on every exit path including an exception.
- **The runtime satisfies [0005](0005.md)'s consumer contract**, exercised
  through the conformance kit's own consumer rather than restated here. Every
  driver is certified against that kit before this runtime exists, so the two
  closing behaviours must not be allowed to drift: if they do, four drivers have
  been conformance-tested against a consumer none of them runs under.
- **`get_state()` is read once, after a stream has ended by any means other than
  an error** — consumer-closed and driver-ended both record; **errored does not
  read it at all**, and that channel's recorded position stays as it was at the
  start of the run.
  ([The channel driver contract](0001.md#the-channel-driver-contract))
- **Exit `0` on completion**, including runs where individual channels failed
  and localised; **non-zero** when the run could not be constructed or
  completed. "No events" is deliberately not distinguished by exit code.
  ([Exit codes](0001.md#exit-codes))
- **The config is read once, at startup, every run.** ([One-shot](0001.md#one-shot))

## Acceptance

*Each criterion names the implementation it falsifies. A criterion that the
design's rejected alternative also passes is not coverage.*

- **A first run creates state and reports no history.** An empty state file and
  a config of *N* channels: state is created for all *N*, no events are reported
  from any of them retroactively, and the run exits on the quiet timeout with
  exit `0`.
  *Falsifies:* a startup that reads each source's available history and reports
  it, which is what a driver resuming "from the beginning" produces and which
  dumps a source's entire past at the caller on first sight.

- **A burst collapses, and a long burst splits.** *M* events arriving within the
  boarding window are reported by a **single** run in one process. A burst whose
  events go on arriving for longer than `boarding_window` after the first is
  **split**: the run departs at `first_event + boarding_window` carrying only
  what it collected by then, and the remainder reaches a later run.
  *Falsifies:* return-on-first-event (fails the first half) and a **sliding**
  window (passes the first half, fails the second). The split is the whole
  criterion — the collapse alone is equally true of the sliding implementation
  the design rejects.

- **The first event of an idle period is not delayed.** Measured **through a
  pipe**, not a terminal: the first event's line reaches the reader in well under
  a second, without waiting out either interval.
  *Falsifies:* always-wait-a-fixed-window, which delays it by the whole window;
  and block-buffered stdout, which delivers it at exit and passes an interactive
  test.

- **Guard one: every stream ended, no failures, and the run still waits.** Every
  driver ends its own stream immediately and none of them fails: the run waits
  out the quiet timeout and exits `0`, rather than exiting as soon as the last
  stream ends.
  *Falsifies:* selecting over the remaining streams and returning when the set
  empties — the natural implementation, and one that turns a total quiet period
  into a spawn loop.

- **Guard two: every driver fails immediately, and the run still waits.** Every
  channel's driver fails at startup: *N* failure records are written to stdout
  as they are observed, the run waits out the quiet timeout, and exits `0`.
  *Falsifies:* counting a failure record as an event, which departs two seconds
  in and abolishes the quiet timeout for anyone with one broken channel; and
  treating a run in which everything failed as a failed run, which exits
  non-zero and wedges the caller's loop on a condition that is per-channel by
  construction.

- **Guard three, negative: the only events came from a stream that has since
  errored.** One channel yields events and then errors, and no other channel
  yields anything. At window close the run does **not** depart: it returns to
  the quiet timeout, and the records it already wrote stay on stdout. Repeated
  against a source that fails at the same point every run, the caller's runs stay
  paced by the quiet timeout rather than collapsing to the length of the window.
  *Falsifies:* departing on any collected event.

- **Guard three, positive: a mixed run departs — including when the broken
  channel opened the window.** One channel yields and then errors while another
  yields and stays healthy: the run **departs** at window close. The criterion is
  run twice, with the failing channel yielding first and second.
  *Falsifies:* a guard scoped to the event that *opened* the window rather than
  to every event collected — which passes when the healthy channel happened to
  yield first, and holds a healthy channel's events for twenty minutes when it
  did not. This exact quantifier drifted repeatedly during the RFC's review; the
  two orderings are what pin it.

- **The three endings are distinguished, and the errored one is not read at
  all.** Consumer-closed → `get_state()` read and recorded. Driver-ended →
  `get_state()` read and recorded. Errored → `get_state()` **not called**, and
  the channel's recorded position is byte-identical to the start of the run.
  The errored case uses a driver whose `get_state()` raises if called, so
  "not called" is observable rather than inferred.
  *Falsifies:* treating driver-ended as an error, which discards the position of
  a driver doing exactly what the contract asks and replays from the beginning
  forever; reading state from a failed stream, which advances a cursor on the
  word of a driver that just failed; and calling it and discarding the result,
  which passes a position-unchanged assertion while imposing on every driver
  author the obligation to make `get_state()` correct after an arbitrary
  exception.

- **Shutdown cancels before it closes.** With *N* drivers all suspended
  mid-pull at window close: every driver's cleanup runs, in reverse order of
  acquisition, with **no `RuntimeError` raised anywhere**, and the same holds
  when the run is unwound by an exception rather than a normal departure.
  *Falsifies:* unwinding the exit stack first. That implementation still runs
  every driver's cleanup — the interpreter's asyncgen shutdown does it at
  end-of-loop — so a criterion asserting only "cleanup ran" is green while the
  ordering and the exception path are both broken. The `RuntimeError` and the
  ordering are what make it a real check.

- **The runtime closes streams the way the conformance kit's consumer does.**
  The kit's consumer contract from [0005](0005.md) is run against this runtime,
  not only against its own stub: the cancel-then-close sequence, the ordering,
  and the point at which a driver's `finally:` observes the close are the same
  under both.
  *Falsifies:* a runtime that closes correctly by its own lights while differing
  from the consumer every driver was certified against — which no driver test
  and no runtime test detects alone, because each is green against the consumer
  it was written for. This is the four-dialects failure [0005](0005.md) exists
  to prevent, moved up a level from the drivers to their consumer.

- **The exit code says whether the run completed, not whether anything
  happened.** A run with events, a run with none, and a run in which some
  channels failed and localised all exit `0`. A structurally invalid config, and
  a state path that cannot be written, exit non-zero.
  *Falsifies:* overloading the exit code with "were there events", which tempts
  callers into branching on it and gets the empty case wrong.

- **The config is read once.** Rewriting the config file while a run is waiting
  changes nothing about that run — not its channel set, not its timing.
  *Falsifies:* re-reading or watching the config, which reintroduces the
  "what happens when the config changes underneath a running process" question
  that being one-shot exists to delete.

- **Two channels on one source are two channels.** Two keys of the same type
  pointing at the same underlying source get two driver instances, two state
  blocks, and independent cursors and `meta`.
  *Falsifies:* deduplicating instances by resolved source, which silently
  couples channels the caller deliberately separated.

## Open questions from [0001](0001.md)

- **Per-channel timing overrides** ([question 3](0001.md#open-questions)) —
  **assigned here.** The config sketch already permits them, so this is not a
  question that can be left open through v1: shipping a field whose behaviour is
  undecided means a caller can write one and get whatever the implementation
  happened to do.

  Three answers are on the table — ignore it, reject it at validation, or make
  the window global and never overridable — and the entanglement is with the run
  context, which carries the **run-wide** `defaults`. A driver on a channel that
  overrides `boarding_window` would read the run-wide value there rather than
  its own, which is the run context's own motivating example turned around.
  **Answering this means saying what such a driver sees**, and any answer that
  leaves a driver able to read a value that does not apply to it is not an
  answer.

  A concrete case to decide against rather than in the abstract:
  [0012](0012.md), where a genuine push source has nothing to wait for and so
  nothing meaningful to do with a boarding window at all.

  **The answer needs a fourth field category first, and that is an amendment to
  [0001](0001.md).** As the RFC stands, a channel carrying `boarding_window` is
  a runner setting under one sentence of [`Shape`](0001.md#shape) and the
  driver's own schema under the next — so it reaches the driver and never
  reaches the runner, and the override cannot work under any of the three
  answers. [0002](0002.md) records the collision in full; the shape of the fix
  is that a channel's fields are `key`, `type`, `meta`, **the run-level timing
  keys**, and the driver's schema — or that this question closes by deciding
  per-channel overrides do not exist, which deletes the category along with the
  case. Whichever is chosen has to be written back into `0001`'s `Shape`
  section, since that is where the two colliding rules live.

  **This decision comes out of order, and has to be pulled forward.** It is
  assigned here, but [0002](0002.md) implements the channel-field handling that
  depends on it and lands first, while this issue lands fifth. Nothing else in
  this issue is needed to answer it — it is a design question about what a
  driver sees and what the loader does, not about the runner — so **the answer
  is owed ahead of this issue's implementation position**. Until it lands,
  0002's channel-level timing-key handling is provisional.
